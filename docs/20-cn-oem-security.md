## 20.0 本章方法与取证限制

### 20.0.1 为什么本章必须先讲「方法」

本章的主题是「国内新势力车企在硬件、通信、平台、OTA、合规五个切面上做了什么」。这是一个**看起来可以写得很厚、实际上极难取证**的题目：车云安全的核心构件（安全芯片型号、握手算法、证书链、OTA 签名方式、密钥托管）几乎全部落在**企业内部文档、供应链合同、器件 Datasheet、招标文件**里，而不是落在面向消费者的官网上。因此，本章若不先讲清取证条件，读者极容易把「本章写得薄」误解为「这些企业做得薄」。

依据 dossier §0（本次采集方法与局限），本次调研存在**三重结构性限制**，必须逐条重申：

**限制一：检索工具不可用。**
- `web_search` / `web_extract` 全程返回 `Insufficient credits`（Firecrawl 402/429），额度耗尽且不自动恢复。**本次调研无法做开放网络发现，只能「直取已知权威 URL」。**（dossier §0）
- 公开搜索引擎在本运行环境同样不可用：Bing 被地理重定向至 cn.bing.com 且对中文品牌词返回噪声；Baidu / Sogou / 360 触发验证码；Google 返回 `/sorry` 机器人墙或空结果；DuckDuckGo 验证码。（dossier §0）
- 直接后果：本节标题里的「五个切面」里，**硬件与通信两个切面几乎无法用关键词去「搜」出来**——它们恰恰最依赖开放检索。这两格因此注定大面积「未取证」。

**限制二：区域与网络封锁。**
- `bmw.com` / `bmwgroup.com` / `rivian.com` 被 Akamai/CloudFront 区域封锁（HTTP 000 / 403）。（dossier §0）
- `iso.org`、`unece.org`、`autosar.org`、`trustedcomputinggroup.org` 被 Cloudflare 或超时拦截；`open.xiaopeng.com` 对所有请求返回 403（openresty）。（dossier §0）
- 直接后果：**AUTOSAR Classic（Crypto Stack / SecOC / IdsM）、TCG TPM 2.0、SHE 这几套「车载硬件安全」的规范文本本次全部取不到正文**（dossier §4 标注为「未验证 / 未找到可核验公开一手 URL」）。因此本章在描述「行业通行的硬件安全做法」时，能援引的规范只能到 GlobalPlatform TEE、EVITA 分级、NIST FIPS/SP 系列这一层。

**限制三：覆盖度偏置。**
- 证据密度向「文档公开可达」的企业倾斜。dossier §0 原文：「对文档未公开的企业（BMW、Rivian、小鹏、极氪、零跑、理想、华为、奇瑞）证据薄弱。**「未找到公开来源」= 本次披露缺口，绝不等于能力缺口**，不得反向推断为「该企业没有该能力」。」
- 直接后果：**本章九家国内车企的证据密度，显著低于国际同行**（对照 dossier §7.1 Tesla 与 §7.2 Mercedes-Benz 的文档完整度）。但这是**披露差异**，不是能力差异。

**本章的写作纪律（与 `00-engagement-plan.md` §3.2 红线对齐）**：
1. **禁止**把 [合理推测] 写成陈述句事实（红线 1）；
2. **禁止**编造 URL、标准编号、条款号、数字、时间（红线 3）；
3. **禁止**把「未找到公开来源」反向表述为「该企业不具备」（中立性红线，红线 4）；
4. 引用单篇原文不得超过该节篇幅的 5%（红线 5）。

### 20.0.2 本章的「应然—实然—缺口—推演」四段式

`00-engagement-plan.md` §4 的方法论给出「证据分层写作法」与「缺口显式化」。本章把它固定为**每个切面的四段式**，贯穿全章：

```
[应然] 国标/规范要求了什么   ── 事实类，有标准依据（20.1）
   │
[实然] 国内可观测到的公开证据 ── 已取证事实（20.2 各家的 (1)-(5)）
   │
[缺口] 逐项列出的证据缺口     ── 「未取证 + 补证动作」（20.5 / 20.6）
   │
[推演] 基于规范的设计空间推演 ── 显式标「[合理推测] / 本报告判断」（20.2 各家的 (1)-(5)）
```

**为什么必须这样写而不是直接写「实现描述」？** 因为 dossier §7.10 第 5 条明确记载：

> **「9 家国内车企本次全部未取得关于『国密 SM2/SM3/SM4』、『mTLS 双向证书』、『证书轮换』、『HSM/SE/TEE』的任何官方一手来源 —— 报告中这些方向的结论一律写为『未找到公开来源 / 待补证』，禁止以行业常识冒充车企事实。」**

这句话直接决定了本章的性质：**本章的主线不是「车企怎么做的」，而是「国标要求了什么 + 国内公开可见的证据有什么 + 缺口在哪里 + 在规范约束下可能的设计空间是什么」。** 任何试图把本章改写成「九家车企硬件安全实现对比」的做法，都会立刻违反 dossier §7.10 第 5 条与 `00-engagement-plan.md` §3.2 第 3 条红线。

## 20.1 国内厂商面临的四大切面合规要求（全章的「应然」基准）

本节回答「**国标要求了什么**」。全部为**事实类**，事实来源于 dossier §1、§3、§4、§5、§6 的一手条目（国家标准全文公开系统 / RFC Editor / 官方规范库）。**本节只陈述标准的存在、编号、名称、发布/实施日期与主题定位；本次未取得任何标准正文条款，因此不给出任何条款编号或款级要求**（`00-engagement-plan.md` §3.2 第 3 条红线）。

### 20.1.1 硬件与密码：GB 44495-2024 与国密算法族

**强制性国标的定位。** dossier §1.1（[A]）载明：
- **GB 44495-2024《汽车整车信息安全技术要求》**——发布 2024-08-23，**实施 2026-01-01**，属**强制性**国标（状态「现行」）。
- **GB 44496-2024《汽车软件升级通用技术要求》**——发布 2024-08-23，**实施 2026-01-01**，同为强制性。

GB 44495 是「整车信息安全」的强制基线。任务要求本章陈述「GB 44495-2024 对身份认证与密码技术的要求方向」。**必须诚实声明：本次未取得 GB 44495 正文，因此无法逐条给出它对密码技术的要求项。** 我们只能从标准名称（「整车信息安全技术要求」）与强制性定位推断其覆盖方向（[合理推测]）：整车信息安全要求的**方向**通常会覆盖身份认证、密码技术、通信安全、数据保护、访问控制、软件升级与安全审计等域；（GB/T 40856-2021 同系的推荐性标准的名称结构——「车载信息交互系统信息安全技术要求及试验方法」——也提示这一分层）。（本报告判断，推测，非事实）

**国密算法族（SM 族）。** dossier §1.2（[A]）给出完整的一手条目：

| 标准号 | 名称 | 在本章语境中的角色 |
|---|---|---|
| GB/T 32918.1~.5-2016/2017 | SM2 椭圆曲线公钥密码算法（总则 / 数字签名 / 密钥交换 / 公钥加密 / 参数定义） | 签名 + 密钥交换 + 公钥加密三合一；取代 ECDSA/ECDH/RSA 的位置 |
| GB/T 32905-2016 | SM3 密码杂凑算法 | 取代 SHA-256 的位置（含 HMAC-SM3） |
| GB/T 32907-2016 | SM4 分组密码算法 | 取代 AES 的位置（含 SM4-GCM / SM4-CCM 等 AEAD 构造） |
| GB/T 35275-2017 | SM2 密码算法加密签名消息语法规范 | **消息语法层**：定义 SM2 加密/签名消息的封装格式 |
| GB/T 35276-2017 | SM2 密码算法使用规范 | **使用层**：定义 SM2 的使用约束 |

**为什么「消息语法」这一层很关键？** 因为「用了 SM2 算法」不等于「产出了可互操作的国密报文」。GB/T 35275 定义的是**消息语法**——即密文/签名的封装结构（相当于国际栈里的 PKCS#7/CMS 位置）。dossier §3 另列有 RFC 8017（PKCS #1 RSA）与 RFC 5480（ECDSA/EC 公钥在 X.509 中的表示），可与 GB/T 35275 形成对照：**国际栈把「算法」与「消息语法」分成 RFC 8017 / RFC 5280 / RFC 5480 三条线，国密栈把对应能力收进 GB/T 35275 / 35276 与 GB/T 32918 系列。** （本报告判断，对照为推测，非事实）

**RFC 8998：国密 TLS 的国际落点。** dossier §3（[A]）载明：
- **RFC 8998 (2021) ShangMi (SM) Cipher Suites for TLS 1.3**——SM2 签名、AEAD_SM4_GCM / AEAD_SM4_CCM、SM3。dossier 对该条的定位注释为：「**国密 TLS 在国际标准层面的唯一落点，国产车云链路合规的关键**」。

**为什么国产链路需要 RFC 8998？** 因为车云链路的上行/下行几乎必然走 TLS（dossier §3 同时列有 RFC 8446 TLS 1.3）。若要做国密化，就必须回答「国密算法如何嵌进 TLS 1.3 的握手框架」——RFC 8998 给出了标准答案：**在 TLS 1.3 的既有握手框架内，用 SM2 做证书签名与握手签名，用 AEAD_SM4_GCM / SM4_CCM 做记录层加密，用 SM3 做杂凑。** 这样国密 TLS 与标准 TLS 1.3 可以在同一套握手状态机下协商，而不是另起一套协议。（本报告判断，推测，非事实）

**硬件根信任的规范侧。** dossier §4 列出的**可援引**一手/权威条目：
- GlobalPlatform TEE System Architecture v1.3（规范号 GPD_SPE_009）—— [A]
- GlobalPlatform 规范库 Secure Element 分类 —— [A]
- OP-TEE（开源 TEE OS）—— [A]
- ARM TrustZone for Cortex-A / Cortex-M —— [B]
- EVITA 项目（定义车载 HSM 的 **Full / Medium / Light 三级分级**）—— [B]
- NIST FIPS 140-3（密码模块安全要求，HSM 认证基线）—— [A]
- NIST FIPS 186-5、FIPS 197、SP 800-57 Part 1 Rev.5、SP 800-38D、SP 800-90A Rev.1、SP 800-133 —— [A]
- Infineon AURIX / TriCore、NXP S32、Renesas RH850、TI Jacinto TDA4VM —— 器件页 [C] 或 [未验证]

**必须声明的阻断**：AUTOSAR Classic Platform（Crypto Stack、SecOC、IdsM 入侵检测）在 dossier §4 标注为 [未验证：autosar.org 超时]；TCG TPM 2.0 为 [未验证：站点 403/超时]；**SHE（Secure Hardware Extension）规范标注为「未找到可核验公开一手 URL：成员制规范」**。这意味着**本章在描述「车载密码栈」时，最贴合车规的 AUTOSAR Crypto Stack 与最通用的 TPM/SHE 均无正文可援引**——这本身就是本章 H1 切面「要求 + 缺口 + 推演」性质的成因之一。

### 20.1.2 通信：GB/T 40855 / 40856 / 40857 三份推荐性国标的适用边界差异

dossier §1.2（[A]）给出三份 2021 年同批发布的推荐性国标，均「发布 2021-10-11，实施 2022-05-01」：

| 标准号 | 名称 | 适用对象（仅就名称与适用对象谈） |
|---|---|---|
| **GB/T 40855-2021** | 电动汽车远程服务与管理系统信息安全技术要求及试验方法 | **「远程服务与管理系统」**——即 TSP / 车云服务端（云侧 + 远程服务链路） |
| **GB/T 40856-2021** | 车载信息交互系统信息安全技术要求及试验方法 | **「车载信息交互系统」**——即车机/座舱侧的信息交互系统（T-BOX、车机 OS、人机交互） |
| **GB/T 40857-2021** | 汽车网关信息安全技术要求及试验方法 | **「汽车网关」**——即车内中央网关/域控制器（车内网络边界） |

**三者的适用边界差异（只谈边界，不给条款）：**
- **GB/T 40855** 落在**云与远程服务**的一端，是本章 H2「通信与证书」与 H3「应用与平台」在推荐性国标上的直接对应物；
- **GB/T 40856** 落在**车机/信息交互系统**的一端，对应「车云链路的车端终结者」；
- **GB/T 40857** 落在**车内网关**的一端，是车内网络与外部网络之间的**边界防护**对象；
- 三者合起来正好覆盖**「云 → 车机 → 网关」**这条垂直链——与 dossier §1.2 另列的 GB/T 38628-2020（汽车电子系统网络安全指南）配合，构成「指南 + 三段技术要求」的组合。

**写作限制**：上述「覆盖垂直链」「落在哪一端」的判断，是基于**标准名称与适用对象**的结构性归纳（本报告判断，推测，非事实）。本次**未取得三份标准正文**，因此**不给任何条款号、不陈述任何具体技术要求项**。

### 20.1.4 OTA：GB 44496-2024 与 GB/T 47325-2026 的定位

dossier §1.1 / §1.2（[A]）：

| 标准号 | 名称 | 性质 | 发布 | 实施 |
|---|---|---|---|---|
| **GB 44496-2024** | 汽车软件升级通用技术要求 | **强制** | 2024-08-23 | **2026-01-01** |
| **GB/T 47325-2026** | 车联网在线升级安全技术要求与测试方法 | 推荐 | 2026-03-31 | 2026-10-01 |

**定位差异（只谈定位，不提条款）**：GB 44496 是**强制**的「软件升级通用要求」，即 OTA 的**合规底线**；GB/T 47325 是**推荐**的「在线升级安全技术要求与测试方法」，偏**在线/远程升级的安全与测试方法**。二者构成「强制通用 + 推荐在线专项」的组合，与 20.1.1 的 GB 44495（强制整车）形成「整车 + 升级」双强制基线。（本报告判断，推测，非事实）

**规范侧对照（dossier §6，[A]/[B]）**：中国 OTA 国标之外，国际侧可援引的公开规范包括：
- **Uptane 框架**（[A]）：dossier 定位「首个面向汽车、面向『可抵御国家级攻击者』设计的软件更新安全系统」，Linux Foundation JDF 项目；**Uptane Standard 2.1.0**（[A]）给出 Director 仓库 + Image 仓库**双仓库模型**。
- **TUF**（[A]/[B]）：Root / Targets / Snapshot / Timestamp 四角色 + 委托 + threshold/quorum 阈值签名模型，用于防仓库/密钥泄露。
- **IETF SUIT**：RFC 9019（固件更新架构，[A]）、RFC 9124（SUIT Manifest 信息模型，[A]）。
- **SBOM**：SPDX（[A]，对应 ISO/IEC 5962:2021）、CycloneDX（[B]）。
- **供应链完整性**：SLSA v1.0 分级（Build L0–L3，[A]）、in-toto（[B]）。

**这组国际规范的共同点**：它们都把「OTA 安全」建模为**「签名 + 阈值 + 版本防回滚 + 元数据可验证」**的问题，而不是单纯「加密传输」。**中国 OTA 国标（GB 44496 / GB/T 47325）与这套国际模型是否对齐，本次无正文可核，属待补证。**（本报告判断，推测，非事实）

### 20.2.1 蔚来 NIO

**(1) 硬件与密码**
- 已取证事实：**无**。dossier §7.7 只取到 Open NSC（服务云开放平台）与隐私政策页，均不涉及硬件/密码。
- 未取证项：TEE/SE/HSM 选型；数字钥匙的密钥存储载体；SM2/SM3/SM4 使用与否；HSM 认证等级（如 FIPS 140-3 / 国密二级）；密钥生命周期与托管方式。以上**均无公开一手来源**。
- 设计空间推演（[合理推测]，非事实）：
  1. **可检验推断 A-1**：若蔚来在海外的车云链路存在，则其车云握手可能采用「国际 TLS 1.3（RFC 8446）+ 常规 X.509（RFC 5280）」栈；若其面向国内销售车型的车云链路需满足国内合规，则**有可能**在其上叠加国密路径（RFC 8998）。（可检验：抓取其 App/车机对云端的 TLS ClientHello，看是否含 `TLS_SM4_GCM_SM3` 等套件。）
  2. **可检验推断 A-2**：数字钥匙若采用 CCC 3.0 路线（dossier §5），则密钥**应存储于 Secure Element**（[A] CCC 3.0 明载「密钥存储于 Secure Element」）——但这只说明「若用 CCC 3.0 则如此」，**不能反推蔚来用了 CCC 3.0**。dossier §7.10 第 1 条：「蔚来 UWB+蓝牙+NFC 三合一数字钥匙」仅见新浪汽车等**二手报道**（[C]），蔚来官方未取得技术说明，无法确认是否 CCC 3.0、是否有 SE 保护。
  3. **可检验推断 A-3**：若蔚来满足 GB 44495 的密码技术要求方向，则其**车端到云端**的关键指令链路**可能**具备签名与防重放（时间戳/序号）机制（依据 RFC 3161 可信时间戳的通用做法）。（可检验：对车机→云与云→车指令进行抓包，观察是否有单调递增序号或时间戳字段。）

**(2) 通信与证书**
- 已取证事实：**无**。dossier 未取到任何蔚来车云链路的 TLS/证书信息。
- 未取证项：是否 mTLS；证书签发与轮换机制（RFC 8555 ACME 式自动化 vs 离线签发）；证书吊销（CRL vs OCSP）；证书链信任锚；是否使用国密证书（GB/T 35275 消息语法）。
- 设计空间推演（[合理推测]）：
  1. **可检验推断 A-4**：车云「服务端到服务端」的链路（如 TSP 与车企内部系统）**可能**采用 mTLS（RFC 8705）以绑定调用方身份；而「车端到云」的链路可能因车端资源约束采用单向 TLS + 应用层签名。这是移动/IoT 场景的常见取舍。（本报告判断，推测）
  2. **可检验推断 A-5**：若采用短周期证书，则**应**存在自动化轮换（RFC 8555）；反之若证书为长周期，则吊销能力（RFC 6960 OCSP 或 CRL）会成为关键控制点。（可检验：从车端/云侧证书的 `notAfter` 长度反推轮换周期。）

**（三）三条横向推演（[合理推测]，非事实）**
1. **合规驱动是共同外因**：九家里**没有任何一家**在官网公开了「国密 / mTLS / OTA 签名」技术说明，而九家**全部**受 GB 44495/44496 约束（2026-01-01 强制）。**本报告判断**：这**更可能**反映「合规信息走监管报送而非公开披露」（见 20.4 成因 2），而非「技术缺失」。
2. **开放形态分化**：比亚迪走「企业级 ESB」（i迪桥）、蔚来走「服务云 + 文档受控」（Open NSC）、理想/零跑/奇瑞/极氪**未见**开放平台。**本报告判断**：这**可能**对应三种不同的对第三方开放策略（企业 B 端 / 服务生态 / 暂不开放），**但这是治理策略差异，不是安全水位差异**。
3. **披露生态薄弱但可观测**：仅奇瑞取到官方漏洞专栏。**本报告判断**：这**可能**反映「缺乏公开赏金文化」（见 20.4 成因 6），而非「无响应能力」。

## 20.3 国内特有的两个切面

### 20.3.1 国密合规在车云的落地路径

本节把「国密在车云上落地要改什么」拆成**算法替换范围、协议栈影响、互操作代价**三段，并与 30/31 章的「双轨制」分析呼应。**本节全部为规范层事实 + 显式标注的推演；不含任何车企实现断言。**

**（一）算法替换范围（规范层事实，dossier §1.2 / §3，[A]）**

| 密码功能 | 国际栈（RFC 编号） | 国密栈（GB/T 编号） | 替换范围说明 |
|---|---|---|---|
| 数字签名 | ECDSA（RFC 6090 / RFC 5480）、RSA（RFC 8017） | **SM2**（GB/T 32918.2 数字签名） | 证书签名、握手签名、消息签名全替换 |
| 密钥交换 | ECDH / RSA 密钥传输 | **SM2**（GB/T 32918.3 密钥交换） | 握手密钥协商、会话密钥派生 |
| 公钥加密 | RSA（RFC 8017） | **SM2**（GB/T 32918.4 公钥加密） | 报文加密、密钥封装 |
| 杂凑 | SHA-2 系列 | **SM3**（GB/T 32905） | 证书指纹、HMAC、KDF 全部替换 |
| 分组加密 | AES（FIPS 197 / SP 800-38D GCM） | **SM4**（GB/T 32907，含 GCM/CCM AEAD） | 记录层对称加密 |
| 消息语法 | PKCS#7/CMS（RFC 8017 系） | **GB/T 35275**（SM2 加密签名消息语法） | 报文封装格式 |
| 使用规范 | — | **GB/T 35276**（SM2 使用规范） | SM2 参数与使用约束 |

**关键观察**：国密化不是「换一个签名算法」，而是**从「签名、密钥交换、加密、杂凑、分组密码、消息语法」六个层面同时替换**。且国密栈在这六层上都有独立国标（GB/T 32918/32905/32907/35275/35276），不是国际栈的「局部补丁」。（本报告判断，基于 dossier §1.2 条目结构的归纳）

**（二）协议栈影响（规范层事实 + 推演）**

- **TLS 套件层**：RFC 8998（[A]）给出 TLS 1.3 下的 SM 套件：**SM2 签名 + AEAD_SM4_GCM / AEAD_SM4_CCM + SM3**。这意味着**国密 TLS 复用 TLS 1.3 的握手状态机**（RFC 8446），只替换其中的密码原语与套件标识。（dossier §3）
- **证书格式层**：国密证书需承载 SM2 公钥与 SM3 签名，对应 **GB/T 35275** 的消息语法与 **GB/T 35276** 的使用规范。**本次未取到「国密证书在 X.509 扩展中的编码约定」的国标正文，属待补证**（对照国际侧的 RFC 5280 / RFC 5480 是明载的）。
- **轮换与吊销层**：国际栈的自动化轮换（RFC 8555 ACME）与状态查询（RFC 6960 OCSP / RFC 5280 CRL）在国密栈中**是否有对应国标**，本次**未取证**——这是国密落地路径上一个**明确的证据空白**。
- **C-V2X 层**：**GB/T 45112-2024**（[A]）是中国 C-V2X 的证书管理体系国标，是「车-云-车」证书体系的国家级规范。**它与 RFC 5280 通用 PKI 的关系（是否兼容/映射）本次未取证**，属待补证。

**（三）与国际栈的互操作代价（[合理推测]，非事实）**

当一辆车在中国销售、又需要与国际云互通（或车企的全球云与中国云并存）时，会面临「双栈」问题。**本报告判断（推测）**其代价集中在四点：
1. **双栈证书与信任锚**：同一设备需管理国密信任锚与国际信任锚两套根，轮换周期需对齐（否则一侧吊销会影响另一侧信任建立）。
2. **双栈握手协商**：需在 ClientHello/ServerHello 中协商套件族（RFC 8998 的 SM 套件 vs 常规 TLS 1.3 套件），且需处理「一端只支持一种栈」的降级情形。
3. **器件支持**：HSM/SE/TEE **需同时支持 SM 与国际算法**——这正是 31 章 T6「双轨互操作压力」在硬件层的落点（`31-summary-trends.md` T6：「HSM/SE 需同时支持 SM 与国际算法」）。
4. **算法迁移窗口**：存量设备的算法替换**需**OTA 分批实施，与证书轮换窗口叠加。

**与 30 章「双轨制」分析的呼应**：本章 20.3.1 的三段（替换范围 / 协议栈影响 / 互操作代价）即 31 章 T6（「国内合规体系与国际 PKI 栈的双轨互操作压力」）与 P2-4（「双栈密码迁移路径」）在**硬件与通信切面**的展开。**需要注意主体边界**：T6/P2-4 是**趋势/建议层**的判断（标注为推测），本章 20.3.1 的**事实层**只到「国密有独立国标族 + RFC 8998 是 TLS 1.3 唯一国际落点」为止；**「某车企实现了双栈」属未取证，不得写入。**

**（四）国密落地的三条可检验推断（[合理推测]）**
- **可检验推断 GM-1**：面向国内销售且需满足国密的车型，其车云握手**应**至少在国内链路上出现 SM 套件（`TLS_SM4_GCM_SM3` 类）；可通过**被动**抓取 ClientHello 观察套件列表验证（受 §1 范围约束，不做主动测试）。
- **可检验推断 GM-2**：若车企采用双栈，其证书管理**可能**存在两套信任锚，可通过证书透明度或设备证书链观察验证。
- **可检验推断 GM-3**：国密化的进度**应**与「GB/T 32918/32905/32907 与 RFC 8998 对应的器件支持清单」相关；可通过器件厂 Design Win 公告侧面验证。

## 20.4 国内车企公开信息供给不足的结构性解释

**本节全部为 [合理推测]（本报告判断，推测，非事实）。** 本节的目的不是「解释为什么他们不公开」，而是**为「为什么本章取证这么难」提供一组可证伪的假设**，避免读者把「证据缺口」误读为「能力缺口」（红线 4）。每条给出**可检验推断**。

| 序号 | 可能成因（推测） | 可检验推断 |
|---|---|---|
| 1 | **B 端客户保密习惯**：国内车企的核心客户/供应商关系偏 B 端，安全能力被视为商务谈判资产而非公开营销素材。 | 若成立，则其安全信息**应**更多出现在**投标文件/RFI 应答**而非官网；可检验：向车企发 RFI 是否比检索官网更易获得信息。 |
| 2 | **监管报送而非公开披露**：合规信息（如 GB 44495 符合性）**可能**以监管报送/备案形式存在，而非公开文档。 | 若成立，则其合规证据**应**在**监管公示/认证公示**渠道而非企业官网；可检验：检索工信/网信/认证机构的公示库。 |
| 3 | **开放平台以商务对接为主**：开放平台**可能**设计为「先签约、后开通」，文档不公开。 | 若成立，则开放平台文档**应**需登录或线下申请（蔚来 Open NSC 的「文档访问需 token」、比亚迪的「组织认证」与 16 章记录的 app-id+secret/APIKey 均**符合**该模式）；可检验：自注册渠道是否存在。 |

| 5 | **供应链信息敏感**：安全芯片、HSM、PKI 供应商关系**可能**受保密协议约束。 | 若成立，则器件信息**应**更多出现在**器件厂 Design Win 公告**而非车企页面；可检验：检索芯片厂汽车 Design Win 公告。 |

| 7（补充） | **信息分散在非官网渠道**：中文技术信息**可能**分散在微信文档、飞书知识库、商务白皮书等**不可被通用检索触达**的渠道。 | 若成立，则常规官网检索**应**持续落空而商务渠道可获；可检验：通过合作伙伴获取其技术文档。 |
| 8（补充） | **本次检索工具失效放大缺口**（dossier §0）：检索额度耗尽 + 搜索引擎验证码，使**开放发现**能力被削弱。 | 若成立，则**恢复检索能力后**同一批 URL 之外**应**能发现更多公开材料；可检验：换出口 IP / 恢复额度后重跑同一批查询。 |

## 20.7 本章小结

**严格分开：事实三条 / 缺口三条 / 推演三条。** 三者不得互相冒充（`00-engagement-plan.md` §3.2 红线 1）。

### 20.7.1 三条事实（全部有 dossier 一手依据）

1. **合规是「应然」的底座已明确。** 中国车云安全有强制基线（**GB 44495-2024 / GB 44496-2024**，2026-01-01 实施）与密集的推荐性国标（**GB/T 40855/40856/40857-2021、47324-2026、47467-2026、45181-2024、45112-2024、44402.1-2024** 等），并有国密算法族（**GB/T 32918/32905/32907/35275/35276**）与国密 TLS 的国际落点（**RFC 8998**）。（dossier §1.1/§1.2/§3，[A]）
2. **国内公开证据只集中在「平台治理」与「数据/管理体系」两处。** 45 格中取得 [A] 的 7 格为：蔚来 Open NSC（文档访问受 token 保护）、小鹏 `open.xiaopeng.com`（403）、理想用户隐私政策（生效 **2026-01-22**，双主体：北京车励行 / 北京罗克维尔斯）、小米信任中心（**ISO/IEC 27001，编号 IS 831552**）、比亚迪 i迪桥（ESB 网关 + 版本公告 3.3.4）、奇瑞官网「网络产品安全漏洞」专栏。（dossier §7.6/§7.7/§7.8/§7.9，[A]）
3. **硬件与通信切面（H1/H2）在九家上「零一手证据」。** 这与 dossier §7.10 第 5 条的记载一致：**九家在国密、mTLS、证书轮换、HSM/SE/TEE 方向均无官方一手来源**。（dossier §7.10 第 5 条、§8，[A]）

### 20.7.2 三条缺口（未确证：披露缺口，非能力缺口）

1. **硬件与密码（H1）全缺**：九家的安全芯片/TEE/SE/HSM 选型、国密参数、密钥托管方式，**均未取证**（红线 4：不得写为「不具备」）。
2. **通信与证书（H2）全缺**：九家是否 mTLS、证书链与轮换机制、是否使用国密证书，**均未取证**。
3. **OTA 签名与 SBOM（D4/D5）全缺**：九家的 OTA 签名算法/密钥托管、SBOM（SPDX/CycloneDX）与供应链完整性（SLSA）实践，**均未取证**。此外**小米汽车专属开放平台、华为 Wallet Kit 数字车钥匙正文、小鹏/极氪/零跑/奇瑞的开放平台**因 JS 空壳/403/500/无 DNS 而未能取证（dossier §7.8/§7.9/§8）。

### 20.7.3 三条推演（[合理推测]，非事实；供下游假设检验）

1. **合规驱动是共同外因（推演）。** 九家**均**受 GB 44495/44496 约束（2026-01-01 强制），却**均未**公开国密/mTLS/OTA 签名技术说明。**本报告判断**：这更可能反映「合规信息走监管报送而非公开披露」（20.4 成因 2），而非技术缺失。**证伪条件**：若能在九家中找到任意一家公开的车云密码/证书技术白皮书，则该推演的「普遍不公开」部分被证伪（并不影响其他七家的判断）。
2. **双栈压力在硬件层落地（推演）。** 国密化需替换签名/密钥交换/加密/杂凑/分组密码/消息语法六层，器件（HSM/SE）**需**同时支持 SM 与国际算法，与 31 章 T6「双轨互操作压力」一致。**证伪条件**：若中国市场车云链路最终采用**单一**国密栈且不与国际栈并存，则「双栈压力」判断被证伪。
3. **披露生态薄弱但可观测（推演）。** 仅有奇瑞取到官方漏洞专栏 URL，**可能**反映「缺乏公开赏金文化」（20.4 成因 6），而非「无响应能力」。**证伪条件**：若能在其余八家中找到公开 SRC/赏金入口（如 16 章未覆盖的渠道），则该「薄弱」判断被证伪。
