本章严格采用证据分层写作法（对齐 00-engagement-plan.md §4 方法论第 4 条）：读者可以一眼区分「这是文档明载的」与「这是本报告的推测」。具体做法是：

31.1 事实层：本次调研确认了什么

本节列出 16 条已经取证确认的硬事实。每条带证据等级与所在章节。本节不含任何推测；凡涉及「其他车企是否同样如此」的反向推断，一律不在此节出现。

31.1.1 规范层面（可引用的标准底座）

F-01（[A]｜章 11、19；档案 §2.1）：OAuth 2.1 处于草案阶段，编号为 draft-ietf-oauth-v2-1-16，其方向性变更为强制 PKCE、废弃隐式流与密码模式、Bearer 令牌最小化。该草案经 RFC Editor / datatracker 取证（HTTP 200）。这意味着「授权码流 + PKCE」是原生 App 与公共客户端的事实基线。

F-02（[A]｜章 11、12；档案 §2.1）：发送方约束令牌在规范层有两条已发布路径：RFC 8705（2020） 定义 OAuth 2.0 Mutual-TLS 客户端认证与证书绑定访问令牌（令牌不可被复制到无对应私钥的持有者）；RFC 9449（2023） 定义 DPoP（Demonstrating Proof of Possession），以 DPoP 头 + JWK 指纹实现发送方约束。两条均为 Standards Track、经 RFC Editor 取证。

F-03（[A]｜章 11、13；档案 §2.1）：结构化授权与可协商授权在规范层各有落点：RFC 9396（2023） 定义 Rich Authorization Requests（RAR），以 authorization_details 结构化权限对象替代裸字符串 scope；RFC 9635（2024） 定义 GNAP（Grant Negotiation and Authorization Protocol），为「细粒度 + 可协商」的下一代授权协议，属 Standards Track、2024-10 发布。

F-04（[A]｜章 02；档案 §6）：固件更新安全在 IETF 侧有两条规范：RFC 9019（2021） 定义 IoT 固件更新的 SUIT 架构；RFC 9124（2022） 定义 SUIT Manifest 信息模型。二者与 Uptane 共同构成车云 OTA 的「防降级 / 防仓库泄露」参照体系。

F-05（[A]｜章 02；档案 §6）：OTA 安全的主参照体系为 Uptane Standard 2.1.0（Director 仓库 + Image 仓库双仓库模型）与 TUF 四角色（Root / Targets / Snapshot / Timestamp）+ 委托 + threshold/quorum 阈值签名。Uptane 由 Linux Foundation Joint Development Foundation 维护，其官网与最新标准页均在本次取证中可达。

31.1.2 国际车企的可读实现（公开文档最完整的两家）

F-06（[A]｜章 13、17；档案 §7.1）：Tesla Fleet API 是本次取证到的、公开文档中最完整的「车-云第三方授权」实现范例。其 scope 全清单为 12 个：openid、offline_access、user_data、vehicle_device_data、vehicle_location、vehicle_cmds、vehicle_charging_cmds、vehicle_specs、vehicle_pricing_info、energy_device_data、energy_cmds、enterprise_management；鉴权头为 Authorization: Bearer <token>；令牌分三类：第三方令牌（代表车主行事）、partner token、third-party-for-business token。

F-07（[A]｜章 12、17；档案 §7.1）：Tesla 的刷新令牌一次性使用（single use only）、3 个月后过期，并对「最近一次使用的刷新令牌」提供 24 小时复用宽限期；刷新失败返回 401 login_required（含令牌过期/被挤出、用户重置密码两种场景）。授权服务器元数据发布在 .well-known/openid-configuration（对应 RFC 8414 / OIDC Discovery）。

F-08（[A]｜章 12、13、17；档案 §7.1）：Tesla 的车端授权校验以虚拟密钥实现：密钥为 P-256 ECDSA（文档明载「车辆仅支持 prime256v1 密钥」），公钥须托管于 https://<domain>/.well-known/appspecific/com.tesla.3p.public-key.pem 且长期可用，私钥绝不可托管于域名；车辆在执行命令前或接受 Fleet Telemetry 配置前验证载荷签名。B2B 车辆自动添加虚拟密钥的条件为已配对密钥少于 20 把；单台车辆最多同时向 5 个第三方应用推流。

F-09（[A]｜章 13、14；档案 §7.1）：Tesla 已实现双层授权控制的直接证据：带 granular_access.hide_private=true 的车辆共享，即使被授予 vehicle_location，位置字段仍被拒绝，遥测返回 HTTP 403「location access not granted」。本报告据此把它判为 Informational → 正面控制案例（00-engagement-plan.md §3.3 的 CSO 判定示例之一）。

F-10（[A]｜章 13、14、17；档案 §7.1）：Tesla 存在一条退出逐车主同意模型的资源访问路径：vehicle_specs 与 vehicle_pricing_info 仅 Partner Token 可用、对任意车辆可用、无需车主授权。本报告按 00-engagement-plan.md §3.3 将其判为 High（授权控制例外），并建议以契约与审计补偿。

F-11（[A]｜章 13、17；档案 §7.2）：Mercedes-Benz 开发者平台文档明载两种鉴权集成模式：OAuth Authorization Code Flow 与 Client Credentials Flow；采用授权码流的理由是「部分 API 提供燃油状态、车门锁状态等数据，属 GDPR 意义上的个人数据，因此需要终端用户同意」。关键参数：授权端点与令牌端点为 ssoalpha.dvb.corpinter.net 下的 /v1/auth 与 /v1/token；访问令牌 expires_in 默认 3599 秒；刷新令牌一次性使用、返回新的访问令牌与新的刷新令牌；令牌端点客户端认证采用 HTTP Basic；scope 采用 mb: 三段式命名空间（示例：openid offline_access mb:vehicle:mbdata:fuelstatus）；同意界面展示 SCOPE 与 purpose URL。

31.2 事实层：本次调研未能确认什么

本节列出 12 条未能确认的缺口。每条写三段：缺口内容 / 为何重要 / 补证方式，并标注其在 19-authz-90-reference-tables.md §19.11 缺口台账中的对应编号（G-xx）。本节所有缺口均为「披露缺口」，不陈述任何主体「不具备」相应能力。

N-01（对应 G-01，优先级 高｜影响章 16）——国内 9 家车企的车云通信安全（mTLS / 国密）

  • 缺口内容：本次对 9 家车企的官网、开放平台、隐私政策、SRC 页均未检索到关于 mTLS 双向证书、国密 SM 算法在车云链路上的使用的任何官方一手来源。
  • 为何重要：车云链路的「哪辆车、哪个云服务」身份依赖双向认证，是授权层的信任前置；国密则是中国市场的合规路径（见 F-16）。
  • 补证方式：向车企发起 RFI、采购安全白皮书、检索专利与招标文件。

N-02（对应 G-02，优先级 高｜影响章 16、02）——国内车企的 TEE / SE / HSM 实现

  • 缺口内容：9 家车企的开发者门户与安全页均未披露车端密钥的硬件保管方案（是否有 SE/eSE、是否存在车载 HSM、TEE 实现形态）。
  • 为何重要：硬件根信任是 L0 层「私钥在哪里」的第一决策，决定令牌/密钥可否被远程提取。
  • 补证方式：器件选型逆向、T-BOX 拆解、芯片厂 Design Win 公告。

31.3 判断层：车云授权技术的六个演进趋势

本节全部内容标注为「本报告判断（推测）」。 每条趋势按五要素给出：趋势陈述 / 依据（已取证规范或事实）/ 时间尺度 / 对车企的影响 / 证伪条件。趋势依据只使用 31.1 的硬事实；时间尺度为本报告的区间估计，非精确预测。

T1 从粗粒度 scope 向结构化、可协商授权演进（RFC 9396 → RFC 9635）

  • 趋势陈述（本报告判断，推测）：车云授权将从「裸字符串 scope 表达类别级权限」逐步演进为「用结构化权限对象表达『哪辆车 / 哪个动作 / 哪个字段 / 多长时间』」，并在更长的时间尺度上出现可协商授权（客户端与授权服务器就授权内容协商）。
  • 依据：F-03（RFC 9396 RAR 与 RFC 9635 GNAP 均已发布，[A]）；F-06（Tesla vehicle_cmds 把「解锁 + 唤醒 + 摄像头」打包在一个 scope 内，是 scope 表达力上限的现实投影，[A]）；章 13 §13.1.1 的分析（裸字符串 scope 无法表达「仅这辆车 / 仅这个动作 / 仅这段时间」）。
  • 时间尺度（本报告估计）：规范已就绪（RAR 2023、GNAP 2024）；RAR 类结构化授权在头部实现中的采用区间约 3–5 年；GNAP 进入主流生产的区间更晚或不确定。此区间为本报告估计，非取证事实。
  • 对车企的影响：授权服务端的校验复杂度上升，需要引入策略引擎（章 15 §15.2）；同意界面的信息密度提高，需要把结构化权限翻译成用户可读的目的描述。
  • 证伪条件：若在未来可观察的窗口内，主流车企的公开授权文档仍只出现裸 scope 字符串、且授权服务器元数据中不出现 authorization_details_types_supported 类声明，则 T1 中「结构化授权成为主流」这一部分被证伪。

T2 从 Bearer 令牌向发送方约束令牌成为默认（RFC 8705 / RFC 9449）

  • 趋势陈述（本报告判断，推测）：对车控、位置、摄像头等高敏感资源的访问，将逐步从「持有即可用」的 Bearer 令牌，转向「持有且证明持有相应私钥」的发送方约束令牌（mTLS 证书绑定或 DPoP），并使约束成为高敏 API 的默认要求。
  • 依据：F-02（RFC 8705 / 9449，[A]）；F-08（Tesla 已把授权校验下沉到车端虚拟密钥，[A]）；章 02 §02.9 薄弱点 1（Bearer 令牌可复制是 OAuth 2.0 的固有语义，可利用性高）。
  • 时间尺度（本报告估计）：规范已就绪（8705 于 2020、9449 于 2023）；高敏接口采用约束令牌的普及区间约 2–4 年。本报告强调：这不是技术可用性问题，而是既有集成方的改造成本问题，故区间受生态迁移速度主导。
  • 对车企的影响：需要 PKI 与密钥托管基础设施（章 02 §02.3、章 12 §12.7）；DPoP 需要处理 nonce 与重放窗口；对第三方应用而言，纯后端集成的门槛提高。
  • 证伪条件：若公开的授权服务器元数据与 API 文档中长期只出现 Bearer 而不同时出现 DPoP/证书绑定（cnf）相关能力声明，且高敏车控接口仍接受可复制令牌，则 T2 被证伪。

T3 从「链路可信」向「资源级 + 字段级」双层授权（granular_access.hide_private 类机制）

  • 趋势陈述（本报告判断，推测）：授权判断将从「链路与令牌是否可信 + 是否含所需 scope」的单层判断，演进为「scope 之上的第二层资源/字段策略」，即授权被授予 ≠ 资源被放行的双层模型；字段级收窄（位置、摄像头、路线）会成为高敏资源的常规控制。
  • 依据：F-09（Tesla hide_private 对位置字段返回 403，[A]）；章 13 §13.3 提炼的四层决策流水线（令牌校验 → scope 检查 → 资源级策略 → 字段级过滤）；章 02 §02.9 薄弱点 6（对象级授权缺失是 API 安全最普遍的越权模式）。
  • 时间尺度（本报告估计）：该机制已在领先实现中出现（Tesla 2024 前后的文档形态）；作为行业惯例普及的区间约 3–5 年。
  • 对车企的影响：需要「资源级策略 + 字段级过滤」的策略引擎与统一的决策日志；流式通道（如推流）必须与请求-响应通道采用一致的拦截语义（否则字段级控制会被流式通道绕过，见章 13 §13.3.2 的「通道一致性」要点）。
  • 证伪条件：若该机制长期只在一家实现中出现、且在后续可观察窗口内无第二家跟进，或公开文档显示高敏字段仍仅按「类别级」放行，则 T3 的「成为惯例」部分被证伪。

T4 数字钥匙从 NFC / BLE 向 UWB + SE 演进（CCC 3.0、FiRa 2.0→4.0）

  • 趋势陈述（本报告判断，推测）：数字钥匙的近距离判定将从「以信号强度为主的 BLE」转向「以 UWB 测距为主的精确距离判定」，并把凭证保管收敛到 Secure Element；NFC 保留为强制备用通道。
  • 依据：F-12（CCC DK 3.0 明载 BLE + UWB + NFC 强制备用，密钥存 SE，[A]）；F-13（FiRa 规范从 2.0 迭代到 4.0，[B]）；章 02 §02.9 薄弱点 10（BLE 信号强度易受中继，若弱化 NFC 备用或省略测距校验可被中继攻击绕过）。
  • 时间尺度（本报告估计）：旗舰车型已见 UWB 化；主流车型普及区间约 2–4 年。
  • 对车企的影响：需要 UWB 芯片与 SE 的器件选型与认证；「距离判定」与「动作授权」需要双重校验；供应链（UWB 芯片、SE 供应商）的 Design Win 会成为能力的外部可验证信号。
  • 证伪条件：若 FiRa 版本迭代出现停滞、或 CCC 后续版本推迟/取消 UWB 的强制地位（即公开规范不再把 UWB 作为数字钥匙的核心通道），则 T4 被证伪。
  • 诚实性提示：F-12/F-13 是规范与联盟公告层的事实；「主流车企已大规模采用 UWB 数字钥匙」是本报告判断（推测），本次对国内车企的数字钥匙实现未取证（对应 N-05、N-12）。

T5 授权与数据合规的技术融合（同意、目的限制、数据最小化落到 API 字段级）

  • 趋势陈述（本报告判断，推测）：数据合规要求（同意、目的限制、数据最小化、分级）将从「政策文本」下沉为「授权系统的技术参数」，即合规要求被翻译成可观测的授权参数（字段级放行、purpose 绑定、同意撤销联动），最终落到 API 的字段级。
  • 依据：F-11（Mercedes 同意界面展示 SCOPE 与 purpose URL，[A]）；F-14/F-15（GB 44495 强制 + GB/T 47324/47467 指向平台与接口侧，[A]）；章 18 §18.3（GB/T 41871-2022 / GB/T 44464-2024 对车云数据处理的约束方向）；章 18 §18.10.2 结论一的「把合规要求翻译成可观测参数」。
  • 时间尺度（本报告估计）：受 2026-01-01 强制适用与 2026 年内实施的三部推荐性国标驱动；合规要求向 API 字段级下沉的区间约 1–3 年。
  • 对车企的影响：授权系统与数据分级系统需要打通；「目的限制」需要可审计的 purpose 记录；撤销必须贯穿到字段级与下游配置。
  • 证伪条件：该趋势的前置条件是上述推荐性标准被实际监管口径或采购要求引用（本次未取证）。若这些标准未被监管或采购引用、合规仍停留在政策文本层面，则 T5 的技术融合部分被证伪。

T6 国内合规体系与国际 PKI 栈的双轨互操作压力（国密 vs 国际栈）

  • 趋势陈述（本报告判断，推测）：面向中国市场的车云链路将同时承载「国密 SM 栈」与「国际 RSA/ECC 栈」，双栈证书、双栈握手与算法迁移的互操作压力将长期存在；RFC 8998 是二者的技术交点。
  • 依据：F-16（SM 族 GB/T 体系 + RFC 8998 为 TLS 1.3 唯一国际落点，[A]）；F-02（国际栈的发送方约束基于 RSA/ECC 体系）；章 02 §02.2.5、章 12 §12.7.3 的双轨分析。
  • 时间尺度（本报告估计）：持续区间约 3–5 年，与国标实施节奏（2025–2026 多部国标落地）叠加。
  • 对车企的影响：需要在「国际互操作」与「中国合规」之间做算法与证书体系的映射；HSM/SE 需同时支持 SM 与国际算法；证书轮换与信任锚需要双轨管理。
  • 证伪条件：若 RFC 8998 之上出现被广泛采用的第三方双栈方案且国际栈标准组织移除 SM 支持路径，或中国侧不再要求国密路径，则 T6 的「双轨压力」判断被证伪。

31.4.1 P0（地基级）：无论当前处于哪个成熟度，都应当先具备的能力

P0-1 逐车主同意（per-vehicle consent）与资源级策略

  • 现状风险：若授权只到「应用 + 类别级 scope」，一个被授予 vehicle_location 的第三方应用即可请求该账号下任意车辆的位置，形成对象级越权（BOLA）面（章 13 §13.7.1）；这是本报告与章 02 §02.9 共同指认的最高可利用性薄弱点之一。
  • 建议控制：在协议层 scope 之上叠加资源级策略——每次请求校验「令牌—车辆」绑定关系；对高敏字段（位置、摄像头、路线）实施字段级收窄；建立可复制的「授权被授予 ≠ 资源被放行」判定链（对标章 13 §13.3.3 的设计清单）。
  • 验证方法：以「用 A 车范围的令牌访问 B 车资源」为回归用例，期望 403/404 而非 200（章 13 §13.8.2 示例，域名与 VIN 均为虚构占位）；对流式通道同样做字段级拦截验证（通道一致性）。
  • 工程量级估计（估算）：策略引擎与判定链改造，数十人月量级；若已有网关可复用，量级下降。

P0-2 发送方约束令牌（避免纯 Bearer 承载高敏操作）

  • 现状风险：纯 Bearer 令牌「持有即证明」，一旦经日志、调试输出、客户端存储泄露即可被复制冒用（章 02 §02.9 薄弱点 1）。
  • 建议控制：对车控、位置、摄像头类接口要求证书绑定令牌（RFC 8705）或 DPoP（RFC 9449）；将 Bearer 的使用范围限制在低敏只读场景。
  • 验证方法：构造「无对应私钥用泄露令牌访问」的失败用例，期望被拒；检查授权服务器元数据是否声明 DPoP/证书绑定能力（对标 F-06 的 .well-known 发布形态）。
  • 工程量级估计（估算）：PKI/密钥托管与客户端改造，数十至百人月量级（依赖既有 PKI 成熟度）。

P0-3 短 TTL + 一次性刷新 + 轮换

  • 现状风险：长效访问令牌与「可重复使用的刷新令牌」扩大泄露暴露窗口；刷新竞态可被并发滥用（章 12 §12.2.2、章 14 §14.4.3）。
  • 建议控制：访问令牌采用短 TTL；刷新令牌一次性使用 + 轮换（对标 F-07 Tesla 与 F-11 Mercedes 的公开实现）；为「应用未持久化轮换后令牌」设计有界宽限并监控其滥用。
  • 验证方法：并发两次使用同一一次性刷新令牌，期望其一返回 invalid_grant 类错误（章 13 §13.8.2 示例）；监控宽限期内异常刷新频次。
  • 工程量级估计（估算）：授权服务器配置与并发安全实现，十至数十人月量级。

P0-4 撤销贯穿到车端（含下游配置回收）

  • 现状风险：撤销授权后，已下发令牌、已配置车端推送、已配对密钥可能仍生效（章 02 §02.9 薄弱点 7）。
  • 建议控制：车主侧提供可撤销入口；撤销触发令牌吊销（RFC 7009）+ 车端凭证回收 + 下游推流配置移除的联动（对标特斯拉「scope 撤销后配置被从车辆移除」的公开实例）。
  • 验证方法：撤销后测量「云端有效授权集合」与「车端有效凭证集合」的对账一致性；测量撤销到车端的同步时延上界（对应缺口 N-12）。
  • 工程量级估计（估算）：跨云、云车联动改造，数十人月量级。

P0-5 审计日志包含授权决策依据

  • 现状风险：日志只记状态码、不含决策依据、可被内部修改或保留期过短，会使事后追溯失效（章 02 §02.9 薄弱点 12）。
  • 建议控制：日志记录五要素（谁 / 何 scope / 何时 / 何策略 / 决策结果，章 02 §02.5.4）；只追加 + 完整性保护；保留期与合规要求对齐。
  • 验证方法：抽样一次被拒请求，核对日志是否含「命中的策略与拒绝理由」；核对日志的不可篡改性与保留策略。
  • 工程量级估计（估算）：日志管道与字段标准化，十人月量级。

31.4.2 P1（强化级）：在 P0 之上提升表达力与运营安全

P1-1 引入 RAR 结构化授权（RFC 9396）

  • 现状风险：类别级 scope 无法表达「仅这辆车 / 仅这个动作 / 仅这段时间」，转化为过度授权（章 13 §13.1.1）。
  • 建议控制：在高敏车控与数据 API 上支持 authorization_details 结构化权限对象，把授权范围显式化、可协商化。
  • 验证方法：检查授权服务器元数据是否声明结构化授权能力；构造结构化授权请求并验证服务端逐字段校验。
  • 工程量级估计（估算）：授权服务器与策略引擎扩展，数十人月量级。

P1-2 步进认证（RFC 9470）

  • 现状风险：车控等高危动作若与低危读取共用同一认证强度，会降低高危动作的认证门槛。
  • 建议控制：对高危动作实施步进认证（acr/amr 挑战），必要时结合 FIDO2/WebAuthn 抗钓鱼凭证（章 11 §11.5）；注意：FIDO/WebAuthn 在车云的落点须以实际集成验证为准，本报告不假设其已被车端原生支持。
  • 验证方法：对高危动作发起请求，期望收到步进认证挑战而非直接放行；验证挑战后令牌的目标范围。
  • 工程量级估计（估算）：认证编排改造，十至数十人月量级。

P1-3 少权限密钥分层与轮换自动化

  • 现状风险：单一高权密钥或长期不轮换的密钥，一旦泄露影响面覆盖全域（章 12 §12.7）。
  • 建议控制：按用途分层密钥（签名 / 加密 / 会话），最小权限；以 ACME（RFC 8555）等自动化手段做证书轮换；对车端密钥数量设上限作为影响范围控制（对标 F-08 的「20 把」上限）。
  • 验证方法：检查密钥分层与轮换作业记录；核对是否有自动化轮换与灰度回滚（章 02 §02.8 片段 B）。
  • 工程量级估计（估算）：密钥管理与轮换体系，数十人月量级。

P1-4 限流与配额作为安全控制（而非仅计费/成本控制）

  • 现状风险：限流配置过松则形同虚设，过紧则成为拒绝服务的放大器；配额耗尽可被构造成不自动恢复的可用性事件（章 13 §13.5.2）。
  • 建议控制：分级限额（不同命令不同配额）；对限额调整做变更管理与灰度；区分善意超限与突发异常；移除下游配置前设冷却并保留可恢复路径。
  • 验证方法：监控误限率；构造配额临界用例，验证有可恢复流程而非「不恢复」。
  • 工程量级估计（估算）：网关限流与告警，十人月量级。

31.4.3 P2（前瞻级）：为未来 3–5 年的演进预置能力

P2-1 跟踪 GNAP（RFC 9635）的采用动向

  • 现状风险：若可协商授权成为下一阶段主流，晚介入会增加迁移成本。
  • 建议控制：跟踪 IETF 实现清单与主流授权服务器的能力声明，评估在非生产实验环境先行验证的可行性。
  • 验证方法：检索 GNAP 实现清单与 .well-known 元数据（对应缺口 G-25，优先级中）。
  • 工程量级估计（估算）：预研，个位数人月至十人月量级。

P2-2 UWB 数字钥匙与 Secure Element

  • 现状风险：BLE 信号强度易受中继；若弱化 NFC 备用或省略测距校验，则数字钥匙可被中继绕过（章 02 §02.9 薄弱点 10）。
  • 建议控制：以 CCC DK 3.0 的BLE + UWB + NFC 强制备用为参照，把凭证保管收敛到 SE，做「距离判定 + 动作授权」双重校验。
  • 验证方法：器件选型与认证材料核查；核实是否与 CCC/FiRa 规范版本对齐（F-12、F-13）。
  • 工程量级估计（估算）：器件与车端集成，因人月量级跨度大，此处不给数值（估算；依赖具体车型平台）。

P2-3 供应链（SBOM / SLSA）与 OTA 阈值签名

  • 现状风险：传递依赖黑箱导致漏洞爆发时无法快速回答影响范围；只做签名验证不做单调性检查会被旧包降级（章 02 §02.9 薄弱点 8、9）。
  • 建议控制：以 SBOM（SPDX [A] / CycloneDX [B]）+ 构建完整性（SLSA v1.0 [A] / in-toto [B]）治理依赖；以 Uptane 双仓库 + TUF 四角色阈值签名做 OTA 防冻结与防降级；版本下界存于不可回退位置。
  • 验证方法：采购契约核查 SBOM 交付条款；核查 OTA 校验顺序中签名验证与单调性检查同时存在（章 02 §02.8 片段 C）。
  • 工程量级估计（估算）：供应链治理与 OTA 体系，数十人月量级。

P2-4 双栈密码迁移路径（国密 × 国际栈）

  • 现状风险：面向中国市场的链路若只按国际栈设计，会在合规上出现缺口；若只按国密设计，会影响国际互操作（T6）。
  • 建议控制：规划以 RFC 8998 为交点的双栈证书与握手路径；HSM/SE 选型覆盖 SM 与国际算法；双轨信任锚与轮换管理。
  • 验证方法：核查链路的双栈握手与证书体系；核查密钥/算法清单是否覆盖 GB/T 32918/32905/32907 与 RFC 8998 对应路径。
  • 工程量级估计（估算）：双栈改造，数十至百人月量级（依赖既有 PKI 与器件能力）。

31.5 车云授权成熟度模型（L0–L5）

本节模型为「本报告提出的评估框架」（自制品，非任何标准组织发布的模型）。 它把本报告的备证事实组织为可自评的六级阶梯，供委托方向内部团队或供应商提问时使用。它不是合规判定工具，也不能替代第三方审核。

模型设计原则：

  1. 每一级的「可验证的客观证据」必须是可在文档、配置或观测中看到的东西，而非主观评价。
  2. 升级的必要行动是本报告给出的建议方向（推测性），用于指引优先级，不构成实施承诺。
  3. 评级只依据公开可观测或可经 RFI 取得的事实；无证据者写「无法评定」，绝不写「处于低级」（对齐 AC-11）。

31.5.1 六级模型定义

L0 —— 无对外车云授权面

  • 特征：无对外车云 API；仅自营 App ↔ 车云 ↔ 车端闭环。
  • 可验证的客观证据：无面向第三方/开发者的开放平台入口（域名无解析或返回占位/500）。
  • 典型控制：自营链路的传输保护与身份认证（范围在本评估之外）。
  • 升级到 L1 的必要行动：建立应用级身份与凭证（应用注册、凭证签发与吊销）。

L1 —— 应用级凭证（API Key / app-id + secret）

  • 特征：以「合作方应用」为身份对象的接口开放，无逐车主同意语义。
  • 可验证的客观证据：调用凭证为 appKey 或 app-id + secret（如 F-17 的比亚迪 i迪桥、蔚来 Open NSC 形态）。
  • 典型控制：凭证签发/审核/吊销；接口级鉴权；基础限流。
  • 升级到 L2 的必要行动：引入「代表车主行事」的授权语义（授权码流 + 同意界面 + scope）。

L2 —— 车主授权（OAuth 授权码 + 同意 + scope）

  • 特征：以「车主 + 应用」为身份对象；有同意界面与 scope 粒度；令牌有生命周期管理。
  • 可验证的客观证据：授权码流文档、openid/offline_access 必要项、scope 清单、刷新令牌轮换与一次性语义（如 F-11 Mercedes 形态）。
  • 典型控制：授权码流 + PKCE、刷新令牌轮换、同意撤销入口、错误语义规范。
  • 升级到 L3 的必要行动：叠加资源级与字段级策略（授权被授予 ≠ 资源被放行），并把校验下沉到车端。

L3 —— 资源级/字段级授权 + 车端校验

  • 特征：scope 之上有资源级/字段级判定；车端在执行前独立验签或校验；撤销贯穿末端。
  • 可验证的客观证据：字段级收窄机制（如 F-09 的 hide_private 403）、公钥托管与车端验签（如 F-08 虚拟密钥形态）、撤销联动配置回收。
  • 典型控制：四层决策流水线、令牌—车辆绑定、车端二次校验、通道一致性拦截。
  • 升级到 L4 的必要行动：引入发送方约束令牌与结构化权限表达，并把同意/审计做成可观测参数。

L4 —— 发送方约束 + 结构化授权 + 可观测合规

  • 特征：高敏接口要求发送方约束令牌；授权范围以结构化对象表达；同意、目的限制与审计日志落到可观测参数。
  • 可验证的客观证据：授权服务器声明 DPoP/证书绑定能力；authorization_details 类结构化字段；purpose 绑定与决策日志含策略依据。
  • 典型控制：RFC 8705 / 9449、RFC 9396 RAR、五要素审计日志、意图与目的的绑定。
  • 升级到 L5 的必要行动：引入可协商授权与跨主体代理链的可归属审计。

L5 —— 可协商授权 + 生态级治理

  • 特征：客户端与授权服务器可协商授权内容；跨主体代理链（令牌交换/代理）有清晰的主体/行为者归属；供给链与 OTA 阈值签名体系与授权体系协同。
  • 可验证的客观证据：GNAP 类可协商协议的使用；RFC 8693 风格 act/subject 链；TUF 阈值签名与 SBOM/SLSA 交付证据。
  • 典型控制：可协商授权、代理链归属审计、供应链完整性、OTA 防降级。
  • 升级到 L5 之上：本模型将 L5 设为最高级；其上为「生态治理」，本报告不再细分。

31.6 后续研究工作包

本节给出 8 个工作包，用于闭合 31.2 的缺口与验证 31.3 的趋势。每个工作包按四要素给出：目标 / 方法 / 产出物 / 依赖。所有工作包均不涉及主动渗透、逆向或实车攻击（对齐 00-engagement-plan.md §1 的范围外声明）；涉及实物的工作为拆解与登记，不含攻击性测试。

WP-1 RFI 问卷（Request for Information）

  • 目标：以结构化问卷向目标车企与平台供应商索取本次未公开的授权与安全信息（对应 N-01~N-03、N-10~N-12）。
  • 方法：编制含授权模型、令牌生命周期、资源级策略、日志、多租户隔离、密钥托管的问卷；设「是否可提供证据文件」列。
  • 产出物：RFI 问卷模板 + 回收登记表 + 与 19.11 缺口台账的闭合映射。
  • 依赖：委托方商务渠道；问卷合规审阅（避免索取涉密信息）。

WP-2 沙箱实测（Sandbox Verification）

  • 目标：在拿到授权后，对公开可申请的沙箱验证令牌生命周期、撤销传播、资源级/字段级拦截（对应 N-04、N-09）。
  • 方法：走一遍授权码流，读取 expires_in；测一次性刷新令牌的并发行为；测租户越界与对象级越权用例（期望被拒）。
  • 产出物：参数实测记录表 + 与 F-06/F-07/F-11 的对标结论 + 缺失参数的补证状态。
  • 依赖：沙箱账号（商务渠道）；测试范围书面确认；不触碰非授权对象。

WP-3 专利与招标检索

  • 目标：从专利与招投标文件侧补充车云授权与密码实现的可核验线索（对应 N-01、N-02）。
  • 方法：检索目标主体的相关专利与招投标公告，提取「器件选型、算法、架构」类公开信息。
  • 产出物：专利/招标线索清单 + 证据等级标注 + 与缺失方向的关联。
  • 依赖：专利与招投标数据库访问。

WP-4 T-BOX 拆解（器件与安全元件登记）

  • 目标：通过对公开可得或委托方自有车辆的 T-BOX 拆解，登记器件选型与是否存在安全元件（对应 N-02）。
  • 方法：非攻击性拆解与器件登记；记录芯片型号、是否有 SE/eSE/HSM 迹象、UWB 芯片有无。
  • 产出物：器件登记表 + 与 EVITA 分级/CCC 通道模型的对照。
  • 依赖：合法持有的拆解对象；不含攻击性测试。

WP-5 白皮书采购

  • 目标：采购目标主体的安全白皮书或公开技术资料，补足授权与分层方案（对应 N-01~N-03、G-09）。
  • 方法：通过商务/采购渠道采购或申请；提取授权与分层控制条目。
  • 产出物：白皮书条目提取表 + 与通用方案（章 02）的对标。
  • 依赖：采购预算与渠道。

WP-6 标准正文获取

  • 目标：获取本次未取证的标准正文（ISO/SAE 21434、ISO 24089、ISO 15118、UN R155/R156、GDPR、EU Data Act）。
  • 方法：通过标准购买渠道、会员渠道或官方 PDF 直链获取（对应 G-10~G-13、G-18~G-24、G-36、G-37）。
  • 产出物：正文可引用条目表（含条款号，仅在取得正文后方可给出）。
  • 依赖：标准购买预算；会员资格；网络出口。

WP-7 双栈密码实验

  • 目标：验证国密与国际栈在车云链路上的双栈互操作路径（支撑 T6 与 P2-4）。
  • 方法：搭建实验环境，验证 RFC 8998 对应的 SM 套件与常规 TLS 1.3 套件的共存与协商（实验环境，非生产）。
  • 产出物：双栈握手实验报告 + 迁移路径建议 + 器件支持清单。
  • 依赖：支持国密的器件/软件栈；实验环境。

WP-8 威胁建模工作坊

  • 目标：把章 14 的威胁模型落到委托方自身架构，形成可跟踪的缓解项（支撑 P0/P1）。
  • 方法：以 STRIDE 与 API 安全 Top 10 为骨架，结合委托方的信任边界与主体清单做工作坊（章 14 §14.1、§14.2）。
  • 产出物：威胁-控制映射表（接续章 14 §14.5）+ 缓解项 backlog + 责任人。
  • 依赖：委托方架构与安全团队参与；不含任何攻击性活动。

31.8 本章小结

本章用三句话浓缩全报告。

第一句——已经能确定什么： 规范层已就绪（OAuth 2.1 强制 PKCE、RFC 8705/9449 发送方约束、RFC 9396/9635 结构化与可协商授权、RFC 9019/9124 SUIT、Uptane 2.1.0），国际一线可读实现提供了完整标尺（Tesla Fleet API 的 12 scope、一次性刷新令牌、车端虚拟密钥、hide_private 字段级 403；Mercedes 的授权码流、purpose 同意与 mb: 三段式 scope），数字钥匙三通道与 SE 存储由 CCC 3.0 定义，中国已建成以 GB 44495/44496（2026-01-01 强制）为基线、并延伸至平台侧与接口侧（GB/T 47324/47467-2026）的国标体系。

第二句——还不能确定什么： 国内 9 家车企在 mTLS/国密、TEE/SE/HSM、资源级授权、T-BOX 安全等方向均无公开一手来源（本次披露缺口，非能力缺口）；小鹏、华为、BMW、Rivian 及 R155/R156 正文因 403 / JS 空壳 / 区域封锁 / Cloudflare 而未能取证；Tesla 访问令牌 TTL 因未走实测而未确认。这些缺口已逐条登记于 19.11（46 条）本章 31.2（12 条），并给出补证方式。

第三句——建议优先做什么： 无论当前处于什么水平，都应先把地基做扎实——逐车主同意与资源级策略、发送方约束令牌、短 TTL + 一次性刷新 + 轮换、撤销贯穿车端、审计日志含授权决策依据（P0 五项）；再补结构化授权（RAR）、步进认证、密钥分层与限流配额（P1）；最后预置 GNAP、UWB+SE、供应链与双栈迁移（P2）。一句话：车云安全的短板集中在授权，而不在密码——把授权从「链路可信」推进到「资源级与字段级可信」，是投入产出比最高的方向（本报告判断，推测，非事实）。
