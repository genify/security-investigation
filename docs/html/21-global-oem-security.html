01

21.0 本章方法与取证限制

21.0.1 为什么本章必须先把「局限」说在最前面

17 章（授权与访问控制）之所以能写得很厚，是因为 Tesla 与 Mercedes-Benz 两家把授权协议、令牌模型、scope 清单、同意流程完整地发布在了公开开发者文档里，构成了一批可逐条复现的 [A] 级证据。授权切面是「天生文档化」的——第三方开发者要接入，平台就必须把鉴权方式讲清楚，否则没有人能写代码。于是授权切面拥有一个商业上被迫公开的信息出口。

本章要写的四个切面（硬件安全 / 通信安全 / 应用与平台安全 / OTA 与合规）没有这个信息出口。原因并不神秘，也不带任何价值判断：

  • 硬件安全（TEE／SE／HSM／安全启动／密钥存储）是供应链上游事实，属于器件选型与内部架构，车企通常只在 TARA（威胁分析与风险评估）报告、型式认证申报材料、内部安全白皮书中涉及，而这些材料绝大多数不公开发布。第三方开发者接不接入 API，与「这辆车用的是哪一款 MCU、有没有独立 HSM」毫无关系，所以平台没有公开它的商业动机。
  • 通信安全的车端部分（车机与 T-BOX 的证书、密钥注入、SecOC 报文认证）同理属于车端内部实现；只有服务端接入侧（例如开发者必须如何校验服务器证书）会因为要指导第三方接入而被迫公开——这就是 Tesla Fleet Telemetry 服务端 TLS 指引成为本次唯一取到的通信安全一手事实的原因。
  • 应用与平台安全的公开面通常只到「开发者侧不能做什么」（如客户端凭证不得下发）这一层，往下（座舱沙箱、进程隔离、云端多租户隔离、入侵检测）几乎不公开。
  • OTA、数据隐私、合规、供应链之间差异很大：合规与隐私会有声明性公开（如 GDPR 表态、ISO 27001 认证编号），但 OTA 的签名算法、阈值策略、回滚策略属于安全敏感细节，供应链的 SBOM 属于近年才被监管逐步强制披露的内容，本次基本未取到。

一句话概括本章的处境：本章研究的四个切面，其公开证据密度显著低于授权切面；越是接近车端与密钥的地方，公开信息越稀疏。 这是本章所有结论都必须套用的「可信度滤镜」。

21.0.2 「未取证 ≠ 无能力」——本章的中立性红线（AC-11）

信源档案 §0 对本次调研有一段强制写作纪律，本章逐字遵守：

「未找到公开来源」= 本次披露缺口，绝不等于能力缺口，不得反向推断为「该企业没有该能力」。 —— 来源：信源档案 §0 —— docs/sources/source-dossier.md —— [A，本项目内部采证记录]。

这条纪律在本章比在 17 章更重要。因为 17 章的缺口主要是「文档没细讲授权流程」，而本章的缺口是「车企没公开硬件与车端密码实现」——后者极易被读者误读为「所以它们可能没做」。本报告明确：车企不公开某硬件安全机制，与它是否部署该机制，是两个独立命题。 一个负责任的调研报告只能描述信息公开结构，不能从信息公开结构的稀疏反推技术实现的缺失。本章凡出现「未取到」「未找到公开来源」字样处，一律指公开披露缺口，不带任何能力评判。

同时（对齐审计计划 §3.2.4 与 AC-11）：本章不得对任何车企使用贬损措辞，不得做「A 比 B 差」的比较级结论。对文档公开度较低的企业（如本次的 BMW、Rivian），本报告的表述一律是「本次未取到其公开文档」，而不是「其缺乏文档」或「其不重视安全」。

21.0.3 通用机制的三档标注法（本章的核心写作工具）

本章会大量出现「行业通行」的机制，例如「车规 MCU 通常集成 HSM」「TLS 1.3 是当前通信安全基线」「OTA 普遍采用签名验证」。这些机制在行业里确实通行，但本次并没有取到任何一家国际车企承认自己采用它的官方一手来源。若把它们写成「Tesla 使用 HSM」，就是编造；若完全不写，读者又无法理解车企实践在行业坐标中的位置。

因此本章发明并使用一套三档标注法，把「行业认知」与「车企事实」在物理上分开：

标注含义允许的写法
【车企一手 [A]】能在信源档案中找到对应条目、且归因到具体车企「Tesla 文档明载……」（附 URL）
【行业通行认知，无本车企一手来源（推测）】行业层面普遍如此，但本次未取到任何车企承认「行业通行做法是……；本报告不将其归因于任何具体车企」
【本报告判断（推测，非事实）】由已取证的架构/规范推导出的解释「本报告判断……（推测）」

硬性纪律：【行业通行认知】档的每一句话禁止出现具体车企名称作为主语。例如可以写「行业通行做法是通信层采用 TLS 1.3 及其以上版本」，不得写成「Tesla 采用 TLS 1.3」——即便 Tesla 文档确实提到 TLS，那也只能在其确有 [A] 出处（如 Fleet Telemetry 的证书校验指引）的范围内，以「文档明载」措辞描述该指引本身，而不得外推为「Tesla 端到端采用 TLS 1.3」。

21.0.4 本章使用的规范底座（用于解释「为什么会这样设计」，不作为车企事实）

21.1.1 已取证事实汇总（按切面归类，每条标 [A]）

Tesla 是本次唯一在「非授权切面」上留有若干 [A] 级事实的国际车企。以下逐条列出，并注明它属于四大切面中的哪一个。全部来源：https://developer.tesla.com/docs/fleet-api/...，证据等级 [A]；条目在信源档案中的位置标注于句末。

【通信安全切面】

  1. 服务端 TLS 证书校验指引：Tesla Fleet Telemetry 文档要求开发者在自建接收服务器上，使用其开源仓库内提供的脚本 tools/check_server_cert.sh 校验主机与 CA 的兼容性 —— 来源：Fleet Telemetry 文档 —— https://developer.tesla.com/docs/fleet-api/fleet-telemetry —— [A]（信源档案 §7.1）。这是本次全报告唯一取到的、由国际车企明确发布、指向「通信链路服务端证书」的一手工程指引。它证明 Tesla 在与第三方的车→云直连链路上，把「服务端证书的正确性」作为开发者必须自证的接入前提。
  2. 认证端点与 API 端点分属不同主机：令牌端点位于 POST https://fleet-auth.prd.vn.cloud.tesla.com/oauth2/v3/token，而 Fleet API 基础地址为 https://fleet-api.prd.na.vn.cloud.tesla.com（audience 必须是 Fleet API base URL）—— 来源：第三方令牌文档 —— https://developer.tesla.com/docs/fleet-api/authentication/third-party-tokens —— [A]。从通信切面看，这构成两个不同的信任域与网络路径：认证域（fleet-auth.）与业务域（fleet-api.）分离，文档并说明 /token 调用「来自应用服务器、适用不同的限流」。
  3. 车→云直连取代轮询：Fleet Telemetry 让车辆直连开发者服务器，取代轮询 vehicle_data 端点 —— 来源：Fleet Telemetry 文档 —— 同上 —— [A]。这在通信模型上意味着：数据流方向由「云↔云（开发者拉取）」（原文描述为取代轮询）改变为「车↔第三方服务器（推送）」，链路拓扑因此多出一条车辆直连第三方的通道。
  4. 服务端证书校验是接入前置条件之一：配合第 1 条，文档把「必须已配对虚拟密钥」列为 Fleet Telemetry 的前置条件之一 —— 来源：Fleet Telemetry 文档 —— 同上 —— [A]（详见下一小节第 13 条）。

【硬件（车端可信执行）切面——仅两条，且都来自授权文档的副产品】

  1. 车辆仅支持 prime256v1 密钥：虚拟密钥生成命令为 openssl ecparam -name prime256v1 -genkey -noout，文档明确「车辆仅支持 prime256v1 密钥」（即 P-256 ECDSA）—— 来源：虚拟密钥开发者指南 —— https://developer.tesla.com/docs/fleet-api/virtual-keys/developer-guide —— [A]（信源档案 §7.1）。这是本次唯一一条国际车企公开的、涉及车端密码学参数的 [A] 级事实：它说明车端在验证第三方虚拟密钥签名时，限定了椭圆曲线族群为 P-256。注意边界：它只证明「虚拟密钥这一条链路的签名算法族群是 P-256」，不能外推为「Tesla 全车密码栈都用 P-256」，更不能外推「车端有／没有 HSM」。
  2. 车辆在执行命令前验证载荷签名：文档明载，车辆在处理命令前或接受 Fleet Telemetry 配置前，会验证载荷签名 —— 来源：虚拟密钥开发者指南 —— 同上 —— [A]。从硬件/可信执行切面看，这条事实的意义是：签名验证发生在车端（而非仅云端），因此车端必须持有可信公钥材料并具备验签能力。但文档未说明验签在哪个执行环境完成（是否为 TEE/SE/独立安全核），本章不得填补这一空白。

【应用与平台安全切面】

  1. 限流分层次（按账号按设备）：实时数据 60 次/分；唤醒 3 次/分；设备命令 30 次/分；同账号多应用共享限额 —— 来源：计费与限额文档 —— https://developer.tesla.com/docs/fleet-api/billing-and-limits —— [A]（信源档案 §7.1）。从平台安全看，这构成服务端资源保护与滥用遏制机制：不同语义的操作拥有不同配额（唤醒最严、命令次之、读取最宽），且配额在账号级归集（同一账号下的多个应用互相挤占）。
  2. 计费与配额行为（多租户经济约束）：计费按用量、月度周期（每月 1 日起算）；每账号计费上限默认 0；达 80% 与 100% 时发邮件；超限会暂停 API 使用并移除 Fleet Telemetry 推流配置（且不恢复）；响应码 <500 全部计费、≥500 不计费；费用四舍五入到 $0.01；个人开发者/小应用每月 $10 折扣 —— 来源：同一计费与限额页 —— 同上 —— [A]。从平台安全与治理看，这些行为包含三层含义：①「默认上限 0」意味着新账号默认不可产生费用（需显式调高，构成一层准入约束）；②「超限即移除推流配置且不恢复」说明经济违规的后果是服务面收缩（而非仅提示）；③「≥500 不计费」使服务端错误不向开发者计费，客观上避免了对故障流量征税。
  3. 漏洞披露与赏金（Bugcrowd）：Tesla 在 Bugcrowd 运营漏洞赏金项目，启动于 2015-08-04，状态 in progress —— 来源：Bugcrowd 项目页 —— https://bugcrowd.com/engagements/tesla —— [A/B]（信源档案 §7.1）。报递流程：车辆/能源产品问题须邮件报至 vulnerabilityreporting@tesla.com 并使用 Tesla GPG 公钥，不走 Bugcrowd 网页表单；硬件研究须先向 Tesla 登记车辆/Powerwall —— 来源：同上 —— [A/B]。规则要点：若访问到不属于自己的数据须在 24 小时内停止并披露；未经 Tesla 批准不得公开披露已确认未修复漏洞；超级充电及相关基础设施不在范围内；涉及第三方库的漏洞可能被转给厂商而不通知研究者 —— 来源：同上 —— [B]。赏金档位：Critical $50,000–$100,000；High $20,000–$50,000；Moderate $10,000–$20,000；Low $500–$10,000 —— 来源：同上 —— [B]。
  4. 开源客户端与命令代理仓库：Fleet Telemetry 客户端源码 https://github.com/teslamotors/fleet-telemetry，命令代理 https://github.com/teslamotors/vehicle-command —— 来源：Fleet Telemetry 文档 —— 同上 —— [A]（信源档案 §7.1）。从平台安全看，Tesla 把接收端（服务端 SDK）与命令代理的实现源码公开，使开发者侧集成行为可被任何人审计。
  5. 车辆最多同时向 5 个第三方应用推流：单台车辆上限 5 个 —— 来源：Fleet Telemetry 文档 —— 同上 —— [A]。这是一条影响范围控制事实：即便多个第三方都完成配对，单车的推流订阅者数量也被收敛到一个可枚举的上限。
  6. 断连缓冲与重连退避：车辆断连时缓冲 5000 条消息（≥2500 秒数据）；重连采用指数退避，最大重试延迟 30 秒 —— 来源：Fleet Telemetry 文档 —— 同上 —— [A]。从平台可用性看，这是车端对链路中断的本地耐久性设计；从安全看，缓冲意味着「短时断连不上报的数据不会丢失」，但 5000 条上限也界定了断连期间的暴露窗口（超过即丢弃，不会被无限缓存）。

21.1.3 基于已取证事实的合理推断（每条标推测 + 检验方法）

以下全部为 【本报告判断（推测，非事实）】。每条都给出「可检验的方法」，以便后续证伪——这是本报告区分推测与事实的工程化做法。

推断 T-I1：开源 Fleet Telemetry 客户端的存在，使「开发者侧集成行为」成为可审计对象。 依据（[A]）：客户端源码与命令代理均在公开仓库 —— 来源：https://github.com/teslamotors/fleet-telemetry、https://github.com/teslamotors/vehicle-command —— [A]。 推断：当接收端逻辑开源时，生态内的实现质量与安全默认值（如是否严格校验证书、是否记录敏感字段）会被外部审计，从而对开发者形成默认安全的软约束。 检验方法：抽样若干使用该 SDK 的第三方集成，比对它们是否启用了仓库提供的证书校验路径（tools/check_server_cert.sh）；或对 SDK 默认配置做静态审查。

推断 T-I2：认证域与业务域分离，意味着两套独立的限流与信任域。 依据（[A]）：/token 位于 fleet-auth.prd.vn.cloud.tesla.com，业务 API 位于 fleet-api.*，且文档称 /token「来自应用服务器、适用不同的限流」—— 来源：第三方令牌文档 —— [A]。 推断：两个域在网络路径、缓存策略、限流策略、可观测性上可以独立演进；攻击面在认证域被收敛为「换码」这一窄接口。 检验方法：对两个域分别做限流边界实测（在授权范围内、使用自有账号）；对比两域的响应头与错误语义差异。

推断 T-I3：「计费上限默认 0」是一种默认关闭式的准入控制。 依据（[A]）：每账号计费上限默认 0；超限会暂停 API 并移除推流（不恢复）—— 来源：计费与限额文档 —— [A]。 推断：新账号在未显式设定额度前无法产生规模化调用，这在效果上等价于默认拒绝（default-deny）的准入行为，可降低「账号意外泄露后被大规模滥用」的经济动机。 检验方法：以新开发者账号发起调用，观察在未设上限时的行为（是否被硬性阻断）与提示文案。

推断 T-I4：「超限移除推流且不恢复」是服务面收缩而非仅告警的控制。 依据（[A]）：同上。 推断：与仅发邮件告警相比，移除推流配置意味着数据面被实际切断，属于执行型控制而非提示型控制。 检验方法：观察计费超限后推流的消失时延与是否自动恢复（文档称不恢复）。

推断 T-I5：「≥500 不计费」使服务端错误不被计费，避免对故障流量征税。 依据（[A]）：响应码 <500 全部计费，≥500 不计费 —— 来源：计费与限额文档 —— [A]。 推断：该策略在激励层面促使平台把「可计费的成功响应」与「不可计费的服务端错误」严格区分，间接鼓励平台降低 5xx。 检验方法：构造合法的、返回 5xx 的请求时机（如瞬时故障窗口）并核对账单。

推断 T-I6：「单车最多 5 个第三方应用」是影响范围的上界。 依据（[A]）：单台车辆最多同时向 5 个第三方应用推流 —— 来源：Fleet Telemetry 文档 —— [A]。 推断：即便凭证被多次滥用，单车可被外部订阅的通道数有硬上界，使「单车被多个第三方同时观测」的规模被收敛。 检验方法：以自有多应用尝试向同一车辆订阅第 6 个推流，观察拒绝行为。

推断 T-I7：prime256v1 的限定说明车端验签的曲线族群被收窄。 依据（[A]）：车辆仅支持 prime256v1 —— 来源：虚拟密钥开发者指南 —— [A]。 推断：限定单一曲线族群降低了车端验签实现的复杂度（无需支持多曲线），若车端验签运行在受限环境（本报告不假设其是否如此），单一曲线的实现面更小。 检验方法：用非 P-256 曲线生成密钥并尝试配对，观察是否被车端拒绝。

推断 T-I8：固件版本门槛（2024.26+ 等）暗示车端能力是「随固件渐进引入」的。 依据（[A]）：Fleet Telemetry 需车辆固件 2024.26+；证书签名类应用需 2023.20.6+；Model S/X（Intel Atom）需 2025.20+ —— 来源：Fleet Telemetry 文档 —— [A]。 推断：车云安全能力的引入以固件版本为闸门——同一家车企在路上的车可能处于不同能力状态，这要求云端对「车辆能力」做异构兼容。 检验方法：以不同固件版本车辆分别配对，观察能力矩阵差异。

21.7 国际车企在「四大切面」上的公开信息结构特征分析

本节仅基于已取证事实（§21.1–§21.6）归纳，观察对象是「信息公开结构」而非「技术能力」。凡由观察推出的解释性判断，一律标 【本报告判断（推测）】，并给出对国内车企（对照 16-authz-60-cn-oem.md / 20-cn-oem-security.md）的启示。观察条数 ≥ 5。

观察 1：开发者门户只对「授权与数据交付」做文档化，硬件与车端实现几乎不公开。

事实依据：五张汇总表中，[A] 事实集中在授权/平台/数据字段层面；硬件列五家全空。Tesla 的 tools/check_server_cert.sh、Mercedes 的「凭证不得下发」都属于为第三方接入服务的文档，而非为安全评审服务的文档 —— 来源：信源档案 §7.1、§7.2 —— [A]。 【本报告判断（推测）】：开发者门户的商业目的是「让第三方能接进来」，因此文档边界由接入所需决定，安全评审所需的车端架构材料天然不进入该边界。 对国内车企的启示：国内车企若要在公开层面证明车云安全能力，不能指望开发者门户；需要单独的安全/信任中心（如小米信任中心的形态——见信源档案 §7.8，其载 ISO/IEC 27001 认证编号 IS 831552，[A]）承载硬件与合规材料。

观察 2：「服务端证书校验」是通信切面唯一被公开的内容，说明车端通信在文档上被抽象掉了。

事实依据：Tesla 是本次唯一公开通信安全工程指引的企业，而该指引面向开发者接收端（服务端校验自己的证书），不涉及车端 —— 来源：信源档案 §7.1 —— [A]。 【本报告判断（推测）】：平台在文档中把「车辆」抽象为一个黑盒端点——开发者只需处理「连上平台/接收推流」，无须理解车端通信。 对国内车企的启示：公开「开发者侧证书校验指引」是低成本、高可信度的安全信号（一条脚本即可展示对证书正确性的重视），国内车企可优先公开此类接入侧指引以提升外部可评审性。

观察 3：平台治理通过「经济约束」实现，而非仅靠技术控制。

事实依据：Tesla 的计费默认上限 0、超限暂停并移除推流（不恢复）、≥500 不计费、个人每月 $10 折扣 —— 来源：信源档案 §7.1 —— [A]。 【本报告判断（推测）】：配额与计费是「影响范围控制」的经济实现——它把滥用成本即时传导给调用者，比纯技术限流更具行为约束力。 对国内车企的启示：可借鉴「默认额度为 0 + 超限即收缩服务面」的默认保守设计，把「未显式授权的大规模调用」变成默认不可发生。

观察 4：隐私合规以「字段级 + UI 级」形态公开，架构级（存储/出境）不公开。

事实依据：Tesla 的字段级 403 语义、Mercedes 的 scope + purpose URL 同意界面 —— 来源：信源档案 §7.1、§7.2 —— [A]；两部欧盟法规正文本次未取到（HTTP 202）—— 来源：信源档案 §1.4 —— [C]。 【本报告判断（推测）】：合规声明服务的是监管者与用户，因此以可见界面与字段行为为落点；数据存储架构属基础设施信息，公开收益低、风险高。 对国内车企的启示：面向《汽车数据安全管理若干规定（试行）》（网信办等五部门令第 7 号，2021-10-01 施行，[A]，信源档案 §1.3）的合规举证，同样应把「字段级控制 + 用户可见的同意/撤销界面」作为可外部核验的证据来建设，而非仅停在内控文档。

观察 5：漏洞披露是最稳定、最可外部核验的平台安全信号。

事实依据：Tesla 的 Bugcrowd 项目含启动日期（2015-08-04）、分档赏金、报递渠道（邮件 + GPG，不走网页表单）、规则（24h 停、未修复不公开、超充不在范围、第三方库可能转厂商、硬件须登记） —— 来源：信源档案 §7.1 —— [A/B]。国内侧仅奇瑞设有「网络产品安全漏洞」专栏（信源档案 §7.9，[A]）。 【本报告判断（推测）】：漏洞披露计划的存在性可被第三方核验（有无专门项目、有无明确规则、有无分级），是比营销白皮书更难虚假的信号。 对国内车企的启示：建立公开、可核验的 SRC/漏洞披露计划（含明确范围、时限、分级），是提升外部安全信任度的高性价比动作——它不需要公开任何车端机密。

观察 6：多品牌集团化会提升「统一基线」收益，但扩大单点失效的横向影响面。

事实依据：CARIAD 自述「1 ecosystem for all VW brands」「45 million connected vehicles」「90 markets connected」（[A，公司自述口径]）；其自我定位为服务 Audi / Volkswagen / Porsche 的集团软件公司 —— 来源：信源档案 §7.3 —— [A，自述]。 【本报告判断（推测）】：统一平台带来一致的鉴权与配置模型（降低对接成本），但若一个平台承载多品牌，一处缺陷的横向影响面随之放大。 对国内车企的启示：集团化/平台化时，应把「品牌级/租户级隔离」与「统一基线」分离设计——统一标准而不统一信任域，避免单点缺陷跨越品牌边界。

观察 7：本次证据密度差异，主要由「文档可达性」与「网络可达性」决定，而非企业安全能力。

事实依据：信源档案 §0 强制纪律——「未找到公开来源」= 披露缺口，绝不等于能力缺口；覆盖度偏置向「文档公开可达」的企业倾斜（Tesla / Mercedes 最厚）—— 来源：信源档案 §0 —— [A]。BMW / Rivian 的空源于区域封锁 —— 来源：信源档案 §7.4、§7.5 —— [A，直接观测]。 【本报告判断（推测）】：任何基于公开信息的车企横向排名，其排序主要由可达性决定，因此不具能力评估意义。 对国内车企的启示：若确有安全能力但文档不可达，会在外部评估中被系统性低估；主动、结构化地公开可核验的安全信号（披露计划、接入侧指引、合规认证）是对冲该偏差的手段。

观察 8：OTA/供应链的公开内容停留在「能力陈述」，不停留在「机制细节」。

事实依据：CARIAD 仅有一句「云支持安全关键更新的 OTA 下发」（[A，自述]）；Tesla 公开的是版本谱系与配置签名（[A]），而签名算法与阈值策略未找到公开来源；SBOM/构建完整性五家全空 —— 来源：信源档案 §7.1、§7.3 —— [A]。 【本报告判断（推测）】：OTA 签名与阈值属于安全敏感细节（公开可能降低攻击成本），供应链 SBOM 则是近年才被逐步强制的披露项，故整体仍以「能力陈述」形态存在。 对国内车企的启示：对 GB 44496-2024《汽车软件升级通用技术要求》（2026-01-01 实施，[A]，信源档案 §1.1）与 GB/T 47325-2026《车联网在线升级安全技术要求与测试方法》（[A]，信源档案 §1.2）的合规举证，可参考国际同行「公开版本谱系 + 保持签名细节私密」的分层策略：公开到可核验，私密到不降低攻击成本。

21.9 本章小结

本章围绕国际五家新能源车企（Tesla、Mercedes-Benz、Volkswagen Group/CARIAD、BMW、Rivian）的硬件安全、通信安全、应用与平台安全、OTA·隐私·合规·供应链四个切面（外加数字钥匙专题）展开，与只写授权切面的 17-authz-70-global-oem.md 明确分工、互不重复。本章可得出的、可溯源的核心结论如下：

  1. 四个切面的公开证据密度显著低于授权切面。 授权切面因「第三方接入必需」而被迫文档化，四个切面没有这一信息出口；越是接近车端与密钥，公开信息越稀疏。本章因此把「局限」说在最前面（§21.0），并以 20 格证据矩阵给出全局地图。
  2. 本次取到的非授权切面 [A] 事实，几乎全部集中在「开发者可见」的两处：通信接入侧（Tesla 的 tools/check_server_cert.sh 服务端证书校验指引）与平台治理侧（Tesla 的限流分层/计费配额/Bugcrowd 报递流程/开源客户端仓库/单车 5 推流/断连缓冲；Mercedes 的「客户端凭证不得下发」/五类产品/HTTP Basic/错误语义）。没有一条 [A] 事实落在车端硬件或车端密码实现上。
  3. 硬件安全是本次唯一的「五家全空」切面。 Tesla 仅遗留两条极薄事实（车端执行前验签、车辆仅支持 prime256v1），且不可外推为完整硬件栈；Mercedes、CARIAD、BMW、Rivian 在硬件切面上均为「未找到公开来源」或「未取到（披露缺口）」。
  4. BMW 与 Rivian 的「空」是可达性缺口，不是能力缺口。 BMW 的 developer.bmwgroup.com 为占位页（"no content deployed"，Last-Modified 2026-04-27）、集团主域区域封锁、b2b.bmw.com 为供应商门户；Rivian 的 rivian.com 返回 CloudFront 国家级 403、developer.rivian.com 无 DNS、api.rivian.com 为 App 后端。本章对两家独立成节（§21.4 / §21.5），逐项列「未取到什么 + 为什么 + 怎么补」，并明确不得反向推断（AC-11）。
  5. 隐私合规呈「字段级 + UI 级」形态。 Tesla 以字段级 403 语义与按字段节流体现数据最小化；Mercedes 以同意界面 + purpose URL 体现目的限定与 GDPR 表态。两家的架构级数据事实（存储位置、出境策略）本次未取到。两部欧盟法规正文本次亦未取到（HTTP 202），故本章不引用任何条款编号。
  6. 平台安全可通过「经济约束」与「披露计划」两个外部可核验信号被观察。 Tesla 的「默认额度 0 + 超限收缩服务面」是默认保守的控制设计；其 Bugcrowd 计划（含启动日期、分档赏金、报递渠道与规则）是比营销白皮书更难以虚假的安全信号。这两类信号不要求公开任何车端机密，是可优先建设的对内对外证明手段（对国内车企的启示见 §21.7）。
  7. 本章的全部结论边界由 §21.0.2 的中立性纪律与 §21.0.3 的三档标注法界定：凡「行业通行认知」一律不与任何具体车企绑定；凡「未取到」一律指披露缺口；凡「本报告判断」一律显式标为推测并附检验方法。本章未引入任何信源档案之外的新 URL、数字或条款号，全部事实可回溯至 docs/sources/source-dossier.md。
  8. 数字钥匙切面：本次唯一可取的一手规范类证据是 CCC（Car Connectivity Consortium）与 FiRa Consortium 的公开规范发布公告，以及中国国标 GB/T 44402.1-2024 数字钥匙参考架构——五家国际车企均未取到其数字钥匙的实现细节（BMW、Rivian 在披露缺口之列；Mercedes 的 CCC 相关文档在 §7.2 明列未取到）。数字钥匙的规范级综述见附录 A。
