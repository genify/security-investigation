12.1 令牌谱系总览

12.1.1 为什么先做"谱系"而不是先做"协议"

授权与访问控制在工程上最终收敛为一件事：一个字符串（或一个签名结构）被随请求携带，由资源服务器判定"这个请求代表谁、可以做什么"。这个字符串就是令牌。车云场景的特殊性在于，这个字符串的持有方链条异常长——车主手机 → 第三方应用 → 车企云 → 车端网关 → 车辆内 ECU——且链条上每一跳的可信度不同。因此本章不从协议流（10/11 号文件已覆盖）入手，而从令牌类型本身的属性入手：一种令牌能活多久、会不会被复制、被绑定到谁、失效后代码会发生什么。

结论一：车云场景的令牌必须从"第 2 行"向"第 7/8/16 行"迁移。 表中第 2 行（Bearer 访问令牌）的"可复制性"标注为"默认可复制"，这是 RFC 6750 语义的固有属性：Bearer 令牌的持有即证明。信源档案 §2 将 RFC 8705 标注为"车云链路最关键的授权规范"，其理由正在于此——车云链路的承载介质（手机 App、车机车机、TSP 服务器）比传统 Web 浏览器更难保证"令牌不离域"。这是一个规范层面的结构性判断，不是对任何单一企业的评价。

结论二：车控命令的最后一道闸门在车端，不在云端。 表第 16 行来自 Tesla 的文档明载：车辆在执行命令前或接受 Fleet Telemetry 配置前验证载荷签名 [A]（信源档案 §7.1）。这意味着即使云端令牌完全泄露，攻击者仍缺少应用私钥，无法构造通过车端验签的载荷。档案同处引述 Tesla 文档称虚拟密钥"甚至能阻止 Tesla 自己的后端访问这些能力" [A]——这是一个去中心化的信任锚点，其意义在 12.3.4 展开。

结论三：静态密钥（第 17/18 行）与令牌体系不是同一代际的设计。 比亚迪 i迪桥文档明载鉴权为 x-Gateway-APIKey（应用 appKey）置于请求头 [A]；蔚来 Open NSC 文档明载 app-id 和 secret 是系统对接调用的唯一凭证 [A]。但必须严格区分：信源档案 §7.10 第 3 条明确警告，i迪桥是企业级 ESB 网关（覆盖供应链/研发/智造/营销/物流/品质/财务七大领域），与"车控开放平台 / 车主 API"不是同一事物，报告必须区分，避免误导向"比亚迪车云授权 = APIKey"的过度归纳。同理，§7.10 第 4 条指出蔚来 Open NSC 文档停留在 2019-08-13、站点自述"正在建设中"，不能代表蔚来当前车云安全架构。

12.2 令牌生命周期治理

12.2.1 令牌 TTL 设计与"过期"的真实语义

12.2.1.1 一个必须先讲清的概念区分

工程上常说"令牌过期了"，但这句话在 OAuth 语义里至少含三个不同的失效原因，它们的处置动作完全不同：

  • 时间到期（exp）：令牌的绝对过期时刻到达。处置：用刷新令牌换新，不打扰用户。
  • 被替代（superseded / squeezed out）：刷新令牌轮换后，旧刷新令牌被新令牌挤出。处置：若应用正确持久化了新令牌则无感；否则触发重新登录。
  • 授权变更（consent revoked / password reset）：用户侧动作导致授权基础消失。处置：无法通过刷新恢复，必须重新走授权码流程。

信源档案 §7.1 有这一区分的直接一手证据：Tesla 文档明载，刷新失败返回 401 login_required 有两种触发场景——"刷新令牌过期/被更新令牌挤出"或"用户已重置密码" [A]。这两个场景被文档明确并列为同一错误码的两个触发条件，说明厂商自身也在客户端侧把它们收敛为同一处置动作（重新登录），但在服务端审计上它们代表完全不同的因果链。

12.2.1.3 "过期"在车云链路上的多层语义

本报告判断（推测，非事实）：车云链路的"令牌过期"会同时发生在多个独立层，各层的过期时间尺度相差数个数量级，且没有统一的协调机制。层与层的对应关系如下：

层级令牌/凭证时间尺度（依据）

应用业务层OAuth 刷新令牌月级（Tesla 3 个月 [A]）

12.2.2 刷新令牌轮换（rotation）

12.2.2.1 轮换机制的形式化

刷新令牌轮换的基本断言是：每次使用刷新令牌换取新访问令牌时，刷新令牌自身也被替换。信源档案中有两处 [A] 直接支持：

  • Mercedes：grant_type=refresh_token，刷新令牌一次性使用，授权服务器返回新的访问令牌与新的刷新令牌 [A]。
  • Tesla：刷新令牌一次性使用（single use only），且最近一次使用的刷新令牌在 24 小时内仍有效 [A]。

这两条合起来给出轮换的完整状态机。本报告判断（推测，非事实）：按规范语义推导，服务端需要维护的刷新令牌状态至少包含四个：当前有效、刚被轮换（宽限窗口中）、已过期、已吊销。客户端侧对应需要维护的持久化状态是"我手里这把是不是最新的"。

12.2.2.2 并发竞态：轮换的真正难点

轮换的工程难点不在轮换本身，而在并发。考虑一个典型的车云第三方应用：它是多副本部署的（负载均衡后 3 个实例），令牌存储在一个共享数据库里。

故障序列（本报告判断，推测，非事实——基于轮换机制语义推导）：

  1. 实例 A 与实例 B 同时收到请求，两者读到的刷新令牌都是 RT_n。
  2. 实例 A 先发出刷新请求，服务端把 RT_n 标记为"刚被轮换"，签发 AT_{n+1} + RT_{n+1}，并在 24 小时宽限窗口内保留 RT_n 可用（Tesla 模型 [A]）。
  3. 实例 A 写入 RT_{n+1}。
  4. 实例 B 稍后发出刷新请求，携带的仍是 RT_n。在 Tesla 模型下，因为落在 24 小时宽窗内，服务端接受，并再签发一对新令牌——但这可能是 AT_{n+2} + RT_{n+2}。
  5. 若实例 B 写入的 RT_{n+2} 晚于实例 A 的写入，则 RT_{n+1} 被覆盖且从未被使用；反之 RT_{n+2} 被覆盖。两者都不会立刻报错，但下一次刷新使用的令牌可能已在服务端被挤出，触发 401 login_required [A]。

这就是"宽限期"在工程上的双刃性：它覆盖了"应用未能持久化轮换后令牌"的失败场景（信源档案 §7.1 明确记录了宽限期的这一用途 [A]），但它同时把单次错误变成可容忍的重复，从而给了并发场景一个"看起来能跑、偶发掉线"的窗口。

12.2.2.3 宽限期设计的两个参数

宽限期这个机制出厂只有两个可调参数：窗口长度与窗口内是否允许重复签发。

策略行为代价
窗口内可重复签发并发刷新都能成功出现"多把有效刷新令牌"，轮换的检测价值下降
窗口内返回同一对令牌（幂等）并发刷新结果一致需要服务端按 RT_n 做幂等映射，状态存储增大
无宽限期（严格一次性）轮换的强检测（重放即拒）任何客户端持久化失败 = 强制用户重新登录

Tesla 的文档明载了窗口长度（24 小时）[A]，但未明载窗口内的行为是"可重复签发"还是"幂等返回"。这是一个必须保留的空白——本章在 12.8.3 给出的实现示意中，采用"幂等键 + 加锁"的客户端方案来规避该不确定性，并明确标注为设计建议，非对 Tesla 行为的断言。

12.2.3 吊销与传播

12.2.3.1 规范层：吊销端点与内省端点

信源档案 §2 收录了两个直接相关的规范，均为 [A]：

  • RFC 7009（2013）OAuth 2.0 Token Revocation：定义令牌吊销端点。它的关键语义边界是——吊销的传播是"尽力而为"的。规范层面，资源服务器并不保证立刻感知。
  • RFC 7662（2015）OAuth 2.0 Token Introspection：定义内省端点，让资源服务器在每次使用时向授权服务器查询令牌状态。

这两个规范合起来描述了一个基本矛盾：吊销需要"实时传播"才有效，而内省是"有成本的实时查询"。

12.2.3.2 车企实现层：Tesla 的三条吊销传播路径

信源档案 §7.1 提供了三条 [A] 的、彼此独立的吊销传播路径，它们分别作用于不同层级：

路径一：授权范围/授权的撤销（车主侧入口） 文档明载车主可通过 https://auth.tesla.com/user/revoke/consent?revoke_client_id=$CLIENT_ID&back_url=$RETURN_URL 管理授权范围或撤销授权 [A]。这是"授权基础"层的撤销，作用点是 OAuth consent。

路径二：scope 缩减对既有令牌的生效规则 文档明载：scope 缩减与既有刷新令牌兼容，仅对新签发的访问令牌生效 [A]。这条规则的工程含义极其重要：

  • 撤销一个 scope 后，已有的访问令牌在到期前仍然带着那个 scope 有效。这是一个"撤销不即时"的明确窗口。
  • 只有重新签发访问令牌时，新的 scope 集合才生效。
  • 反向操作（新增 scope）需要以 prompt_missing_scopes=true 重新发起 /authorize [A]——即新增权限必须重新经过车主同意界面。

路径三：配置级的下游联动（Fleet Telemetry） 文档明载：Fleet Telemetry 配置由应用私钥签名且"Tesla 无法编辑"；若所需 scope 被撤销导致配置失效，配置会被从车辆移除 [A]。这是一条非常值得对标的控制：撤销一个云端授权，触发了车端推流配置的自动回收。它不是"下次请求被拒"，而是"主动清理既有状态"。

路径四（命令级）：虚拟密钥的删除 文档明载，虚拟密钥的吊销由用户在车辆 Locks 界面删除密钥完成 [A]。注意这条路径的作用域：它关闭的是车端命令执行能力，而不是云端 API 访问能力——两者独立。

12.2.3.3 吊销传播的时间线（本报告判断，推测）

把上面四条路径合起来，可以画出一条多级、非同时的吊销传播时间线。本报告判断（推测，非事实）——这是对已知事实组合出的推理，档案未直接描述这条时间线：

t0  车主点击 revoke consent（路径一，[A] 入口）
    │
    ├─ t0 + ε   刷新令牌立即失效（推断依据：刷新需在线校验授权状态）
    │            客户端下次刷新 → 401 login_required（[A] 错误语义）
    │
    ├─ t0 + T_at  当前访问令牌到期（T_at 见 12.2.1；Tesla 值未证实）
    │            在此之前，被撤销 scope 对应的 API 调用【仍可能成功】
    │            依据：文档明载 scope 缩减"仅对新签发的访问令牌生效"（[A]）
    │
    └─ 车端侧：
         ├─ Fleet Telemetry 配置被从车辆移除（[A] 明载的自动联动）
         └─ 虚拟密钥【仍存在】直至车主手动在 Locks 界面删除（[A]）

这张图暴露的核心风险：在 t0 到 t0 + T_at 之间，存在一个"已撤销但未到期"的访问令牌窗口。攻击者若在此窗口内持有被撤销前泄露的访问令牌，仍可调用 API。这不是 Tesla 的缺陷陈述——文档明载的"scope 缩减仅对新签发访问令牌生效"是 OAuth 生态的通行语义；本报告判断（推测，非事实）：缩短访问令牌 TTL 是压缩该窗口最直接的手段，而 Tesla 的访问令牌 TTL 恰恰是本次未证实项（12.2.1.2），因此该窗口的实际长度无法从公开文档评估。

12.2.3.4 吊销事件的可观测性缺口

信源档案 §7.1 记录了 Tesla 的限流与计费模型，其中一个细节与吊销治理有关：超限会暂停 API 使用并移除 Fleet Telemetry 推流配置（且不恢复） [A]。这是一条"非安全性的吊销"——它由计费边界触发，但后果与安全吊销（配置被移除）在表现上无法区分。

本报告判断（推测，非事实）：这意味着一个第三方应用运维团队在收到"推流配置消失"的告警时，无法仅凭现象判定是"车主撤销了授权"还是"我们超额被暂停了"。缓解手段是为两种路径建立可区分的审计事件（例如授权服务器在撤销时发出一次带原因的信号）。这是 L 级（Low，文档与可观测性缺失）问题，按 00-engagement-plan.md §3.3 归入合规映射章节。

12.2.4.1 RFC 8555 ACME 作为短周期证书的工程前提

信源档案 §3 收录 RFC 8555（2019）ACME，并标注其定位为"自动化证书签发/轮换，短周期证书的工程前提" [A]。

本报告判断（推测，非事实）：短周期证书（例如 90 天或更短）的安全性优势是"私钥暴露窗口小、吊销依赖弱"，但它的前提是轮换必须全自动——人工轮换与 90 天周期不兼容。因此对车云场景而言，"是否使用短周期证书"这个问题实际上等价于"是否具备全自动证书生命周期管理能力"。这是规范语义推导出的工程结论，档案未对任何车企的 ACME 使用情况作出陈述（信源档案 §7.10 第 5 条：9 家国内车企的"证书轮换"方向未找到公开来源）。

12.2.4.2 RFC 3161 时间戳作为防重放的时间基准

信源档案 §3 收录 RFC 3161（2001）Time-Stamp Protocol，标注为"防重放的时间基准" [A]。

协同点：令牌/签名的防重放依赖"接受方与签发方对时间的判断一致"。若车端时钟可被操纵（车辆长期停放在地库、断开网络、电瓶断电），则：

  • 基于本地时钟的令牌过期判断可能被绕过（本报告判断，推测，非事实——前提是车端使用本地时钟做 exp 校验）。
  • 基于本地时钟的随机数/nonce 新鲜度判断可能失效。
  • 基于本地时钟的签名时间戳校验可能失效。

RFC 3161 提供的是由可信时间源签发的、可验证的时间戳，它把"时间"从本地状态变成"可验证的外部断言"。本报告判断（推测，非事实）：在车云场景中，凡是需要"证明某条命令在某个时间范围内首次出现"的控制点，都应考虑引入 RFC 3161 时间戳或等价的可信时间源，而不是依赖车端本地时钟。档案未记录任何车企在此方向的实现。

12.2.4.3 轮换的协同时序（本报告判断，推测）

一个协同完整的设计时序大致如下（全部为设计建议，非对任何企业实现的断言）：

  1. 车端设备证书临近到期 → ACME（RFC 8555）自动签发新证书；新旧证书在一段重叠窗口内并存。
  2. 车端用新证书重新建立与车云的 mTLS 链路（RFC 8446 / RFC 8705）。
  3. mTLS 链路上，资源服务器依据证书指纹校验绑定令牌（cnf / x5t#S256）——注意：证书轮换会导致已绑定令牌的指纹失配。
  4. 因此在证书轮换的重叠窗口内，服务端必须同时接受旧证书指纹与新证书指纹各自绑定的令牌，直至旧令牌全部自然到期。
  5. 命令级载荷的防重放校验以 RFC 3161 时间戳为基准，而非车端本地时钟。

第 3–4 步是一个必须显式设计的协同点，也是最容易被忽略的地方：令牌轮换与证书轮换若不同步，会在证书轮换瞬间造成"授权层拒绝合法请求"的批量故障。见 12.9 失败模式表对应行。

12.3 发送方约束令牌（Sender-Constrained Tokens）

12.3.1 为什么车云场景必须先解决"令牌可被复制"问题

12.3.1.1 Bearer 令牌的固有缺陷

RFC 6750 定义的 Bearer 令牌的核心语义是：持有即授权。信源档案 §2 将其内容描述为"Bearer 令牌在 HTTP 中的使用、WWW-Authenticate 错误语义" [A]。这个语义的推论是：任何获得令牌字节串的实体，都在授权范围内拥有与原始客户端完全等同的权限，且服务端无法区分两者。

在传统 Web 场景中，这个缺陷被三个条件部分抵消：浏览器同源策略限制了令牌的可获取路径；服务端渲染减少了令牌在客户端的停留；攻击者获取令牌的路径相对明确（XSS、日志泄露）。

在车云场景中，这三个条件同时弱化：

传统 Web 场景车云场景后果（本报告判断，推测）
浏览器沙箱 + 同源策略原生 App（RFC 8252 要求外部浏览器，见 12.5.1）、车机系统令牌可能落在应用私有存储，也可能落在系统级存储、日志、崩溃报告
单一进程持有令牌手机、车机、车企 TSP 服务器、第三方服务器多跳持有每一跳都是潜在的令牌泄露点
令牌泄露通常因单一漏洞令牌需在车企云 → 第三方 → 车链路上传递每一跳的运维方都有令牌可见性
泄露影响一个用户会话泄露影响一台或多台真实车辆的车控能力后果从数据泄露升级为物理安全

本报告判断（推测，非事实）：正是这张表的最后一行，使得车云场景对发送方约束令牌的需求强度高于一般的 API 场景。信源档案 §2 把 RFC 8705 标注为"车云链路最关键的授权规范"，正是同一判断的规范侧表述。

12.3.1.2 RFC 6750 的语义边界

需要注意，RFC 6750 并非"不安全规范"——它明确定义了传输要求（TLS 之上）、错误语义（WWW-Authenticate 响应头）与令牌不应用于 URL 查询参数等约束（信源档案 §2 将其内容概括为"Bearer 令牌在 HTTP 中的使用、WWW-Authenticate 错误语义" [A]）。

边界在于：这些要求约束的是"令牌如何传输"，而不改变"持有即授权"这一核心语义。因此 RFC 6750 与发送方约束令牌不是替代关系，而是"在无绑定能力时的下限"与"在有绑定能力时的增强"关系。OAuth 2.1 草案 draft-ietf-oauth-v2-1-16 明确包含"Bearer 令牌最小化"的方向（信源档案 §2 [A]），也印证了这一演进判断。

12.3.2 mTLS 证书绑定令牌：RFC 8705

12.3.2.1 机制概述

信源档案 §2 对 RFC 8705（2020）的描述是："mTLS 客户端认证 + 证书绑定令牌，即'持有的令牌不可被复制盗用'" [A]。它同时解决两个问题：

  1. 客户端认证：客户端用 mTLS 证书向授权服务器证明身份（取代或补充 client_secret）。
  2. 令牌绑定：访问令牌被绑定到客户端证书，使得令牌在被转移到另一条 TLS 连接后无法使用。

12.3.2.2 cnf / x5t#S256 绑定

RFC 8705 的绑定实现方式（信源档案条目给出的关键要素）：令牌中携带 cnf（confirmation）声明，其中包含证书指纹 x5t#S256——即客户端证书的 SHA-256 指纹。

工作方式（本报告判断，推测，非事实——按规范语义推导的机制描述）：

授权服务器                             资源服务器
    │                                      │
    │  1. 客户端以 mTLS 建立连接，             │
    │     出示客户端证书 C                     │
    │                                      │
    │  2. 授权服务器计算 SHA-256(C) = F       │
    │     签发访问令牌 AT，其中                │
    │     cnf: { "x5t#S256": F }             │
    │  ─────────── AT ────────────────────▶  │
    │                                      │
    │  3. 客户端以 mTLS 调用资源服务器，        │
    │     出示同一个证书 C                     │
    │  ──────────────────────────────────▶   │
    │                                      │
    │                          4. 资源服务器计算
    │                             SHA-256(C) = F'
    │                             断言 F' == AT.cnf.x5t#S256
    │                             不等即拒

关键点：绑定发生在 TLS 握手层提供的证书，而不是令牌内的任何自述字段。 这决定了它不可被复制——攻击者即使拿到了令牌字节串，也无法出示对应的客户端私钥来建立握手的证书（假设私钥不可导出）。

12.3.2.3 握手层与授权层的双层校验

本报告判断（推测，非事实）：RFC 8705 场景下存在两个独立且都必须通过的检查：

层检查内容失败的典型原因
握手层证书链是否可信（RFC 5280 [A]）CA 不受信、证书过期、链不完整
握手层证书是否被吊销（CRL [A] / OCSP [A]）证书已吊销但 OCSP 响应缓存过期
授权层令牌是否有效（exp、签名、aud）令牌过期
授权层cnf.x5t#S256 是否等于当前连接的证书指纹证书轮换窗口内指纹失配

第四行的失效模式值得单列：当客户端证书被轮换（RFC 8555 ACME 自动轮换，见 12.2.4）而令牌尚未过期时，新证书的指纹与令牌中的 cnf 不匹配。这不是安全缺陷，而是协同设计缺陷——缓解手段是轮换重叠窗口（见 12.2.4.3）。这个失效模式会在 12.9 表中以 High 等级出现。

12.3.2.4 车云场景的适用性讨论

本报告判断（推测，非事实）：mTLS 证书绑定令牌在车云链路上的最强适用点是服务器到服务器的链路（车企云 ↔ 第三方云、车企云 ↔ TSP），因为：

  • 服务端持有证书私钥的边界清晰（有 KMS/HSM 管理，信源档案 §4 收录 FIPS 140-3 [A] 作为 HSMA 认证基线）。
  • 服务端不需要面对"用户卸载应用后私钥残留"这类问题。
  • 服务端证书轮换可完全自动化（RFC 8555 [A]）。

最弱适用点是手机端第三方应用，因为客户端证书在移动端的部署、更新、吊销都更复杂。这正给了 DPoP 一个位置（12.3.3）。档案未记录任何车企在这两个方向的具体实现——Tesla 与 Mercedes 的已读文档中，本次未取得 mTLS 相关条目（Mercedes 明确列为未取到项，信源档案 §7.2）。

12.3.3 DPoP：RFC 9449

12.3.3.1 机制概述

信源档案 §2 对 RFC 9449（2023）的描述是：OAuth 2.0 Demonstrating Proof of Possession（DPoP），发送方约束令牌，DPoP 头 + JWK 指纹绑定 [A]。

与 mTLS 的核心区别：DPoP 在应用层（HTTP 头）而非传输层（TLS 握手）证明持有。它不要求客户端证书，代价是引入了自己的防重放机制。

要点一：私钥与公钥的物理隔离是"不可复制"的来源。 私钥在应用服务器、公钥在车辆，二者之间唯一的流通是公钥的托管与配对。攻击者若只攻破云端令牌存储，拿不到私钥，无法构造通过车端验签的载荷。这补齐了 12.3.1 中 Bearer 令牌的最大短板。

要点二：公钥托管要求"长期可用"是一个运维契约，也是一个可用性风险。 文档明载公钥文件必须长期可用 [A]。本报告判断（推测，非事实）：这意味着该 URL 成了一个长期依赖的可用性单点——若开发者的域名到期、证书失效、well-known 路径被重定向，可能影响车辆侧对密钥的校验与重新配对流程。缓解手段是把公钥的可用性纳入 SLO 监控（注意：Tesla 文档未明载"公钥取不到时的行为"，因此在 12.10 中列为待补证）。

要点三：密钥数量上限（< 20 把）是"影响范围控制"的工程手段。 文档明载 B2B 项目车辆可自动添加虚拟密钥的条件之一是已配对密钥少于 20 把 [A]。本报告判断（推测，非事实）：这是一个上限型配额——它不阻止单个开发者添加密钥，但限制了"一台车最多被多少方同时持有命令签名能力"，从而限制了一台车的授权扇出（fan-out）。这是车端密钥治理中最直接的影响范围控制，值得与 Tesla 的另一条配额对照：单台车辆最多同时向 5 个第三方应用推流 [A]（Fleet Telemetry）。

12.3.4.3 与 OAuth 令牌层的关系

本报告判断（推测，非事实）：虚拟密钥层与 OAuth 令牌层是串联而非并列的两道闸门：

  • OAuth 层（scope） 控制"这个第三方应用能调用哪些云端 API"。撤销 scope → 云端调用被拒；Fleet Telemetry 配置被移除 [A]。
  • 虚拟密钥层（签名） 控制"这个应用能否让车辆执行命令/接受推流配置"。删除密钥 → 车辆拒绝未通过验签的载荷 [A]。

串联意味着任何一层失败都不能导致越权。反之亦意味着任何一层失败都会导致合法业务中断——这正是 12.9 中"授权层与命令层不同步"这类失败模式的来源。文档明载的配对前置条件（用户须先授予 vehicle_device_data/vehicle_cmds/vehicle_location 之一 [A]）说明两层之间存在顺序依赖：OAuth consent 是虚拟密钥配对的前提。

12.4.1 RFC 9068 at+jwt profile

12.4.1.1 规范定位

信源档案 §2 对 RFC 9068（2021）的描述是：JWT Profile for OAuth 2.0 Access Tokens（typ: at+jwt、aud/iss/exp 校验要求） [A]。

这条规范解决的是一个长期存在的实现问题：OAuth 2.0 从未规定访问令牌的格式，导致 JWT 格式的访问令牌与 id_token 在结构上高度相似，接受方容易混淆。

12.4.1.2 强制校验清单

RFC 9068 的核心价值在于把"应该校验什么"从最佳实践提升为 profile 要求。本报告判断（推测，非事实——下表是对规范校验点的工程化组织，档案条目仅概括为"aud/iss/exp 校验要求"）：

12.4.1.3 aud 必须绑定 Fleet API base URL 的含义

信源档案 §7.1 有一条极其具体的 [A] 事实：Tesla 的 /token 换码参数含 audience（必须是 Fleet API base URL，如 https://fleet-api.prd.na.vn.cloud.tesla.com） [A]。

这条事实的技术含义（本报告判断，推测，非事实）：

  1. 区域隔离：示例值中的 na 表明 base URL 携带区域信息。aud 绑定 base URL 意味着一个区域的令牌不能被用于另一个区域的端点。这是把"物理部署拓扑"编码进"授权语义"的做法。
  2. 受众收敛：即使令牌泄露，它只能用于指定的 Fleet API 区域端点，不能被"挪"到 Tesla 的其他 API 面（例如授权端点本身、或未来的其他服务）。
  3. aud 校验的失败模式：若资源服务器不校验 aud，则跨区域/跨服务的令牌重用成为可能——这正是 12.4.3 第 1 条。

这是一个可推广的对标点：信源档案 §7.1 同时记录了 Tesla 的令牌端点与 API 端点分属不同主机 [A]（fleet-auth.prd.vn.cloud.tesla.com 与 fleet-api.prd.na.vn.cloud.tesla.com），并说明 /token 调用"来自应用服务器、适用不同的限流" [A]。本报告判断（推测，非事实）：主机分离 + audience 绑定 + 差异化限流这三者组合，构成一个清晰的"授权平面与数据平面分离"架构。这是本章推荐其他车企对标的一个重要结构性实践。

4把 id_token 当 access_token 用id_token 的 aud 是客户端而非资源服务器，且 id_token 语义是"认证某用户"，不含授权范围。若资源服务器接受它，则任何拿到 id_token 的方都能访问资源；且 scope 检查会落空取一个 id_token 直接当 Bearer 使用，观察是否通过；检查资源服务器是否校验 typ（RFC 9068 要求 at+jwt [A]）

10接受非 at+jwt 的 typ 或缺失 typ无法区分令牌类型，为第 4 条打开入口检查 typ 头；发送 typ: JWT（id_token 常见值）的令牌
11JWKS 未固定来源或允许任意 jku/jwk 头攻击者提供自己的 JWKS URL（jku）或内嵌公钥（jwk），使令牌验签通过构造带 jku 指向攻击者域名的令牌；检查服务端是否忽略这两个头
12虚拟密钥公钥文件未长期可用（车端场景特有）文档明载公钥须长期可用 [A]；若不可用，可能影响校验/重新配对流程（具体行为未取证）对 /.well-known/appspecific/com.tesla.3p.public-key.pem 做长期可用性监控；模拟 404/重定向观察影响

12.5 客户端认证与授权链

12.5.1 公共客户端 vs 机密客户端

12.5.1.1 定义与判定

本报告判断（推测，非事实——按 OAuth 2.0 生态通行语义组织）：

类型判定标准车云场景中的例子
机密客户端能安全保存 client_secret（服务器侧，无用户可直接访问）车企 TSP 服务器、第三方云端服务
公共客户端无法安全保存 client_secret（用户设备上运行）车主手机 App、车机应用

12.5.1.2 RFC 7636 PKCE 的必须性

信源档案 §2 对 RFC 7636（2015）的描述是：PKCE（Proof Key for Code Exchange，公共客户端授权码拦截防护） [A]。

PKCE 解决的问题（本报告判断，推测，非事实）：公共客户端无法用 client_secret 保护自己，因此授权码在重定向回客户端的过程中可能被同设备上的恶意应用拦截。PKCE 通过在授权请求中携带一个变换后的挑战值（code_challenge）并在换码时出示原始值（code_verifier），使得"拦截到授权码但没有原始 verifier"的方无法完成换码。

必须性的来源：信源档案 §2 明载 OAuth 2.1 草案 draft-ietf-oauth-v2-1-16 的核心方向之一是"强制 PKCE、废弃隐式流与密码模式" [A]。这意味着 PKCE 从"扩展"变成了下一代规范的基础要求。

本报告判断（推测，非事实）：因此对车云场景的推论是——任何在用户设备（手机、车机）上运行的授权码流程，PKCE 都不是可选项。而 Mercedes 的文档明载其采用"standard OAuth 2.0"（信源档案 §7.2 [A]），文档页面中本次未取得 PKCE 的明确说明（信源档案未记录 PKCE 条目）——这是 12.10 的一条待补证项，不能据此推断 Mercedes 未实现 PKCE。

12.5.1.3 RFC 8252 与车机场景的推论

信源档案 §2 对 RFC 8252（2017）的描述是：OAuth 2.0 for Native Apps（原生 App 必须使用系统浏览器/外部用户代理，禁止内嵌 WebView） [A]。

规范要求的技术理由（本报告判断，推测，非事实）：内嵌 WebView 无法保证"用户看到的界面与用户实际授权的对象一致"——宿主应用可以在 WebView 中注入内容、读取输入、窃取授权码。使用系统浏览器则把这层控制在应用边界之外。

对车机场景的推论（本报告判断，推测，非事实）：车机是一个受限 UI 环境。把 RFC 8252 的"必须用系统浏览器"规则机械地套到车机上会遇到两个问题：

  1. 车机可能不存在"用户可信任的通用浏览器"这一概念（车机浏览器生态与手机不同）。
  2. 车辆账号往往不是车主个人账号，而是车辆绑定账号——授权的主体界定本身更复杂。

因此车机场景更可能采用 RFC 8628 设备授权流（见 12.6）——即把授权动作外移到车主手机上，车机只负责展示设备码。这是一个规范语义的推论；档案未记录任何车企车机场景的授权流实现（信源档案 §7 中，车机侧的 OAuth 授权流实现未找到公开来源）。

12.5.2 客户端凭证的托管责任

12.5.2.1 Mercedes 的明载要求

信源档案 §7.2 有一条极其清晰的 [A] 事实：Mercedes 文档要求客户端凭证必须保存在后端服务器，应用"不得向客户端暴露任何客户端凭证（client id、client secret、访问令牌）" [A]。同处还记录了客户端指引：在服务端应用缓存访问令牌与刷新令牌；访问令牌有效期内直接使用，失效后由缓存的刷新令牌换取 [A]。

这条要求的三个含义（本报告判断，推测，非事实）：

  1. 架构强制：它实际上排除了"App 直连 Mercedes API"的架构，强制引入一个后端中转。
  2. 令牌不外流：访问令牌同样不得暴露给客户端——意味着后端不只是"代持密钥"，还要代理令牌。
  3. 缓存位置：令牌缓存必须在服务端，客户端侧不持有可长期复用的凭证。

12.5.2.2 Tesla 的对应事实

信源档案 §7.1 有两处 [A] 相关事实：

  • 授权端点不计费；/token 调用"来自应用服务器、适用不同的限流" [A]。
  • 令牌端点与 API 端点分属不同主机 [A]。

本报告判断（推测，非事实）：Tesla 虽未像 Mercedes 那样给出"不得暴露动词"的显式禁令文本（本次未取证到同等表述），但"/token 来自应用服务器"这一描述与"令牌在服务端换取"的架构一致，且由主机分离提供了拓扑上的强制。

12.5.2.3 静态密钥路径的对照

信源档案 §7.6 / §7.7 记录了两种非 OAuth 的接入方式：

平台凭证形式文档明载
比亚迪 i迪桥x-Gateway-APIKey（应用 appKey），置于请求头"用户创建应用 → 审核后生成 appKey 作为调用者身份识别" [A]
蔚来 Open NSCapp-id + secret 双凭证"app-id 和 secret 是系统对接调用的唯一凭证……通过商务渠道获取" [A]

本报告判断（推测，非事实）：这两类的工程属性与 OAuth 令牌族不同——静态密钥没有 TTL、没有轮换协议、没有内省端点、没有 scope 收窄机制（至少在已取证文档中未见）。它们依赖"商务渠道 / 审核发放"作为授权控制，依赖"撤销密钥"作为吊销手段。必须重申信源档案 §7.10 的警告：

  • i迪桥是企业级 ESB 网关（供应链/研发/智造/营销/物流/品质/财务），不等于车控开放平台——不得将"比亚迪车云授权 = APIKey"作为结论。
  • 蔚来 Open NSC 文档停留于 2019-08-13、业务范围为服务云（一键加电/维保/拖车/租车/代泊/航班），不含车控/数字钥匙 API，且站点自述"正在建设中"——不得以此代表蔚来当前架构。

一个值得注意的正面观察：信源档案 §7.7 记录，蔚来 Open NSC 的接口规范正文本身受 token 保护——"请联系文档提供人获取文档访问 token" [A]。这是"把文档访问本身纳入授权控制"的做法，本报告判断（推测，非事实）：它在信息层形成了一道"需先获授权才能看到接口定义"的闸门，客观上降低了攻击者的信息收集效率。

12.5.3 代理链与令牌交换

12.5.3.1 RFC 8693 的核心构件

信源档案 §2 对 RFC 8693（2020）的描述是：OAuth 2.0 Token Exchange（subject_token/actor_token，代理链授权） [A]。

两个令牌的角色（本报告判断，推测，非事实）：

  • subject_token：代表谁的权限被使用（主体的身份/授权）。
  • actor_token：代表谁在代替主体行事（代理方的身份）。

交换产出的新令牌中携带 act 声明，记录代理链。

12.5.3.2 车云"车企云 → 第三方 → 车"双层代理的 act 链路

本报告判断（推测，非事实——这是基于 RFC 8693 语义对本报告动机中的链路结构的建模，档案未记录任何企业采用该机制）：

车主 (resource owner)
  │ 授权
  ▼
第三方应用 (actor 1, subject = 车主)
  │ 携带 subject_token = 车主授权、actor_token = 第三方身份
  │ 调用车企云的令牌交换端点 → 得到新令牌 T1（含 act: {第三方}）
  ▼
车企云 (actor 2, subject = 车主, 已代理 1 层)
  │ 携带 subject_token = T1、actor_token = 车企云服务身份
  │ 交换 → 得到新令牌 T2（含 act: {第三方, 车企云}）
  ▼
车端网关
  │ 验证 T2 的 act 链是否完整、是否被允许
  ▼
执行（或拒绝）

act 链的价值（本报告判断，推测，非事实）：

价值说明
审计归因每条命令可追溯到完整的代理链，而非只有最终调用方
权限收窄每一跳可在交换时收窄 scope（RFC 8693 语义 + RFC 9396 [A]）
授权撤销传播若车主的原始授权失效，链路中任意一跳的交换都应失败
责任界定"谁的命令"在协议层可验证，不依赖应用日志自述

风险（本报告判断，推测，非事实）： 代理链越长，令牌交换的次数越多，每一跳都新增一个可被攻破的身份。若任一跳的 actor_token 管理不当，攻击者可以伪造某一跳的代理身份，导致 act 链被"污染"——最终的 act 链看起来合法，但其中一环是攻击者。缓解手段是每一跳的 actor_token 都必须由该跳自己独立持有（不可复用上游的凭证）。

12.5.3.3 RFC 7523 客户端断言

信源档案 §2 对 RFC 7523（2015）的描述是：JWT Profile for OAuth 2.0 Client Authentication and Authorization Grants（服务账号 + 客户端断言） [A]。

它解决的问题是：服务间调用没有"用户"参与，用什么证明客户端身份？ 两种用途：

  1. 客户端认证：用 JWT 断言（含 iss/sub/aud/exp/jti）取代 client_secret，避免静态密钥。
  2. 授权授予：用 JWT 断言直接换取访问令牌（服务账号流程）。

本报告判断（推测，非事实）：RFC 7523 对车云场景的价值在于它是消除静态密钥（12.5.2.3 表中的 secret/appKey）的规范路径——把"长期有效的共享密钥"换成"短时有效的签名断言"。这正好落在信源档案 §2 所述 OAuth 2.1 草案"Bearer 令牌最小化"的方向上 [A]。

12.5.3.4 两种代理机制的取舍

维度RFC 8693 令牌交换RFC 7523 客户端断言
主要用途跨主体/跨信任域的权限代表客户端身份认证 + 服务账号授权
是否表达代理链是（act 声明 [A]）否
典型场景车企云 → 第三方 → 车服务间无用户调用
与车云的关系双层代理的表达服务间凭证去静态化

本报告判断（推测，非事实）：两者在车云中通常是串联使用——第三方用 RFC 7523 客户端断言认证自己的服务身份，再用 RFC 8693 交换出代表车主的令牌。

12.5.4 步进认证：RFC 9470

12.5.4.1 构件

信源档案 §2 对 RFC 9470（2023）的描述是：OAuth 2.0 Step Up Authentication Challenge Protocol（acr/amr 步进认证挑战） [A]。

两个声明（本报告判断，推测，非事实）：acr 表示"认证上下文"，amr 表示"认证方法"。步进认证的机制是：资源服务器发现当前令牌的认证强度不足以完成某个操作时，返回一个挑战，要求客户端重新认证到更高的强度。

12.5.4.2 为高危车控命令引入二次认证的设计示例（推测设计）

以下完全为推测设计，档案未记录任何车企实现此机制：

设计假设：把车控命令按后果分级，为高危命令要求更高的 acr。

命令类别示例（依 Tesla scope 命名，信源档案 §7.1 [A]）建议 acr 要求（设计建议）
只读数据vehicle_device_data 覆盖的实时数据常规（单因素即 OAuth consent）
非车主本人驾驶场景操作添加/移除驾驶员（vehicle_cmds 覆盖）常规
车辆解锁vehicle_cmds 覆盖的解锁 [A]建议步进（要求二次认证）
远程启动vehicle_cmds 覆盖的远程启动 [A]建议步进
Live Camera 访问vehicle_cmds 覆盖的 Live Camera 访问 [A]建议步进（隐私敏感）
精确位置流式vehicle_location 覆盖建议步进（隐私敏感）

本报告判断（推测，非事实）：Tesla 的 scope 命名（vehicle_cmds 覆盖"添加/移除驾驶员、Live Camera 访问、解锁、唤醒、远程启动、预约软件更新" [A]）说明它是把多个不同后果的操作聚合在同一个 scope 下。这意味着仅靠 scope 无法对"解锁"与"预约软件更新"做差异化控制。步进认证正是补齐这一粒度缺口的机制。

风险与代价（本报告判断，推测，非事实）：步进认证在车云场景会遇到一个现实的可用性障碍——车主不一定在线。若车辆处于共享状态（代客泊车、维修、家人使用），远程解锁可能正是为了"让某人进入"，此时要求车辆持有者完成二次认证是合理的；但若要求的是"发起远程启动"的第三方应用持有者，则可能造成业务断裂。因此建议的落地方案是把步进认证与"命令风险等级 + 场景"联合判定，而非对所有高危命令一刀切。

12.6 设备授权与受限 UI：RFC 8628

12.6.1 规范要点

信源档案 §2 对 RFC 8628（2019）的描述是：OAuth 2.0 Device Authorization Grant（无浏览器设备授权，车机/受限 UI 场景适用） [A]。

流程骨架（本报告判断，推测，非事实）：设备向授权服务器发起请求 → 获得 device_code（设备用）与 user_code（人读用）→ 设备展示 user_code 与验证 URL → 用户在另一台设备（手机/电脑）上完成认证与授权 → 设备轮询令牌端点，直到获得令牌或超时。

12.6.2 轮询 interval 与 slow_down 语义

信源档案 §2 的 RFC 8628 条目概括提及设备码流程，未在本档案中记录 interval/slow_down 的数值语义。因此本节按规范语义描述（本报告判断，推测，非事实）：

机制语义工程含义
expires_in设备码的有效期用户在窗口内未完成授权则需重新发起
interval设备轮询的最小间隔设备必须遵守，否则触发 slow_down
slow_down轮询过快时的错误响应设备应增大轮询间隔，而非重试同一间隔
authorization_pending用户尚未完成授权设备继续按间隔轮询
access_denied用户拒绝设备应停止轮询，终止流程

slow_down 的设计意图（本报告判断，推测，非事实）：它是服务端对客户端行为的自适应节流——服务端不硬性拒绝，而是通过错误码让客户端自己变慢。这在设备数量庞大（如车队）的场景中尤其重要，因为所有设备可能在同一批次中被激活，形成同步的轮询风暴。

本报告判断（推测，非事实）：RFC 8628 在车机场景中的核心权衡是：

12.6.4 与设备码相关的安全边界

本报告判断（推测，非事实）：RFC 8628 引入了一个在授权码流程中不存在的攻击面——user_code 的猜测/社工。user_code 通常较短（便于人工输入），因此可能被暴力枚举或通过社工骗取。防护（规范语义）：

  • user_code 有有效期（expires_in），窗口外失效。
  • 用户完成授权时，授权界面应展示发起请求的设备信息，让用户确认"我是在为这个设备授权吗"。这在车机场景中尤其重要——如果用户看到的是一个陌生的设备标识，就应该拒绝。

本报告判断（推测，非事实）：RFC 8628 的企业采用情况在档案中未找到公开来源——Tesla 与 Mercedes 的已读文档中均未见设备授权流的条目。

  • L1 的信任完全在云侧（HSM 保护，但云被攻破即失效）。
  • L4/L5 的信任锚点在车端——Tesla 文档明载"车辆在执行命令前验证载荷签名" [A]，且称虚拟密钥"甚至能阻止 Tesla 自己的后端访问这些能力" [A]。CCC Digital Key 的密钥存于 Secure Element [A]。

这个倒置是车云安全的独有特征：云侧密钥泄露不会自动导致车端能力丧失，前提是车端有独立的验签/验密能力。本报告判断（推测，非事实）：因此评估一家车企的车云安全水平时，"云端令牌治理是否严密"与"车端是否有独立于云端的密钥校验"应当分开评估——前者决定数据与 API 的暴露面，后者决定物理车辆的可控性。

本报告判断（推测，非事实）：L5 与其他四级的关键差异在于它是唯一一个"物理接近性即授权"的密钥——BLE/UWB/NFC 的作用域是空间性的。因此它的失效后果不是"数据泄露"而是"车辆被开走"。这决定了 L5 的密钥必须存于 Secure Element（[A] 明载）而非普通存储，且必须具备中继攻击（relay attack）防护——这正是 UWB 精确定距被引入的原因（CCC Release 3.0 明载 BLE + UWB 组合 [A]）。

12.7.3.2 P-256 在车云中的实际位置

信源档案 §7.1 有一条极为具体的 [A] 事实：Tesla 虚拟密钥的生成命令为 openssl ecparam -name prime256v1 -genkey -noout，且文档明确"车辆仅支持 prime256v1 密钥"（即 P-256 ECDSA）[A]。

这条事实的四层含义（本报告判断，推测，非事实）：

  1. 算法约束来自车端：不是"应用想用什么"，而是"车辆只支持什么"。文档明载的"仅支持"是硬约束。
  2. 曲线选择与性能相关：P-256 在嵌入式验签性能与安全性之间是均衡点。本报告判断（推测，非事实）：车辆 ECU 的验签算力、功耗与延迟要求，使得更高安全等级的曲线（如 P-384/P-521）验签成本更高。档案未记录 Tesla 车辆的验签性能数据。
  3. ECDSA 的随机数要求：ECDSA 签名的安全性依赖每次签名使用唯一且不可预测的随机数 k（k 复用会导致私钥被直接恢复）。本报告判断（推测，非事实）：因此应用侧的签名实现必须依赖合规的 RNG（SP 800-90A [A]），且必须防止并发签名复用 k。这是"算法合规 ≠ 实现合规"的典型例子。
  4. 与证书体系的衔接：RFC 5480 [A] 定义了 EC 公钥在 X.509 中的表示，因此若车端设备证书也使用 P-256，则算法族统一，便于统一密码模块（FIPS 140-3 [A]）的验证范围。

12.8.1 令牌校验中间件伪代码

功能覆盖：aud / iss / exp / nbf 校验 + cnf 指纹比对 + 内省兜底 + 授权决策钩子。

# ─────────────────────────────────────────────────────────────
# 令牌校验中间件（示意代码）
# 设计目标：把 12.4.1 的强制校验清单、12.3.2 的 cnf 绑定、
#           12.4.2 的内省兜底、12.5.3 的 act 链，收敛为一个函数
# ─────────────────────────────────────────────────────────────

function authorize(request):
    raw = extract_bearer(request.headers["Authorization"])
    # 依据：RFC 6750 —— Bearer 令牌通过 Authorization 头传输
    if raw is null:
        return reject(401, "missing_token")

    # ── 第 1 步：令牌形态判定 ─────────────────────────────
    token = try_parse_jwt(raw)
    if token is null:
        # 不透明令牌路径：直接走内省（RFC 7662）
        return introspect_then_authorize(raw, request)

    # ── 第 2 步：JWT 形态的结构校验 ───────────────────────
    # 依据：RFC 9068 —— typ 必须为 at+jwt，强制校验 aud/iss/exp
    if token.header.typ != "at+jwt":
        # 注意：缺这一条就无法区分访问令牌与 id_token（见 12.4.3 第 4 条）
        return reject(401, "invalid_token_type")

    # 算法白名单（防止 alg 混淆，见 12.4.3 第 3 条）
    if token.header.alg not in ALLOWED_ALGS:   # 例如仅允许 ES256
        return reject(401, "alg_not_allowed")

    # 签名验证：从固定的 JWKS 来源取公钥（不信任 jku/jwk 头）
    jwks = JWKS_CACHE.get(issuer=token.claims.iss)   # 固定映射，非令牌自述
    if not verify_signature(token, jwks):
        return reject(401, "bad_signature")

    # ── 第 3 步：声明校验 ─────────────────────────────────
    now = trusted_now()   # 依据：RFC 3161 提供可信时间基准
    clock_skew = 60       # 设计建议值：秒

    if token.claims.iss != EXPECTED_ISSUER:
        return reject(401, "bad_issuer")

    if request.resource_audience not in as_list(token.claims.aud):
        # 依据：RFC 9068 —— aud 必须包含目标资源
        # 车云含义：Tesla 的 audience 必须是 Fleet API base URL
        return reject(401, "audience_mismatch")

    if now > token.claims.exp + clock_skew:
        return reject(401, "expired")

    if token.claims.nbf and now < token.claims.nbf - clock_skew:
        return reject(401, "not_yet_valid")

    # ── 第 4 步：发送方约束校验（RFC 8705 / RFC 9449）──────
    cnf = token.claims.get("cnf")
    if cnf is not null:
        if "x5t#S256" in cnf:
            # mTLS 证书绑定：比对当前 TLS 连接的客户端证书指纹
            actual = sha256(request.tls.client_certificate)
            if !constant_time_eq(actual, cnf["x5t#S256"]):
                return reject(401, "cnf_cert_mismatch")
            # 注意：证书轮换窗口内会在此失配（见 12.2.4.3 / 12.9）
        if "jkt" in cnf:
            # DPoP JWK 指纹绑定：校验 DPoP 头 + jti 去重 + nonce
            proof = request.headers.get("DPoP")
            if proof is null:
                return reject(401, "dpop_proof_missing")
            if !verify_dpop(proof, expected_jkt=cnf["jkt"],
                            seen_jti=JTI_STORE, required_nonce=SERVER_NONCE):
                return reject(401, "dpop_invalid")
            # nonce 挑战（RFC 9449 语义，见 12.3.3.3）
            if proof.nonce != SERVER_NONCE:
                return reject(401, "use_dpop_nonce",
                              nonce=SERVER_NONCE)   # 要求重试
            JTI_STORE.mark_seen(proof.jti, ttl=proof_ttl)

    # ── 第 5 步：内省兜底（高风险操作强制实时校验）─────────
    if is_high_risk(request) or token_age(token) > FRESHNESS_LIMIT:
        # 依据：RFC 7662 内省；RFC 7009 吊销
        intro = introspect(raw)
        if !intro.active:
            return reject(401, "token_revoked")
        if intro.scope != token.claims.scope:
            return reject(401, "scope_changed")   # 授权变更检测

    # ── 第 6 步：授权决策钩子 ─────────────────────────────
    ctx = {
        "subject":   token.claims.sub,
        "client_id": token.claims.client_id,
        "scope":     parse_scope(token.claims.scope),
        "act_chain": token.claims.get("act"),        # RFC 8693 代理链
        "resource":  request.resource,               # 例如 {"vehicle_id": "..."}
        "auth_time": token.claims.iat,
    }
    decision = POLICY_ENGINE.decide(ctx, request.action)
    # 依据：RFC 9470 —— 若认证强度不足，返回步进认证挑战
    if decision.verdict == "step_up_required":
        return reject(401, "insufficient_user_authentication",
                      acr_values=decision.required_acr)
    if decision.verdict != "allow":
        return reject(403, "policy_denied", reason=decision.reason)

    return next(request, with_context=ctx)

这份伪代码中每一条注释对应的前文小节：typ/aud/iss/exp/nbf → 12.4.1；alg 白名单 → 12.4.3 第 3 条；cnf.x5t#S256 → 12.3.2；cnf.jkt + DPoP nonce → 12.3.3；内省兜底 → 12.4.2；act 链 → 12.5.3；acr 步进 → 12.5.4。

一个实现细节的强调：第 4 步的 constant_time_eq 是必需的——指纹比对本应是固定长度字节比较，若用短路比较会引入时序侧信道。本报告判断（推测，非事实）：这是令牌绑定校验中最容易出的实现错误之一。

12.8.3 刷新令牌轮换的并发安全实现示意

针对 12.2.2.2 描述的并发竞态。设计要点：分布式锁 + 宽限期判定 + 幂等键。

# ─────────────────────────────────────────────────────────────
# 刷新令牌轮换的安全刷新器（示意代码）
# 目标：消除 12.2.2.2 的并发竞态；覆盖 12.2.2.3 的三种策略之一
# 注意：这是【设计建议】，不是对 Tesla / Mercedes 行为的断言
# ─────────────────────────────────────────────────────────────

class TokenRefresher:
    def __init__(self, store, lock, api):
        self.store = store      # 共享持久化存储（多副本安全）
        self.lock  = lock       # 分布式锁（按 client_id 粒度）
        self.api   = api

    def get_access_token(self, client_id):
        # ── 快速路径：本地缓存的访问令牌仍有效 ──────────────
        cur = self.store.load(client_id)
        if cur.access_token_valid(skew_seconds=60):
            # 依据：Mercedes 文档指引 —— 有效期内直接使用
            return cur.access_token

        # ── 慢速路径：需要刷新，先取锁 ─────────────────────
        with self.lock.acquire(client_id, ttl_seconds=30):
            # 双检：拿到锁后重新读，可能已被其他实例刷新
            cur = self.store.load(client_id)
            if cur.access_token_valid(skew_seconds=60):
                return cur.access_token

            # ── 幂等键：同一把刷新令牌并发刷新只做一次 ───────
            idem = derive_idempotency_key(cur.refresh_token)
            cached = self.store.get_idempotent_result(idem)
            if cached is not None:
                # 说明本进程外已有人用同一 RT 刷新过；直接复用结果
                self.store.save(client_id, cached)
                return cached.access_token

            # ── 真正的刷新调用 ─────────────────────────────
            try:
                resp = self.api.refresh(
                    grant_type="refresh_token",
                    refresh_token=cur.refresh_token,
                    client_id=client_id,
                )
                new = Tokens(
                    access_token=resp.access_token,
                    refresh_token=resp.refresh_token,   # 轮换后的新 RT
                    expires_in=resp.expires_in,
                )
                # 原子写入：新令牌整体落库，避免半写
                self.store.save_atomic(client_id, new)
                self.store.put_idempotent_result(idem, new, ttl=300)
                return new.access_token
            except RefreshRejected as e:
                # ── 失败恢复分派（见 12.2.2.4）────────────────
                if e.reason == "already_used":
                    # 可能落在宽限期外；再读一次存储，看是否
                    # 其他实例已经写入了更新的令牌
                    latest = self.store.reload(client_id)
                    if latest.refresh_token != cur.refresh_token:
                        return self.get_access_token(client_id)  # 重试一次
                    raise LoginRequired("refresh_token_superseded")
                if e.reason == "expired":
                    raise LoginRequired("refresh_token_expired")
                if e.reason == "user_password_reset":
                    # Tesla 文档明载：用户重置密码会触发 401 login_required
                    raise LoginRequired("user_password_reset")
                raise

设计说明（本报告判断，推测，非事实）：

设计动作解决的问题对应前文
快速路径（本地有效期判定）减少刷新调用频率，降低并发概率12.2.1
分布式锁（按 client_id）保证同一时刻只有一个刷新在途12.2.2.2
取锁后双检避免"等待锁的实例在拿到锁后重复刷新"12.2.2.2 步骤 4
幂等键（由刷新令牌派生）同一把 RT 的并发刷新复用同一结果12.2.2.3 策略二
save_atomic避免"新 AT 写了、新 RT 没写"的半写状态12.2.2.2 步骤 5
失败后 reload + 重试一次覆盖"宽限期竞态导致 already_used"12.2.2.4

必须注意的边界：这份实现不解决"授权被撤销"的场景——那需要重新走授权码流程（12.2.2.4 第三行）。伪代码中的 user_password_reset 分支直接抛出 LoginRequired，不做任何自动重试，这是刻意的：因授权基础变化而失败时，任何自动重试都是错误行为。

12.11 本章小结

12.11.1 事实层结论（全部可回溯至信源档案 [A] 条目）

  1. 令牌轮换已是主流的强约束实现。 Tesla 的刷新令牌一次性且 3 个月过期、最近使用的刷新令牌 24 小时内仍有效 [A]；Mercedes 的刷新令牌一次性且刷新返回新访问令牌与新刷新令牌 [A]。两家都实现了轮换。
  2. 访问令牌时长是部署决策，规范不规定。 Mercedes 明载默认 expires_in=3599 秒 [A]；Tesla 的访问令牌 TTL 在本次已读页面中未证实 [A]（档案列为待补证）。
  3. 吊销传播是多路径、非同时的。 Tesla 有五条可用证据：车主撤销入口 URL [A]、scope 缩减仅对新签发访问令牌生效 [A]、Fleet Telemetry 配置因 scope 撤销被从车辆移除 [A]、虚拟密钥由车主在 Locks 界面删除 [A]、超限会移除推流配置且不恢复 [A]。
  4. 车端存在独立的第二道闸门。 Tesla 车辆在执行命令前或接受 Fleet Telemetry 配置前验证载荷签名 [A]；公钥经 .well-known/appspecific/com.tesla.3p.public-key.pem 托管且须长期可用 [A]；私钥不入域名 [A]；算法被约束为 prime256v1（P-256）[A]；B2B 自动添加条件为已配对密钥少于 20 把 [A]。文档称虚拟密钥"甚至能阻止 Tesla 自己的后端访问这些能力" [A]。
  5. 授权平面与数据平面可分离。 Tesla 的令牌端点与 API 端点分属不同主机 [A]；/token 来自应用服务器、限流策略不同 [A]；audience 必须是 Fleet API base URL [A]。
  6. 客户端凭证托管责任已被明确写入部分车企文档。 Mercedes 明载不得向客户端暴露 client id / client secret / 访问令牌 [A]。
  7. 存在"退出逐车主同意模型"的授权路径。 vehicle_specs 与 vehicle_pricing_info 仅 Partner Token 可用、对任意车辆可用、无需车主授权 [A]。按 00-engagement-plan.md §3.3 归为 High。
  8. 存在双层授权控制的正面案例。 带 granular_access.hide_private=true 的车辆共享即使被授予 vehicle_location 也拿不到任何位置、且无法流式传输位置字段 [A]；位置类字段在 hide_private 车辆上会返回 HTTP 403 "location access not granted" [A]。归为 Informational→正面控制案例。
  9. 静态密钥路径与令牌路径在不同平台并存。 BYD i迪桥为 x-Gateway-APIKey（appKey）[A]；NIO Open NSC 为 app-id + secret [A]。但 i迪桥是企业级 ESB 网关、NIO 文档停留于 2019-08-13，两者的证据不能推广为"这些企业的车云授权模型"（信源档案 §7.10 第 3、4 条）。
  10. 规范底座完整。 本章使用的 OAuth 2.x 族（RFC 6749 / 6750 / 7009 / 7523 / 7636 / 7662 / 8252 / 8414 / 8628 / 8693 / 8705 / 9068 / 9396 / 9470 / 9449 / 9635）、OIDC Core、PKI 族（RFC 5280 / 6960 / 3161 / 8555 / 8446 / 5480 / 8017 / 6090 / 8998）、NIST 族（FIPS 140-3 / 186-5 / 197、SP 800-57 Pt1 R5 / 800-38D / 800-90A R1 / 800-133）均为 [A] 一手条目。

12.11.2 判断层结论（本章标注为推测，非事实）

以下四条是本章由规范语义与已取证事实推导出的工程判断，不构成对任何企业的技术陈述：

  1. 车云场景对发送方约束令牌的需求强度高于一般 API 场景，因为令牌持有链长且每跳可信度不同（12.3.1.1）。
  2. 令牌轮换与证书轮换必须同步设计，否则在证书轮换瞬间会出现批量授权拒绝（12.2.4.3、12.9 第 8 行）。
  3. "命令授权层无自动过期"是最易被忽视的暴露面决定因素——系统有效暴露面由最长的那个凭证周期决定（12.2.1.3）。
  4. 端点分离 + audience 绑定 + 差异化限流三者组合，构成可对标的结构性实践（12.4.1.3）。
