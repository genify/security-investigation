13.0 本章方法与覆盖度声明

13.0.1 本章要回答的问题

前面三个切面分别回答了「授权协议有哪些」（协议族）、「令牌与密钥怎么管」（令牌模型）、「总体分几层」（总论）。本章回答一个更尖锐的问题：

当授权被「授予」之后，系统如何确保它只能作用于「恰好应当被作用的那个资源」？

这个问题在车云场景里被放大到极端，因为资源不再是数据库里的一行记录，而是：

  • 一辆价值数十万元、载人的物理车辆；
  • 一个可以开锁、启动、鸣笛、打开后备箱的物理执行器；
  • 一条可以精确到米级的位置轨迹；
  • 一路车内摄像头的实时视频；
  • 一份诊断与维修记录。

因此本章的论证主线是「授权粒度收窄」：从最粗的裸字符串 scope，到 RFC 9396 的结构化权限对象，再到资源级策略（resource-level policy） 这一「第二层闸门」。核心命题是：

授权被授予 ≠ 资源被放行。

本条命题不只是一个理论断言，而是在 Tesla Fleet API 文档中有可直接引用的实现证据（见 13.3.1）。本章因此把 Tesla 作为「资源级授权」的正面标尺，把 Mercedes-Benz 作为「scope 命名空间治理」的正面标尺，并对其余车企按证据可得性做有限对标。

02

13.1 从范围授权到资源级授权

13.1.1 裸字符串 scope 的表达力上限

OAuth 2.0（RFC 6749，2012）用 scope 参数承载授权范围。scope 的定义是一个空格分隔的不透明字符串集合：

scope=openid offline_access vehicle_location vehicle_cmds

这种设计的工程优势是简单、可缓存、易比较。但在车云场景，它有一个结构性缺陷：一个 scope 字符串必须同时编码「资源集合」「动作集合」「时间/条件约束」三类信息，而字符串本身不携带任何结构。

把车辆、命令类别、数据域压成一个字符串，直接后果是：

  1. 无法表达「仅某辆车」。vehicle_cmds 一旦授予，在令牌层面即覆盖该车主名下全部车辆。要收窄到单车，只能依赖服务端在资源级再做一次判定——而这恰恰是 OAuth scope 机制本身不提供的。
  2. 无法表达「仅解锁」。Tesla 文档明载 vehicle_cmds 覆盖「添加/移除驾驶员、Live Camera 访问、解锁、唤醒、远程启动、预约软件更新」这一组差异极大的动作 [A]。第三方应用只要申请 vehicle_cmds，就同时拿到了「唤醒」与「打开摄像头」——前者是低敏感操作，后者是隐私高敏感操作。scope 层面无法区分。
  3. 无法表达「仅接下来 2 小时」。授权码流签发的令牌只有统一的 expires_in，没有「按 scope 分级的有效期」概念。短期授权与长期授权被迫共用同一 TTL。
  4. 无法表达「仅读不写」之外的条件。例如「仅在工作日」「仅当车辆停放时」「仅当车速为零时」——这些环境条件在裸 scope 里无处安放，只能下沉到服务端业务逻辑，脱离授权服务器的统一审计。

本报告判断：上述四点不是「实现 bug」，而是协议表达力的理论上限。围绕它的合理工程结论是——凡涉及高敏感资源（位置、摄像头、车控）的车云授权，都应在 scope 之外叠加一层结构化的资源级策略，而非试图通过「把 scope 字符串写得更长」来逼近目标。（推测，非事实——这是对协议能力的推理，非对某家车企实现的断言。）

13.1.2 RFC 9396 Rich Authorization Requests：结构化权限对象

RFC 9396（2023）OAuth 2.0 Rich Authorization Requests 直接针对上述上限 [A]。其核心引入一个 authorization_details 参数，取值是一个结构化对象数组，每个对象用 type 声明权限类别，其余字段由该 type 的语义定义。

RFC 9396 规定的通用字段族包括（文档明载的字段语义）：type、locations、actions、datatype、identifier、privileges 等——即「在哪（locations）」「做什么（actions）」「操作什么数据（datatype/identifier）」「以什么特权（privileges）」。

下面给出一个车控场景的 authorization_details 示意 JSON（本示意为本报告自行构造，用于说明字段语义，非任何车企的真实报文，不可实际调用）：

{
  "type": "vehicle_command",
  "locations": [
    "https://fleet.example-oem.com/vehicles/VIN1234567890"
  ],
  "_comment": "locations 表达『仅这辆车』——资源定位符指向单一 VIN",
  "actions": [
    "unlock"
  ],
  "_comment2": "actions 表达『仅解锁』——不复用整组 vehicle_cmds",
  "datatype": "vehicle_control",
  "privileges": [
    "single_use",
    "not_before=2026-09-28T12:00:00Z",
    "not_after=2026-09-28T14:00:00Z"
  ],
  "_comment3": "privileges 表达『仅接下来 2 小时』——时间窗写在授权凭证内部"
}

逐字段解释（如何表达「仅这辆车、仅解锁、仅接下来 2 小时」）：

字段示意取值表达的能力裸 scope 的对应缺陷
typevehicle_command声明这是一条「车控」类权限，授权服务器据此路由校验逻辑裸 scope 无类别概念
locations指向单一 VIN 的 URL仅这辆车：把资源从「账号下全部车辆」收窄到「一个 VIN」vehicle_cmds 覆盖全账号车辆
actions["unlock"]仅解锁：白名单式动作枚举vehicle_cmds 一封全包
datatypevehicle_control声明被操作的数据对象类别，供字段级策略挂载无
privilegessingle_use + not_before / not_after仅接下来 2 小时：时间窗与一次性约束写在凭证内令牌只有统一 TTL

关键工程含义：RFC 9396 让「资源级约束」从服务端业务代码里的 if 判断，上升为授权凭证本身的一部分。带来的直接收益是：

  • 可审计：授权服务器签发的对象即可被独立记录与复核，不必事后拼凑服务端日志。
  • 可撤销到细粒度：撤销可以针对单个 authorization_details 条目。
  • 同意界面可结构化呈现：同意界面能逐条渲染「应用将能解锁 VIN1234567890 这辆车，有效期 2 小时」，而不是展示一串无语义的字符串。

13.1.3 scope 与 authorization_details 对照表

下表对照裸 scope 与 RFC 9396 结构化权限对象在四个工程维度上的差别。表中「裸 scope」列的判断依据为 RFC 6749 的机制定义 [A]，「结构化对象」列的判断依据为 RFC 9396 的机制定义 [A]；最后一行的校验复杂度为工程推断，标推测。

维度裸字符串 scopeRFC 9396 authorization_details
表达力只能表达「类别级」权限；无法内嵌资源、动作白名单、时间窗、条件可表达资源定位（locations）、动作枚举（actions）、数据类别（datatype）、特权/条件（privileges）

工程取舍建议（本报告判断，推测，非事实）：

  • 当授权对象只有一类、粒度为「全账号」且敏感度低（如仅 openid 身份）时，裸 scope 的简单性优于 RAR。
  • 当授权对象是高敏感资源（车控、位置、摄像头）且需要按车/按动作/按时限收窄时，RAR 的结构化表达力是必需的，服务端校验复杂度是必须支付的代价。
  • 混合策略（低敏感用 scope、高敏感用 authorization_details）在协议上可行——RFC 9396 允许 scope 与 authorization_details 并存。

13.1.4 OAuth 2.1 草案与 RFC 9635 GNAP 作为演进方向

OAuth 2.1 草案 draft-ietf-oauth-v2-1-16 [A]：该草案的方向是收敛与硬化——强制 PKCE、废弃隐式流与密码模式、推动 Bearer 令牌最小化。它并不新增资源级表达能力，但通过淘汰弱流程压缩了「因流程本身脆弱而导致授权被滥用」的空间。对车云场景的含义是：沿用 OAuth 2.x 生态的工程路线会自然向 2.1 收敛，RAR（RFC 9396）是这条路线上的资源级增强件。

RFC 9635（2024）GNAP [A]：Grant Negotiation and Authorization Protocol，Standards Track，2024-10 发布。它代表更远的一步——「可协商授权」。GNAP 的设计理念是：客户端不是单向「申请一组固定 scope」，而是与授权服务器协商获得授权；授权服务器可以根据上下文（客户端身份、资源敏感度、环境）决定授予什么、附带什么约束。GNAP 面向「细粒度 + 可协商」授权，是资源级授权在协议层的长线演进方向。

本报告判断（推测，非事实）：对车企的现实建议不是「立刻上 GNAP」——GNAP 的生态成熟度远低于 OAuth 2.x——而是在 OAuth 2.x 之上先落地 RFC 9396 的资源级表达，把治理模型与协议解耦，使未来若迁移到 GNAP 时，资源级策略资产可以复用。

13.2.1 对 scope 清单的横向解读

解读一：粒度不一致的「三分层」。 12 个 scope 实际上落在三个截然不同的资源粒度上：

  • 身份/会话层：openid、offline_access——不涉及车辆资源。
  • 车辆/能源资源层：vehicle_device_data、vehicle_location、vehicle_cmds、vehicle_charging_cmds、energy_device_data、energy_cmds——账号下全部同类资源，是「一次授权、全量覆盖」的粗粒度。
  • 退出逐车主模型层：vehicle_specs、vehicle_pricing_info、enterprise_management——不进入逐车主同意链路。

这一分层本身就是本章要论证的「资源级授权」问题的现场：处在中间层的 6 个 scope，其令牌粒度是「账号级」而非「车辆级」；把授权收窄到单车的能力，只能由 scope 之外的机制提供。

解读二：vehicle_cmds 是「动作全包」的典型风险点。 文档明载它同时覆盖「解锁」「唤醒」与「Live Camera 访问」[A]。这三个动作的敏感度是梯度上升的：唤醒 < 解锁 < 摄像头。第三方应用一旦申请 vehicle_cmds，就同时获得三者，车主在同意界面上看到的是一个无语义的字符串，无法选择「只给唤醒、不给摄像头」。

本报告判断（推测，非事实）：这正是 13.1.1 所述「裸 scope 表达力上限」的现实投影。若按 RFC 9396 的 actions 字段重构，vehicle_cmds 应拆为 ["wake"]、["unlock"]、["live_camera"] 等可独立授予的动作枚举。

解读三：vehicle_device_data 的语义宽度。 文档明载它覆盖「实时数据、服务历史、服务预约、服务沟通、可升级项、附近超充、所有权信息」[A]——横跨「车辆遥测」与「车主服务流程」两个域。这意味着该 scope 同时承担了「读车」与「读服务记录」两类不同性质的权限。

13.2.2 vehicle_specs / vehicle_pricing_info：绕过逐车主同意模型的资源访问路径

这是本章最需要严肃对待的授权控制例外。

文档明载 [A]：

  • vehicle_specs 仅 Partner Token 可用，且对任意车辆可用、无需车主授权；
  • vehicle_pricing_info 仅 Partner Token 可用。

为什么这是「退出逐车主同意模型」的路径？ 在正常的第三方授权码流里，令牌代表车主行事，其资源范围被车主的同意范围绑定。而 Partner Token 代表的是合作伙伴自身。当 vehicle_specs 对「任意车辆」可用且「无需车主授权」，意味着：

存在一条不经过车主同意即可读取车辆规格信息的资源访问路径。

严重度判定（按 00-engagement-plan.md §3.3 口径）：CSO 已在计划文档中预先判定为 High——理由是「单一凭证可横向影响平台其他『资源对象』」，且属于授权控制例外，需在报告中显式标注为『退出逐车主同意模型』的路径。计划文档原文建议「以契约与审计补偿」。

注意边界（不可越线）：

  • 该判定的对象是授权模型设计，不是 Tesla 的实现缺陷——文档本身就把它作为「仅 Partner Token 可用」的受控能力公开。
  • 判定不涉及「读取了车主个人数据」——文档列举的是车辆规格与定价信息，属产品级/目录级信息，而非车主隐私。
  • 严重度之所以为 High 而非 Critical，是因为 §3.3 对 Critical 的判据是「授权链可被绕过，导致任意车辆车控/位置被未授权访问」——vehicle_specs 不提供车控或位置能力，故不达 Critical 门槛。

补偿控制建议（本报告提出，工程建议）：

控制目标对应威胁
契约约束合作伙伴协议中限定 vehicle_specs 的用途（仅产品目录、市场分析），禁止与车主身份关联数据用途越界
审计对 Partner Token 调用 vehicle_specs / vehicle_pricing_info 全量记录并按 VIN 聚合分析异常量级凭证泄露后的批量枚举
最小化应答字段响应仅返回产品级规格，剥离任何可关联到具体车主/账号的字段规格信息与个人数据再关联

13.3 双层授权控制：scope 之上的资源级策略

13.3.1 granular_access.hide_private=true 的语义

Tesla 文档明载 [A]：

带 granular_access.hide_private=true 的车辆共享，即使被授予 vehicle_location，也拿不到任何位置，且无法流式传输位置字段。

这是本报告在全部取证材料中找到的唯一一条「授权已授予、资源仍被拒绝」的一手实现证据。它的工程意义在于：它把「授权（authorization）」与「资源放行（resource release）」显式分离为两层。

受影响的遥测字段（文档逐条列出 [A]）：

字段名语义（车云遥测中的典型含义）
Location车辆当前位置
OriginLocation行程起点位置
DestinationLocation行程终点位置
DestinationName目的地名称
RouteLine行驶路径线
GpsStateGPS 状态
GpsHeadingGPS 航向

文档明载：位置类字段需要 vehicle_location；而 hide_private 共享车辆尝试访问会被拒绝并返回 HTTP 403，错误语义为 location access not granted [A]。

这条 403 的关键价值在于它的错误语义：它不是笼统的「权限不足」，而是明确指认「位置访问未获准」。本报告判断（推测，非事实）：这种字段级、语义化的拒绝，使调用方能够准确区分「我的令牌缺 scope」与「车主对该车设置了私有化共享」——这对第三方应用的降级处理与用户体验至关重要（前者应重新请求授权，后者应提示「该车主已隐藏位置」）。

13.3.2 「授权被授予 ≠ 资源被放行」的判定链

把 Tesla 的实现抽象为一条决策流水线（ASCII 图，本图为本报告依据文档明载事实绘制的抽象模型，非任何车企的原始架构图）：

        ┌──────────────────────────────────────────────────────────┐
        │ 第 0 层：令牌存在性与签名                                  │
        │   Authorization: Bearer <token>                           │
        │   校验：签名 / iss / aud / exp（RFC 9068 风格）             │
        └───────────────────────────┬──────────────────────────────┘
                                    │ 通过
                                    ▼
        ┌──────────────────────────────────────────────────────────┐
        │ 第 1 层：scope 检查（粗粒度闸门）                          │
        │   token.scope ⊇ { 请求端点所需的 scope } ?                 │
        │   例：请求 vehicle_data → 需 vehicle_device_data           │
        │   例：请求位置字段     → 需 vehicle_location               │
        └───────────────────────────┬──────────────────────────────┘
                                    │ 通过（注意：此处通过 ≠ 放行）
                                    ▼
        ┌──────────────────────────────────────────────────────────┐
        │ 第 2 层：车型/资源级策略（resource-level policy）          │
        │   读取该车（该 VIN）的共享策略                             │
        │   例：granular_access.hide_private == true ?               │
        │        → 位置类字段一律拒绝                                │
        └───────────────────────────┬──────────────────────────────┘
                                    │ 通过
                                    ▼
        ┌──────────────────────────────────────────────────────────┐
        │ 第 3 层：字段级过滤（field-level filtering）               │
        │   按该资源策略，对响应 / 流式报文逐字段裁剪                │
        │   流式场景：位置字段不进入推流负载                          │
        └───────────────────────────┬──────────────────────────────┘
                                    │
                    拒绝时返回统一语义错误                      放行
                    HTTP 403 "location access not granted"   → 返回裁剪后的资源

这条流水线的可复制性要点：

  1. 两层是「与」关系，不是「或」关系——必须同时满足。token 有 scope 只是必要条件。
  2. 第 2 层的判定输入是「资源自身的属性」（该车的共享策略），不是令牌的属性。这就是「资源级」的含义。
  3. 第 3 层把「拒绝」细化到字段，使非敏感字段（如 BatteryLevel）仍可正常提供，而敏感字段（如 Location）被剥除——避免了「一刀切全拒」导致的功能损失。
  4. 流式通道与轮询通道同等对待——文档明载 hide_private 车辆「无法流式传输位置字段」[A]，说明策略贯穿到 Fleet Telemetry 这条车→云直连通道，而不只是 REST 端点。

13.3.3 该模式作为正面控制案例的可复制设计清单

按 00-engagement-plan.md §3.3，granular_access.hide_private 被 CSO 判定为 Informational → 正面控制案例，建议其他车企对标。以下是本报告提炼的可复制设计清单（工程建议，非对任何车企事实的断言）：

设计项具体做法解决的缺陷
双闸门强制明确区分「授权层」与「资源放行层」，二者逻辑独立、代码路径分离避免把 scope 当唯一闸门
资源属性参与判定把车辆/设备侧的隐私策略（如 hide_private）作为授权决策的输入使「同一令牌、不同车辆」可被区别对待
字段级裁剪拒绝粒度下沉到字段，而非整接口保功能、保隐私
语义化错误码用可区分的错误语义（如 location access not granted）替代笼统 403便于客户端正确降级
通道一致性REST 轮询与流式推送走同一套资源级策略堵住「换个通道绕过策略」
策略可撤销资源侧策略变更（车主改为私有化）后，已签发令牌不得重新获得该字段防止策略变更与令牌缓存不一致
审计记录「因资源级策略而拒绝」的事件，与「因缺 scope 而拒绝」的事件分开统计可区分治理问题与授权问题

反例提示（本报告提醒）：若把资源级策略只实现在 REST 端点而漏掉流式通道，则会形成「轮询拿不到、推流拿得到」的绕过路径。Tesla 文档明载其在流式上同样拦截 [A]，这是值得显式对标的实现细节。

13.4 最小权限与同意模型

最小权限（least privilege）在车云场景不能止步于「scope 尽可能少」，还必须同时满足：同意的知情性、授权的可增量性、撤销的贯穿性。本节按这三条展开。

13.4.1 逐车主同意（per-vehicle consent）的实现要素

（一）同意界面的知情决策设计——Mercedes-Benz 样本

Mercedes-Benz 文档明载 [A]：同意界面展示所请求的 SCOPE 与「purpose URL」，便于终端用户知情决策。文档同时给出采用授权码流的理由：「部分 API 提供燃油状态、车门锁状态等数据，属 GDPR 意义上的个人数据，因此需要终端用户同意」[A]。

工业价值在于：「purpose URL」把「为什么需要这项权限」写进了同意流程。车主看到的不是孤立的 mb:vehicle:mbdata:fuelstatus，而是「字符串 + 用途说明链接」的组合。本报告判断（推测，非事实）：这是在 GDPR「目的限制原则」约束下的一种把「目的」显式化的工程手段，值得作为「知情同意」的对标基准。

Mercedes 文档还明载两项前置 scope 语义 [A]：

  • openid scope 为获得有效令牌所必需；
  • offline_access 为获得刷新令牌所必需。

即：若应用需要长期代表车主访问，必须同时申请 offline_access；若只申请 openid+业务 scope 而不申请 offline_access，则拿不到刷新令牌。这是一种「按需申请长期凭据」的默认最小化设计——不申请 offline_access 的应用天然只有短期授权。

（二）prompt_missing_scopes 与 require_requested_scopes 的语义差异——Tesla 样本

Tesla 文档明载 /authorize 的两个附加可选参数 [A]：

参数文档语义生效后的授权行为工程用途
prompt_missing_scopes=true对尚未授权的 scope 再次提示增量授权：只针对缺的 scope 弹同意，已有 scope 不重复打扰新增能力时不要求车主从头再同意全部
require_requested_scopes=true必须授权全部请求 scope 才放行全有或全无：任一 scope 未授权则整个授权失败保证应用拿到完整的能力集后再进入业务

两者的语义差异是本章一个重要辨析点：

  • prompt_missing_scopes 是关于「同意界面如何展示」——它改变的是「是否对缺的 scope 再次提示」，即增量授权的实现方式。
  • require_requested_scopes 是关于「授权成功与否的判定条件」——它改变的是「部分授权算不算成功」。

本报告判断（推测，非事实）：这两个参数解决的是两个不同的问题，可能被误认为同义：

  • 若应用能容忍部分授权（例如「有车辆数据但没位置」也能工作），则不设 require_requested_scopes，配合 prompt_missing_scopes 引导增量补齐。
  • 若应用的业务逻辑强依赖全部 scope（例如「必须同时有位置和充电命令」），则设 require_requested_scopes=true，避免「拿到了半套权限却按全套逻辑运行」的隐藏故障。

文档另明载 show_keypair_step=true 用于「预告虚拟密钥配对第二步」[A]——即授权流程中存在第二步的密钥配对，该参数使同意界面能提前告知车主。

（三）增量授权与 scope 缩减对既有刷新令牌的兼容规则——Tesla 样本

Tesla 文档明载 [A]：

Scope 缩减与既有刷新令牌兼容，仅对新签发的访问令牌生效；新增 scope 需以 prompt_missing_scopes=true 重新发起 /authorize。

这条规则包含两个方向相反的兼容性约定，值得逐字拆解：

变更方向对既有刷新令牌（3 个月、一次性）的影响何时生效
缩减 scope兼容（既有刷新令牌仍可换码）仅对新签发的访问令牌生效——即下一次刷新时，新访问令牌已不含被撤 scope
新增 scope既有刷新令牌不足以获得新 scope必须重新走 /authorize 且带 prompt_missing_scopes=true

为什么这个设计是合理的（本报告判断，推测，非事实）：

  • 缩减不需要重新同意——因为「用更少的权限」对车主是收紧，不构成隐私风险，无需再次征求同意。这让「应用主动降权」成为一种零摩擦的自我约束。
  • 新增必须重新同意——因为「用更多的权限」是扩张，触及车主知情权，必须回到授权端点由车主重新确认。这防止了应用「先拿低权限获得信任、再静默升级至高权限」。

这条规则是「最小权限」在令牌生命周期上的具体落点：它使「权限只能经车主明示同意而增长，而可以无声地收窄」成为机制约束。

13.4.2 mb: 三段式 scope 命名空间的治理价值

Mercedes-Benz 文档给出的示例 scope 字符串为 [A]：

scope=openid offline_access mb:vehicle:mbdata:fuelstatus

其中 mb: 前缀的命名空间呈现三段式结构：mb:<域>:<子域>:<资源>，可解读为「品牌前缀 · 业务域 · 数据/资源域 · 具体资源」。

Mercedes 平台的产品分类为 Fleet Data、Smart Vehicle Data、Infrastructure Data、Vehicle Commerce Data、Repair & Maintenance Data [A]——这恰好对应命名空间中「域」与「子域」的层次。示例中的 mb:vehicle:mbdata:fuelstatus 即「车辆域 · 车辆数据子域 · 燃油状态资源」。

治理价值对照（本报告分析）：

治理维度mb: 三段式命名空间粗粒度裸 scope（如 vehicle_device_data）
可读性字符串自身携带层次语义，运维与审计人员可判读需外部文档才能理解含义
可扩展性新增资源 = 新增命名空间叶子，不改动既有权新增能力常导致 scope 数量线性增长且无结构
冲突避免品牌前缀 mb: 天然避免与通用 scope（openid）混淆无命名空间时易与标准 scope 混用
授权粒度粒度可细到单个资源（fuelstatus）粒度停在类别级
同意界面语义更易映射为「资源 X 的访问权」只能展示类别，车主难判断
通配与批量可通过命名空间做前缀匹配（如 mb:vehicle:*）实现批量授权需逐条枚举

本报告判断（推测，非事实）：mb: 命名空间实际上是在裸 scope 机制内部做的一次「穷人版结构化」——它没有 RFC 9396 那种可内嵌时间窗与条件的能力，但通过命名约定大幅提升了 scope 的语义含量与治理秩序。对不愿立刻引入 RAR 的车企，规范化的 scope 命名空间是一个低成本的中间态。

13.4.3 同意撤销路径：撤销必须贯穿到最末端执行点

Tesla 文档明载三条位于不同层次的撤销路径 [A]：

撤销层次机制文档明载的行为
云端同意层https://auth.tesla.com/user/revoke/consent?revoke_client_id=$CLIENT_ID&back_url=$RETURN_URL车主可管理授权范围或撤销授权
车辆端密钥层用户在车辆 Locks 界面删除虚拟密钥车端授权校验失效；文档称虚拟密钥「甚至能阻止 Tesla 自己的后端访问这些能力」
流式配置层所需 scope 被撤销导致 Fleet Telemetry 配置失效时配置会被从车辆移除

三者构成一条「撤销贯穿到最末端执行点」的完整链路：

   车主撤销同意（云端）
        │
        ├──► 刷新令牌失效 → 401 login_required（下一刷新周期）
        │
        ├──► Fleet Telemetry 配置因 scope 撤销被【从车辆移除】
        │
        └──► （若同时删除虚拟密钥）车端拒绝执行命令 / 拒绝接受遥测配置

为什么「贯穿到最末端」是原则性问题（本报告分析）：

  1. 云端撤销有时延。文档明载刷新令牌一次性且 3 个月有效，且最近一次使用的刷新令牌在 24 小时内仍有效（宽限期，用于覆盖「应用未能持久化轮换后令牌」的失败场景）[A]。这意味着：仅靠云端撤销，不可能做到「即时生效」——因为已签发的访问令牌在其 TTL 内仍然有效，且 24 小时宽限期内旧刷新令牌仍可用。
  2. 因此必须有「末端闸门」。虚拟密钥（车端验签）与 Fleet Telemetry 配置移除（流式通道回收）在车辆侧提供了一道不依赖云端时延的闸门。文档明载虚拟密钥由车端执行命令前验证载荷签名 [A]，且密钥删除由车主在车辆 Locks 界面完成 [A]——删除动作发生在车辆上，立即生效。
  3. 配置回收是「自动化」的末端闸门。Fleet Telemetry 配置由应用私钥签名且「Tesla 无法编辑」[A]，但当所需 scope 被撤销导致配置失效时，配置会被从车辆移除 [A]。本报告判断（推测，非事实）：这是一条由授权状态驱动的资源回收，把「撤销」从「人工操作」变成了「授权服务器与车辆固件的联动」。

归纳出的原则（本报告提出，工程原则）：

撤销必须同时落在「凭证层」「执行器层」「数据通道层」三处；任何一层的缺失都会形成「撤销了但还能用」的残留窗口。

警示：Tesla 的这条链路之所以能贯穿到车端，前提是虚拟密钥模型（车端持有公钥、私钥在应用服务器、车端验签）[A]。若某平台的命令执行不经过车端验签，则撤销只能止步于云端，必然存在残留窗口。这是架构依赖，不是配置能弥补的。

13.5 影响范围控制（Blast Radius Containment）

按 00-engagement-plan.md §3.3，High 的判据之一是「单一应用/单一凭证被攻破可横向影响同账号其他车辆或平台其他租户」。本节系统性梳理 Tesla 文档中明载的各项「限制影响范围」的控制。

13.5.1 「单一应用被攻破不影响整个平台」的控制清单

控制Tesla 文档明载内容限制的横向扩散证据
令牌—应用绑定第三方令牌代表车主行事、由特定 client_id 获取；/token 需 client_id + client_secret攻破应用 A 的令牌不能用于应用 B 的调用链路[A]
令牌—资源绑定（aud）/token 的 audience 必须是 Fleet API base URL（如 https://fleet-api.prd.na.vn.cloud.tesla.com）令牌不能跨 audience 使用（RFC 9068 风格约束）[A]

逐项解读：

「令牌—车辆绑定」是这一清单的核心。 文档明载虚拟密钥是公私钥对，公钥由可信用户添加到车辆，私钥留在应用服务器，车辆在执行命令前或接受 Fleet Telemetry 配置前验证载荷签名 [A]。这意味着：攻击者即使窃取了云端令牌，若没有对应私钥，也无法构造出车端验签可通过的命令载荷。文档进一步称虚拟密钥「甚至能阻止 Tesla 自己的后端访问这些能力」[A]——这是一条车端主导的授权，其权威高于云端。

「同账号多应用共享限额」的防御语义（本报告分析）：文档明载同账号多应用的限额是共享的 [A]。这在安全上意味着：一个被攻破的应用无法通过「另起一个应用」来突破限流——因为限额挂在账号维度，不挂在应用维度。这是在配额设计里预置了横向抑制。

「单车上限 5 个第三方应用」的防御语义：文档明载单台车辆最多同时向 5 个第三方应用推流 [A]。本报告判断（推测，非事实）：这是一条显式的资源占用上限，其安全价值在于——它把「第三方向一辆车订阅遥测」的规模硬性封顶，使得「攻破 N 个第三方以汇聚一辆车全量数据」的攻击需要先挤掉合法应用的名额，从而提高攻击可观测性。

「已配对密钥少于 20 把」的防御语义：文档明载 B2B 车辆自动添加虚拟密钥的条件是已配对密钥少于 20 把 [A]。本报告判断（推测，非事实）：这是把「密钥配额」作为防密钥泛滥的手段——若不设上限，一个被攻破的应用理论上可反复添加密钥建立持久后门；上限使密钥集合成为有限且可审计的集合。

13.5.2 限流与配额作为安全控制

Tesla 文档明载的限流与计费机制 [A]（来源：developer.tesla.com 的 billing-and-limits 文档，见 dossier §7.1）：

维度文档明载内容
实时数据60 次/分
唤醒3 次/分
设备命令30 次/分
限额归属按账号按设备计；同账号多应用共享
计费周期按用量，月度周期（每月 1 日起算）
计费上限每账号计费上限默认 0
告警达 80% 与 100% 时发邮件
超限后果暂停 API 使用，并移除 Fleet Telemetry 推流配置（且不恢复）
折扣个人开发者/小应用每月 $10 折扣
计费规则响应码 <500 全部计费，≥500 不计费；费用四舍五入到 $0.01
过渡日期文档原文：应用访问在该付款过渡期内不会被禁用，该过渡期结束于 2024-02-01

「超限即暂停并移除推流配置且不恢复」的双重语义：

  • 作为成本控制：超限暂停是防止账单失控的常规手段。
  • 作为（事实上的）影响范围控制：一旦某账号触发超限，其 Fleet Telemetry 推流配置被移除且不恢复 [A]——这意味着异常高频的调用会被系统性地切断数据通道。

本报告识别出的风险：配额耗尽是可用性攻击面。

考虑一个攻击场景（以下为威胁分析，非对任何已发生事件的陈述）：

攻击者目的：让受害者（车主或第三方应用）的车辆遥测不可用
攻击路径  ：窃取/滥用某账号凭证 → 高频调用至触及 100% 上限
后果链    ：超限 → API 被暂停 → Fleet Telemetry 推流配置被移除【且不恢复】
               → 受害者需人工介入重建配置 → 服务中断 + 恢复成本

为什么「不恢复」放大了该风险：文档明载超限后果包含「移除 Fleet Telemetry 推流配置（且不恢复）」[A]。「不恢复」意味着从可用性损伤中自动恢复的路径不存在——这使一次配额耗尽不仅造成短期中断，还留下需要人工修复的持久损伤。

缓解建议（本报告提出，工程建议）：

缓解做法针对的风险
区分「善意超限」与「异常突发」对平稳超限走计费告警路径，对瞬时突发走临时限速而非「暂停 + 移除配置」避免攻击者用突发流量触发最严重的惩罚档
移除配置前设冷却与确认移除 Fleet Telemetry 配置这类破坏性且不自动恢复的动作，应设二次确认或较长冷却降低单次误触发的损伤
凭证与配额绑定到「最小可用范围」按应用而非按账号隔离配额，或对单应用设子配额防止单应用耗尽整账号配额（注意：Tesla 现为账号级共享，这本身也是 13.5.1 中的正向控制，二者存在权衡）
配额耗尽的可观测性将「接近上限」「已触发暂停」作为安全事件而非纯计费事件记录使攻击可被检测
恢复自动化若确认超限为误触发/攻击，提供一键恢复清空恶意配置而不必重建缩短 MTTR

注意这对设计的张力（本报告判断，推测，非事实）：「按账号共享限额」在安全上是有利的（抑制横向扩权，见 13.5.1），但在可用性上放大单点耗尽风险。二者不是谁对谁错，而是需要在「横向抑制」与「纵向韧性」之间取平衡的工程决策。

13.6 授权模型选型：RBAC / ABAC / ReBAC

本节性质声明：RBAC / ABAC / ReBAC 是授权领域的行业通行概念，source-dossier.md 中没有对应的一手条目。因此本节的所有映射与示例均为本报告基于领域知识的构造，按红线必须显式标注为推测/示意，不得表述为任何车企的既成事实。

13.6.1 三种模型的车云映射表

维度RBAC（基于角色）ABAC（基于属性）ReBAC（基于关系）

13.6.2 ABAC 策略示例（自然语言 + 伪策略）

自然语言策略示例一：亲属驾驶员的解锁权

当主体是「与该车辆存在有效共享关系」的「亲属」角色，且动作为「解锁」，且当前时间为车主设定的可用时段内，则放行；否则拒绝。

自然语言策略示例二：车位代泊的限时委托

当主体是「代客泊车员」，且动作为「解锁 + 启动」，且委托时间窗（not_before/not_after）有效，且车辆处于车主设定的地理围栏内，则放行；否则拒绝。

自然语言策略示例三：服务技师的诊断读取

当主体是「授权服务中心技师」，且动作为「读取诊断数据」，且该技师所属机构与该车存在有效维修工单，则放行；否则拒绝。注意：该策略不得扩展至位置或摄像头。

伪策略（Pseudo-Policy，示意语法，非任何真实策略引擎格式）：

// 伪策略 1：亲属限时解锁（本报告示意，非事实）
ALLOW action == "unlock"
  WHEN subject.relation(vehicle) == "shared:family"
   AND subject.role == "family_member"
   AND now() WITHIN owner_window(vehicle)
   AND vehicle.share_policy.hide_private == false      // 资源级策略参与判定
  OTHERWISE DENY

// 伪策略 2：代泊限时委托（本报告示意，非事实）
ALLOW action IN {"unlock", "start"}
  WHEN subject.role == "valet"
   AND delegation.not_before <= now() <= delegation.not_after
   AND vehicle.geofence.contains(subject.location)

// 伪策略 3：技师仅有诊断读取权（本报告示意，非事实）
ALLOW action == "read" AND resource.datatype == "diagnostics"
  WHEN subject.role == "service_technician"
   AND exists(work_order(subject.org, vehicle))
DENY action IN {"read_location", "live_camera"}              // 显式兜底拒绝

关键设计点：伪策略 3 中的显式兜底 DENY 是「最小权限」的常见实现手法——先给最小必要权限，再对高敏感动作显式拒绝，而不是依赖「没写 ALLOW 就等于拒绝」的隐式默认，从而让审计者能看到对敏感动作的明确否定。

13.6.3 选型建议（本报告判断，推测，非事实）

场景建议模型理由
车企内部运维/后台RBAC角色稳定、审计简单
车主-车辆-共享人关系ReBAC（叠加 ABAC 条件）「一车多人」本质是关系图
车控动作的条件判定ABAC需编码车速/地点/时段等环境属性
第三方应用授权OAuth scope + RFC 9396 RAR + 资源级策略与协议生态兼容

本报告判断：车云场景不存在「选一种」的选项——真实的资源级授权是 ReBAC 的关系图 + ABAC 的条件求值 + 协议层的 scope/RAR 的叠加。把三者混为一谈（例如试图用「更大的 RBAC 角色表」解决所有问题）会导致角色爆炸，最终无法维护。（推测，非事实。）

13.7 常见授权缺陷（OWASP API Security Top 10 对齐）

本节性质声明：OWASP API Security Top 10 是行业通行框架，source-dossier.md 中没有对应条目。本节按框架 + 车云具象化 + 检测 + 修复 + 严重度的方式展开，其中「车云场景的具象后果」部分与 13.2/13.3 已取证的事实（如 vehicle_cmds 覆盖多动作、vehicle_specs 无逐车主授权）联动引用。严重度按 00-engagement-plan.md §3.3 口径判定。

13.7.1 API1 —— 对象级授权缺失（BOLA / Broken Object Level Authorization）

项内容
缺陷端点接受资源标识（如 VIN），但不校验该标识是否属于当前令牌的主体
车云具象后果VIN 越权：攻击者以自己车辆的合法令牌，把请求路径中的 VIN 替换为他人的 VIN，若能成功即读到/控制他人车辆。这是车云最危险的授权缺陷——一辆车换取全平台车辆
检测方法双账号对拍：用账号 A 的令牌请求账号 B 的 VIN 资源；对所有接受资源标识的端点逐一测试；检查响应状态码是否为 403/404（而非 200）
修复策略在资源访问层强制校验「令牌主体 ↔ 资源归属」；资源查询使用参数化主体过滤（WHERE vin = ? AND owner = token.sub），禁止先查后判
严重度Critical（§3.3：授权链可被绕过，导致任意车辆车控/位置被未授权访问）

13.7.2 API2 —— 认证失效（Broken Authentication）

项内容
缺陷令牌签发/校验缺陷：弱密钥、无签名校验、接受 alg:none、刷新令牌可无限复用
车云具象后果伪造令牌即可代表任意车主；对对比参考：Mercedes 明载刷新令牌一次性使用，Tesla 明载刷新令牌一次性且 3 个月有效、宽限期 24 小时 [A]——这类约束正是防复用的机制
检测方法篡改 JWT 载荷后重放；测试 alg 降级；重放同一刷新令牌两次观察是否都被接受
修复策略强制签名校验与算法白名单；刷新令牌一次性 + 轮换；参照 RFC 9068 校验 iss/aud/exp
严重度Critical

13.7.3 API3 —— 对象属性级授权（BOPLA / Excessive Data Exposure）

项内容
缺陷端点授权正确（允许访问该对象），但响应中返回了超出授权范围的字段
车云具象后果响应字段越权：授权只覆盖 vehicle_device_data（如电量），但响应里顺带返回了 Location。这正是 13.3.2 第 3 层「字段级过滤」要解决的问题——Tesla 在 hide_private 场景下对位置字段返回 403 而非静默返回空值 [A]，是属性级控制的正面样本
检测方法对比不同 scope 下同一端点的响应字段集；用差分测试找「多出来的字段」；检查是否有字段在 scope 未授予时仍出现
修复策略白名单式响应构造（只序列化授权字段），而非黑名单剥除；对敏感字段（位置、摄像头）设独立字段级策略
严重度High（§3.3：可横向暴露同账号车辆的敏感字段）

13.7.4 API5 —— 功能级授权缺失（BFLA / Broken Function Level Authorization）

项内容
缺陷对「不同功能层级」的端点不做角色/权限区分，普通用户可达管理功能
车云具象后果函数级越权：普通第三方应用可达「添加/移除驾驶员」这类本应属于车主或企业的功能。具象锚点：Tesla 的 vehicle_cmds 同时覆盖「添加/移除驾驶员」与「解锁/唤醒」[A]——若端点不按动作细分权限，则申请「唤醒」的应用可能触及「添加驾驶员」
检测方法枚举端点清单；以低权限令牌访问高权限端点；测试 HTTP 方法（GET→POST/DELETE）的权限一致性
修复策略逐端点声明所需权限；高敏感功能（改权限、改密钥、改同意）设独立权限或步进认证（RFC 9470）
严重度Critical（若可导致「添加驾驶员/远程启动」）

13.7.5 API8 —— 安全配置错误（Security Misconfiguration）

项内容
缺陷CORS 过宽、调试端点暴露、默认凭证、错误信息泄露内部结构
车云具象后果调试端点若暴露车辆台账或令牌信息，可为 BOLA 提供枚举字典；过宽 CORS 使恶意网页可代车主发起请求
检测方法扫描 /debug、/actuator、Swagger 等；检查 CORS 头；触发错误观察是否泄露堆栈/内部主机名

严重度Medium（§3.3：影响范围可被扩大）→ 若直接暴露凭证则升 High

13.7.7 混淆代理（Confused Deputy）在车云链路的形态与防护

形态描述：车企云为了给第三方提供「代车主访问车辆」的能力，自身成为拥有高权限的代理。若无防护，第三方可诱使代理用它自己的高权限去访问第三方本无权访问的车辆：

   第三方应用 ──「帮我访问 VIN_OTHER」──► 车企云（高权限代理）
                                            │
                                            │ 【缺陷】代理不校验
                                            │  第三方是否对该 VIN 有权
                                            ▼
                                        访问 VIN_OTHER ──► 越权成功

防护的核心：让代理「以第三方的身份」而非「以自己的身份」行事。

RFC 8693 OAuth 2.0 Token Exchange [A] 提供 subject_token / actor_token 机制：代理链上应显式记录「谁在替谁行事」。文档明载 RFC 8693 用 subject_token/actor_token 表达代理链授权 [A]。据此，防护设计为：

   第三方应用 ──► 车企云（以第三方的限定令牌请求代访问）
                    │
                    │ 【防护】代理链显式携带 act 声明（谁在替谁）
                    │         + 资源级判定（第三方是否对该 VIN 有权）
                    │         + 逐车主授权（车主是否同意该第三方访问）
                    ▼
                访问车辆 —— 三重均通过才放行

补偿控制清单（本报告提出，工程建议）：

控制说明
act 链显式化用 RFC 8693 的 actor_token 记录代理身份，使最终资源方能区分「车主本人」与「第三方经代理」
逐车主授权参与代理转发前校验车主是否已同意该第三方访问该车（对齐 13.4.1 的逐车主同意）
资源级判定前置代理在转发前重新执行资源级授权（对齐 13.7.6 与 13.3.2 第 2 层）
令牌，不转发凭证代理绝不把车主令牌原样交给第三方；第三方的请求经限定作用域的令牌交换
车端独立验签车端对任何来源的载荷验签（Tesla 虚拟密钥模型 [A]），使代理被攻破也不足以伪造命令

严重度：Critical——混淆代理在车云代理链上直接等价于 13.7.1 的 BOLA，且更隐蔽（因为代理本身是「合法高权限主体」）。

13.11 本章小结

13.11.1 主要结论

  1. 裸字符串 scope 的表达力存在理论上限：它无法表达「仅这辆车」「仅这个动作」「仅这段时间」。当资源是高敏感的车控、位置、摄像头时，这一上限会直接转化为过度授权。RFC 9396（authorization_details）提供了结构化表达，代价是服务端校验复杂度上升。
  2. Tesla Fleet API 的 12 个 scope 呈现「三分层粒度」：身份/会话层（openid、offline_access）、车辆/能源资源层（6 个，账号级粒度）、退出逐车主模型层（vehicle_specs、vehicle_pricing_info、enterprise_management）。其中 vehicle_cmds 的「动作全包」（解锁 + 唤醒 + 摄像头）是「scope 表达力上限」的现实投影。
  3. vehicle_specs / vehicle_pricing_info 的「仅 Partner Token 可用且对任意车辆无需车主授权」是一条退出逐车主同意模型的资源访问路径 [A]。按 00-engagement-plan.md §3.3 判为 High，并给出契约、审计、最小化应答字段等补偿控制。
  4. 「授权被授予 ≠ 资源被放行」有直接实现证据：granular_access.hide_private=true 的车辆即使被授予 vehicle_location，位置字段仍被拒绝并返回 HTTP 403「location access not granted」 [A]。本报告将 Tesla 的实现抽象为四层决策流水线（令牌校验 → scope 检查 → 资源级策略 → 字段级过滤），并提炼出含「通道一致性」（流式同样拦截）的可复制设计清单。
  5. 最小权限在车云场景的三个落点：知情同意（Mercedes 的 SCOPE + purpose URL [A]）、增量授权与缩权兼容（Tesla 的 prompt_missing_scopes / require_requested_scopes 与「缩减兼容、新增需重授权」[A]）、撤销贯穿末端（Tesla 的云端撤销 + 车辆删除虚拟密钥 + Fleet Telemetry 配置自动移除 [A]）。
  6. 影响范围控制是多层叠加：令牌—应用绑定、令牌—资源绑定（audience）、令牌—车辆绑定（虚拟密钥）、按账号按设备限流（60/3/30 次每分，同账号共享）、单车上限 5 个第三方应用、密钥上限 20 把、企业级 scope 隔离——全部为文档明载 [A]。
  7. 配额是一把双刃剑：文档明载的「超限暂停并移除 Fleet Telemetry 配置（且不恢复）」[A] 既是成本控制，也是事实上的影响范围控制；但本报告识别出「配额耗尽是可用性攻击面」——攻击者可借触发超限造成不自动恢复的服务中断。缓解建议为区分善意超限与突发、移除配置前设冷却、凭证与配额绑定最小范围。
  8. 授权模型不存在「选一种」的答案：车云的资源级授权是 ReBAC 关系图 + ABAC 条件求值 + 协议层 scope/RAR 的叠加。（本报告判断，推测，非事实。）
  9. 授权缺陷最危险的是 BOLA / 混淆代理：VIN 越权与「车企云代理第三方访问」链路上的混淆代理，均可导致任意车辆被未授权访问，判为 Critical。防护的关键是让代理以被代理者的身份行事——RFC 8693 的 act 链 + 资源级判定 + 逐车主授权三重把关，并配合车端独立验签。
