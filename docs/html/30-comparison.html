30.0 本章方法与对比的可比性声明

30.0.1 本章要回答的问题

AC-6 要求给出"国内外技术路线差异对比"，包含至少 5 个维度的对比矩阵与差异归因。本章把这一要求拆成 6 个对比维度（30.2–30.7），加 1 个归因分析专节（30.8），再加 1 个"与通用分层技术方案的差异"专节（30.9，对应调研目标的第二条），最后给出结论（30.10）与待补证清单（30.11）。本章要回答的核心问题是：

  1. 可观测到的技术方案形态在"通用方案 / 已落地方案"之间、"国内路线 / 国际路线"之间、"车企与车企"之间，到底有哪些结构性差异？
  2. 这些差异里，哪些是证据层面的差异（只是"没公开"），哪些是方案层面的差异（确实选了不同的做法）？
  3. 造成这些差异的可能成因是什么，能否给出可检验的推断与检验方法，以便后续 RFI 补证？

30.0.2 关键声明：证据密度不均衡导致的可比性偏差（本章最重要的方法论前提）

本章首先且必须说明一个会支配全部结论的可比性偏差：

  • 本次取证的条件（见信源档案 §0）：检索工具 web_search / web_extract 全程额度耗尽（Firecrawl 402/429），公开搜索引擎全部不可用（Bing 地理重定向、Baidu/Sogou/360 验证码、Google 机器人墙、DuckDuckGo 验证码），部分权威站点被区域封锁或 Cloudflare 拦截（bmw.com、bmwgroup.com、rivian.com、unece.org、iso.org、autosar.org、trustedcomputinggroup.org），且 open.xiaopeng.com 对所有请求返回 403。因此本次调研无法做开放网络发现，只能"直取已知权威 URL"。
  • 由此产生的证据密度极端不均衡：
    • 文档公开充分者：Tesla（developer.tesla.com 证据最厚）、Mercedes-Benz（developer.mercedes-benz.com）——这两家本次取得了接口级的一手文档，包括鉴权流程、scope 清单、令牌参数、错误语义。
    • 取证受限者：BMW（站点返回占位页"no content deployed"）、Rivian（CloudFront 区域封锁）——本次未取得任何授权文档。
    • 九家国内车企：9 家全部未取得关于「国密 SM2/SM3/SM4」「mTLS 双向证书」「证书轮换」「HSM/SE/TEE」的任何官方一手来源（信源档案 §7.10 第 5 条）。仅蔚来、比亚迪两家取得了服务层的鉴权形态（且均非 OAuth），小米取得了 IoT 平台与信任中心认证信息。
  • 本章的核心纪律——把"证据可见度"与"安全水平"严格区分：
    • 证据可见度（documentation visibility / evidence density）：一个主体对外公开了多少可检索的技术文档。这是披露策略、商业定位、语言与渠道的函数，与安全能力无必然关系。
    • 安全水平（security level）：一个主体实际实现的安全控制强度。这是工程、算法、硬件、流程的函数，在本次条件下基本不可直接观测。
    • 两者的关系不是单调的：文档公开充分的 Tesla 与文档几乎不可见的国内某车企，其实际安全水平在本报告的证据里无法排序——因为排序所需要的观测数据（文档）在一侧充足、在另一侧缺失。把"证据可见度"误当"安全水平"排序，是本章乃至全报告最需要防范的推理错误。
  • 因此，本章的比较对象被严格限定为：
    • ✅ 可观测到的技术方案形态：即"文档里写出来的架构、协议、参数、命名、流程"。
    • ❌ 不比较"安全水平"：本章不给任何车企的安全能力强弱打分、排序或暗示。
    • 凡涉及"某车企是否具备某能力"的断言，一律写为「未找到公开来源 / 本次未取证」，并声明这不等同于能力缺失（对齐审计计划 §3.2 第 4 条红线）。

30.1 三组对比的定位

本章的对比不是"一条轴"，而是三组不同性质的对比。混在一起会导致"苹果对橙子"的错误。三组对比如下：

A 组：通用方案 vs 已落地方案

  • 对比物：docs/02-general-layered-security.md 描述的六层通用参考模型（硬件 → 通信 → 授权 → 应用平台 → 生命周期/合规，包含 TEE/HSM、mTLS、OAuth 2.x 族、UPTANE/SUIT 等规范层能力） vs 本次已取得一手文档的落地实现（Tesla Fleet API、Mercedes-Benz Developer Platform 的授权形态）。
  • 性质："规范应有的控制"对"某实现实际公开的控制"。用于识别"通用方案里被落地实现的点"与"公开文档未覆盖的点"。
  • 风险：落地实现只取到了 2 家的公开细节，因此 A 组结论的适用面仅限这 2 家 + 规范层，不能外推为"行业实态"。
  • 落点：30.9 专节。

B 组：国内路线 vs 国际路线

  • 对比物：中国监管与标准制度（GB/GB/T 强制与推荐国标族、数据出境与重要数据制度、国密算法族） vs 国际监管与标准制度（UN R155/R156 型式认证、GDPR、EU Data Act、ISO/SAE 21434 族）。
  • 性质："制度驱动"对"制度驱动"——两侧都是规范层的对比，不是车企实现层。
  • 风险：国际侧的法规模块本次均未取得正文（R155/R156 标 [未验证]，GDPR/Data Act 标 [C]），因此 B 组只能对比名称与方向，不给条款与时间表。
  • 落点：30.5 专节。

C 组：车企之间的方案形态差异

  • 对比物：被取证主体之间的方案形态（Tesla、Mercedes-Benz、BYD、NIO、Volkswagen/CARIAD、Xiaomi 等有公开材料者），涵盖鉴权形态、scope 命名、令牌参数、开放生态位、披露政策。
  • 性质："可观测形态"对"可观测形态"——这是三组里最接近"实证"的一组，但受 30.0.2 的可比性偏差支配最严重（每个主体的可观测面大小不同）。
  • 风险：把"某主体文档多"误读为"该主体方案更完整"。
  • 落点：30.2、30.3、30.4、30.6、30.7 五个专节。

30.2.2 开放度分级模型（L0–L3）

为把上表的结构化，本报告提出一个开放度分级模型（本报告构造的分析框架，属 [合理推测] 框架，非任何标准）：

L3  完整接口级公开文档
    —— 鉴权流程 + scope 清单 + 令牌参数 + 错误语义，均可公开检索
    —— 开发者可自助接入

L2  接口级文档但受限
    —— 有接口规范，但需注册 / 商务渠道 / 文档访问 token，或文档明显陈旧

L1  仅公开"合规与治理"文件
    —— 门户/信任中心/隐私政策/漏洞专栏存在，但无接口级技术文档

L0  无公开文档
    —— 无开发者入口，或入口不可达（占位页 / 区块封锁 / 403 / 500）

按此模型对本次取证主体的归类（归类依据均为上表的已取证事实；归类本身为 [合理推测]，且 L 值描述的是"公开度"，不是"安全性"）：

关于该模型的三条纪律：

  1. L0–L3 是"公开度"刻度，不是"安全性"刻度。一个 L0 主体完全可能拥有比 L3 主体更强的实际安全实现——只是本次无法观测。把 L 值当"安全等级"读，是本章禁止的推理。
  2. L 值有"可达性噪声"：BMW/Rivian 的 L0 来自区域封锁（本报告出口 IP 受限），小鹏/极氪的 L0 来自站点拒绝服务——这些是本次的观测失败，不是主体的披露选择。
  3. 该模型的用途是"补证排序"：L0 主体应优先用"换出口 IP / 沙箱账号 / RFI"补证（对齐信源档案 §8），而非据 L0 下任何结论。

30.2.3 从开放度看"三类开放性来源"

把 L1–L3 的取证来源分类，可以看到开放度不是单一维度的——不同主体开放的是不同种类的东西：

开放种类已取证主体特征与安全的关系
开放"接入"（接口级文档）Tesla、Mercedes-Benz、比亚迪、蔚来文档面向"如何接入"可直接观测授权形态
开放"合规"（信任中心/隐私政策/认证）小米（ISO/IEC 27001）、理想（隐私政策）文档面向"合规承诺"只能观测治理承诺，不能观测技术实现
开放"披露"（漏洞专栏/赏金）奇瑞（漏洞专栏）、Tesla（Bugcrowd，见 30.7）文档面向"安全问题上报"可观测披露成熟度，不直接反映技术实现

本报告判断（推测，非事实）："越靠近车辆物理安全，越不公开" 这一模式在信源档案 §7 与 docs/16-authz-60-cn-oem.md §16.3.4 的缺口聚类中已被观察——合规层（易公开）、平台层（较易公开）的公开度高于硬件层、通信层（基本不公开）。检验方法：对同一主体，分别检索其"信任中心/隐私政策"与"mTLS/密码套件文档"，比较两者的可获取性。

30.3 对比度 2：鉴权与授权形态（核心维度）

这是 AC-6 最重要的对比维度，也是全报告授权章节（第 3 部分）的横向收敛点。本节把被取证主体的鉴权形态并置，只在"可观测形态"层面比较。

  • 分叉 F-2（披露动因的分叉）：本报告判断（推测，非事实）：市场驱动路线下，公开开发者文档是建立生态的资产（故 Tesla/Mercedes 文档充分）；合规驱动路线下，披露常被视作合规义务而非获客手段（故可能"满足最低披露即止"）。可检验推断：观察 2026-01-01（GB 44495/44496 实施）之后，国内是否出现类似 developer.tesla.com 的完整公开授权文档。检验方法：定期检索国内车企域名的接口文档。
  • 分叉 F-3（时间点的分叉）：中国侧有一个硬节点 2026-01-01，其合规压力是集中式的；国际侧（R155/R156 的生效时间表）本次未取证，故本报告不比较时间点，只指出"中国侧的强制时间点已明确、国际侧的本次未取证"这一可见度事实。

30.8 国内外差异的归因分析

本节把前文的差异读作现象，并为每个现象给出一条可能成因（推测）、一条可检验的推断、一条检验方法。全部归因均为 [合理推测]，与事实物理分段。共 7 个归因维度（超出 AC-6 的"至少 5 个"要求）。

归因 1：监管时序

  • 现象：中国侧 GB 44495/44496 于 2026-01-01 实施（硬节点，[A]）；国际侧 UN R155/R156 的时间表本次未取证。
  • 可能成因（推测）：中国的强制国标体系倾向"设一个集中的强制时间点"以快速确立基线；国际型式认证体系的时间表本次未能核验。
  • 可检验的推断（推测，非事实）：中国的合规压力在 2025–2026 年呈集中释放，可能在 2026 年后推动一批授权/OTA 基线文档的公开。
  • 检验方法：跟踪 2026-01-01 前后国内车企官网/开放平台的文档更新频率。

归因 2：数据主权

  • 现象：中国侧制度核心是"境内存储 + 出境评估"（[A]）；国际侧（欧盟）核心是"可携/可访问"（Data Act，[C]）。
  • 可能成因（推测）：数据主权制度的取向差异，塑造了授权层不同优先级的控制点（流向控制 vs 用户同意可视化）。
  • 可检验的推断（推测，非事实）：国内主体的授权审计日志应更强调"数据流向/地域"；国际主体的授权界面应更强调"用户同意管理"。
  • 检验方法：对比两侧 OAuth 同意界面与审计日志字段文档。

归因 3：生态成熟度

  • 现象：Tesla 有公开完整开发者文档与按用量计费生态（[A]）；国内有取证平台多为服务层/企业集成（[A]）。
  • 可能成因（推测）：第三方开发者生态的成熟度影响"公开文档"的激励强度——生态越需要开发者，越倾向公开接入文档。
  • 可检验的推断（推测，非事实）：国内若开放车控，可能先以"伙伴制/商务定向"起步，再逐步走向自助式公开文档。
  • 检验方法：观察国内车企开放平台的接入方式是否从"商务渠道"转向"自助注册"。

归因 4：商业模式

  • 现象：Tesla 车控开放按用量计费（[A]）；国内服务云平台以商务渠道对接（[A]）。
  • 可能成因（推测）：计费模式决定文档的"获客价值"——计费 API 的文档是获客漏斗的一部分，故公开度更高。
  • 可检验的推断（推测，非事实）：引入计费的国内平台可能逐步提升文档公开度。
  • 检验方法：观察国内平台服务目录是否引入"按用量/按订阅"的明码计费。

归因 5：手机生态依赖

  • 现象：数字钥匙与近场授权中，CCC 3.0 明确"跨 OS 生态"并依赖手机侧 SE 存密钥（[A]）；小米宣称"人车家全生态"但车云 API 细节未取证（[A]）。
  • 可能成因（推测）：手机生态（Apple/Google/Android 阵营 vs 国内手机厂商阵营）决定数字钥匙的凭证载体与信任锚选择，进而影响车厂在数字钥匙上的技术路线。
  • 可检验的推断（推测，非事实）：国内数字钥匙实现可能更倾向"国标参考架构（GB/T 44402.1）+ 本土手机生态"的组合。
  • 检验方法：跟踪 GB/T 44402 系列后续部分，以及国内车企数字钥匙官方技术白皮书。

归因 6：供应链结构

  • 现象：国际侧公开了 TEE/SE/HSM 的规范族与芯片生态站点存在（GlobalPlatform、EVITA、Infineon AURIX、NXP S32 等，[A]–[C]/[未验证]）；国内侧 TEE/SE/HSM 实现全部未取证。
  • 可能成因（推测）：芯片与安全元件的选型多为供应链内部信息，公开度天然低；不同供应链结构下，"可对外披露的安全元件"形态不同。
  • 可检验的推断（推测，非事实）：国内侧的安全元件信息更可能通过芯片厂 Design Win 公告、T-BOX 拆解或专利间接获得，而非车企自述。
  • 检验方法：检索芯片厂公开的汽车 Design Win 与安全元件产品公告；采用器件选型逆向（本次不做，属范围外）。

归因 7：人才与工程文化

  • 现象：Tesla/Mercedes 的文档呈现"开发者导向"（错误语义、变更策略、发现元数据齐备，[A]）；国内有取证平台的文档更偏"对接说明"（[A]）。
  • 可能成因（推测）：文档风格反映面向的受众——面向第三方开发者的团队更倾向"开发者体验优先"的文档；面向企业内部/合作方的团队更倾向"对接流程优先"的文档。
  • 可检验的推断（推测，非事实）：随着第三方生态需求上升，国内文档可能向"开发者体验优先"演进。
  • 检验方法：对比两侧文档是否包含错误语义表、变更日志、.well-known 发现元数据等"开发者体验"要素。

30.9 "与通用分层技术方案的差异"专节（对应调研目标第二条）

本节对应调研目标的第二条——把"通用分层技术方案"（docs/02-general-layered-security.md 的六层参考模型）与"本次取证到的落地实现"逐层对照，识别"通用方案应有的控制 / 已落地的控制 / 差异与缺口"。通用方案侧为规范层能力（[A]）；落地实现侧仅含本次取得一手文档的主体。逐层一个子节，节末一张小结表。

30.9.1 硬件安全层

  • 通用方案应有的控制（[A]）：密钥与证书的硬件保管（TEE/SE/HSM）、安全启动与可信启动链、密码算法基线（国际 ECC/AES 或国密 SM 系列）、车载 HSM 分级（EVITA Full/Medium/Light）。
  • 本次取证到的落地实现：
    • Tesla：虚拟密钥须为 prime256v1（P-256 ECDSA），公钥须托管于域名 /.well-known/appspecific/com.tesla.3p.public-key.pem 且长期可用，私钥绝不托管（[A]）；配对深链 https://tesla.com/_ak/<developer-domain.com>（[A]）。未见其 TEE/HSM 的一手文档。
    • Mercedes：未取得硬件根信任相关文档。
    • 国内侧：9 家全部未取得 TEE/SE/HSM 的一手来源（信源档案 §7.10 第 5 条）。
  • 差异与缺口：
    • 差异（事实）：通用方案的"TEE/HSM/安全启动"在已落地方案中几乎不可观测——Tesla 只公开了应用层密钥托管形态（虚拟密钥），未公开底层的 TEE/HSM。
    • 缺口（声明）：硬件层是全报告取证最薄的一层（呼应 docs/16-authz-60-cn-oem.md §16.3.4 的 C1 列取证率为 0）。这是披露缺口，不是能力缺口。

30.9.2 通信安全层

  • 通用方案应有的控制（[A]）：mTLS 双向证书车云链路、TLS 1.3（RFC 8446）、证书全生命周期（签发/轮换/吊销）、防重放（时间戳 RFC 3161 / nonce）、分段与信任边界。
  • 本次取证到的落地实现：
    • Tesla：授权端点与令牌端点分属不同主机（auth.tesla.com vs fleet-auth.prd.vn.cloud.tesla.com，[A]）；Fleet Telemetry 要求开发者用仓库内 tools/check_server_cert.sh 校验主机与 CA 兼容性（[A]）；授权 /authorize 支持 nonce（文档描述为"用于防重放的随机值"）与 state（"用于校验的随机值"）（[A]）。
    • Mercedes：未取得 mTLS/证书固定文档。
    • 国内侧：9 家全部未取得 mTLS/证书轮换的一手来源。
  • 差异与缺口：
    • 差异（事实）：通用方案的"mTLS 双向证书"在已落地文档中未直接出现——Tesla 公开的是OAuth + 虚拟密钥的授权层控制，其链路加密细节（是否 mTLS）未取证。
    • 缺口（声明）：通信层与硬件层同样基本不可观测（C2 列取证率为 0）。mTLS 是否被采用，本次对任何主体均无一手证据。

30.9.3 授权与访问控制层

  • 通用方案应有的控制（规范层，[A]）：OAuth 2.x 族（RFC 6749/6750/7636/8252/8705/9449/9396/8693…）、令牌生命周期治理（TTL/轮换/吊销）、资源级授权（RFC 9396 RAR）、发送方约束令牌（RFC 8705 mTLS 绑定 / RFC 9449 DPoP）。
  • 本次取证到的落地实现：
    • Tesla（[A]）：完整 authorization_code 流；12 个 scope；刷新令牌一次性 + 3 个月 + 24h 宽限；.well-known/openid-configuration 发布（对应 RFC 8414）；虚拟密钥的车端二次校验（车辆在执行命令前验证载荷签名）；granular_access.hide_private 的双层收窄（授权被授予但资源级策略进一步收窄，403）；vehicle_specs/vehicle_pricing_info 仅 Partner Token 可用且无需车主授权（授权控制例外）。
    • Mercedes（[A]）：Authorization Code Flow + Client Credentials Flow；mb: 命名空间 scope；expires_in 默认 3599 秒；刷新令牌一次性 + 轮换；HTTP Basic 客户端认证；要求客户端凭证存后端、不得暴露给客户端。
    • 国内侧：比亚迪（APIKey+x-Gateway-APIKey，[A]）、蔚来（app-id+secret，[A]）——均为非 OAuth 的服务层形态。
  • 差异与缺口：
    • 差异（事实）：授权层是全报告取证最厚的一层（这正是第 3 部分占用 300K+ 字符的原因）。通用方案的多数控制点在 Tesla 侧可观测到落地；Mercedes 侧部分可观测。
    • 差异（事实）：RFC 9396（RAR）与 RFC 9449（DPoP）在已落地文档中均未出现——通用方案里"资源级授权"与"发送方约束令牌"的规范能力超前于已落地的 scope 形态（Tesla 以 granular_access 自定义实现收窄，尚未采用 RAR）。
    • 缺口（声明）：国内 9 家在车控层授权上全部未取证。

30.9.4 应用与平台安全层

  • 通用方案应有的控制（[A]）：最小权限、服务身份、多租户隔离、密钥托管、影响范围控制（blast radius）、入侵检测与审计。
  • 本次取证到的落地实现：
    • Tesla（[A]）：影响范围控制的多个具体工程手段——B2B 自动添加虚拟密钥的条件为"已配对密钥少于 20 把"（密钥数量上限）、单台车辆最多向 5 个第三方应用推流、限流按账号按设备计（实时数据 60 次/分、唤醒 3 次/分、设备命令 30 次/分，同账号多应用共享限额）、计费超限会暂停 API 并移除 Fleet Telemetry 配置。
    • Mercedes（[A]）：明确"客户端凭证必须保存在后端服务器，应用不得向客户端暴露任何客户端凭证（client id、client secret、访问令牌）"。
    • 国内侧：蔚来的文档访问本身纳入授权控制（接口规范正文需"文档访问 token"，[A]）——这是一处平台治理的可观测实例。
  • 差异与缺口：

  2. 【事实型结论】 本次取得一手文档的三种鉴权形态分别为：APIKey/ESB（比亚迪）、App-ID+Secret（蔚来）、OAuth 授权码（Tesla/Mercedes）。前两者为应用身份型、身份对象为应用；后者为用户代理型、身份对象为车主/终端用户（30.3.1）。

  8. 【推测型结论】 两条路线的架构分叉（授权语义、披露动因）可能与"合规驱动"与"市场驱动"的起点差异相关——需以"是否出现类似 developer.tesla.com 的公开文档""同意界面字段差异"等可检验推断验证（30.5.2）。

30.12.1 本章完成了什么

本章按 AC-6 要求给出了 6 个维度的对比矩阵（证据可见度、鉴权与授权形态、硬件根信任与密码栈、监管驱动、开放生态位、披露治理）与 7 个维度的差异归因（监管时序、数据主权、生态成熟度、商业模式、手机生态依赖、供应链结构、人才与工程文化），另设"与通用分层技术方案的差异"专节逐层对照，并给出 12 条结论（8 条事实型、4 条推测型）与 17 项待补证清单。

30.12.2 本章的三条核心结论

  1. 【事实】 本次对比的最大变量是证据可见度，不是安全水平。Tesla/Mercedes 的文档充分、国内多家取证受限，是披露与可达性的产物；本章全程把"证据可见度"与"安全水平"分离，不据可见度给任何主体排序（30.0.2）。

  3. 【推测】 国内外差异的可能成因集中在制度起点（合规 vs 市场）、数据主权取向、生态与商业模式；这些均为可检验推断，须由后续 RFI 补证，本章不将其写成事实。
