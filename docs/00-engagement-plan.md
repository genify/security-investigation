## 1. 委托范围与验收标准冻结

本计划把委托方需求固化为可判定的验收标准（AC）。**AC 编号在全部工作流中通用**，任何交付物必须注明其覆盖的 AC 编号。

| AC | 验收标准（可判定） | 判定方式 |
|---|---|---|
| AC-1 | 报告含 6 个规定结构：概述 / 通用车云安全技术方案分析 / 国内新势力车企实践分析 / 国际新能源车企实践分析 / 对比与差异分析 / 总结与趋势 | 章节标题逐一核对 |
| AC-2 | **「授权与访问控制」章节 ≥ 300K 字符**（委托方原文"不得少于 300K"） | `wc -m` 统计该章节合并后字符数；同时记录字节数 |
| AC-3 | 覆盖 5 层分析框架：硬件安全 / 通信安全 / 授权与访问控制 / 应用与平台安全 / 其他（OTA、数据隐私、合规、供应链） | 每层至少 1 个专章，且授权层占比最大 |
| AC-4 | 国内 ≥ 9 家（蔚来、小鹏、理想、小米、零跑、华为鸿蒙智行、极氪、比亚迪、奇瑞）逐家拆解 | 每家有独立小节，含"方案 / 与通用方案的异同 / 证据等级" |
| AC-5 | 国际 ≥ 5 家（特斯拉、Rivian、大众、宝马、奔驰）逐家拆解 | 同上 |
| AC-6 | 国内外技术路线差异对比 | 至少 5 个维度的对比矩阵 + 差异归因 |
| AC-7 | 信源可靠、优先官方白皮书/专利/标准/公开演讲/权威媒体，并标注参考资料 | 每条事实带 `[A]/[B]/[C]` 等级 + URL（见 §3） |
| AC-8 | 区分公开信息与合理推测，不确定内容明确标注 | 存在「待补证清单」章节，且正文无未标注的推测 |
| AC-9 | 输出 Markdown 与 HTML 两种格式，**每一部分**均需两种格式 | 每个 `docs/*.md` 有对应 `docs/html/*.html` |
| AC-10 | HTML 为 **CARIAD 风格**（简洁、现代、科技感、清晰信息层级、适合技术报告阅读） | 使用确定性转换脚本 `md2cariad.py`；渲染断言见 §6 |
| AC-11 | 客观中立，不夸大或贬低任何车企 | 每家企业结论句不得含比较级贬损；缺证据一律写"未找到公开来源" |
| AC-12 | 技术深度与可读性并重 | 每章含架构图（ASCII/SVG）、表格、工程实现片段 |

**范围外（明确不做）**：
- 不做针对任何在售车型的漏洞测试、渗透、逆向或实车攻击。本委托为**公开信息调研**，不含主动测试。
- 不披露任何未修复漏洞（对齐行业披露伦理与各厂 SRC 规则，如 Tesla Bugcrowd 规则第 3 条）。
- 不臆造国内车企的密码算法/硬件实现细节。**缺证据即写缺证据。**

## 3. 证据分级与严重度分类标准（本委托的统一口径）

### 3.1 证据分级（每条事实必须带等级）

| 等级 | 定义 | 允许的表述措辞 |
|---|---|---|
| **[A] 一手** | 标准正文（openstd.samr.gov.cn / RFC Editor / 官方规范库）、OEM 官方开发者文档、官方白皮书、官方漏洞政策、官方年报 | "**文档明载**…" |
| **[B] 权威第三方** | 学术论文、检测认证机构、权威媒体、官方 SDK 仓库、行业联盟规范页 | "**据 …（第三方）**…" |
| **[C] 二手** | 自媒体、博客、论坛、聚合站 | "**有报道称**…（未经一手核实）" |
| **[未验证]** | 站点可达性已确认但正文未取到 | "**尚未取证**，URL 结构待复核" |
| **[合理推测]** | 由已知架构/规范推导 | "**本报告判断**…（推测，非事实）" |
| **未找到公开来源** | 已检索指定对象无果 | "该方向**未找到公开来源**，不等同于能力缺失" |

### 3.2 写作红线（违反即退回重写）

1. **禁止**把 [合理推测] 写成陈述句事实。
2. **禁止**为凑字数引入无关内容、重复段落、无信息量的填充。所有体量来自真实的对照表、机制剖析、工程片段、逐家拆解。
3. **禁止**编造 URL、标准编号、条款号、数字、时间。本委托已有一次因工具额度导致的取证受限（见信源档案 §0），**不得用记忆填补缺口**。
4. **禁止**把"未找到公开来源"反向表述为"该企业不具备"。这是中立性红线（AC-11）。
5. 引用单篇原文不得超过该节篇幅的 5%（避免搬运替代分析）。

### 3.3 发现严重度分类（沿用本次审计口径，用于"风险"类结论）

| 等级 | 判据（满足其一） | 报告中的处理 |
|---|---|---|
| **Critical** | 授权链可被绕过，导致任意车辆车控/位置被未授权访问；或根密钥可被远程提取 | 必须在"对比与差异"中作为行业级风险单列，并给出缓解控制 |
| **High** | 单一应用/单一凭证被攻破可横向影响同账号其他车辆或平台其他租户 | 单列控制建议（最小权限、令牌绑定） |
| **Medium** | 令牌生命周期管理不当（长效令牌、无轮换、无吊销联动）导致影响范围扩大 | 归入"工程实现参考"的控制清单 |
| **Low** | 文档与可观测性缺失、日志不含授权决策依据 | 归入合规映射章节 |
| **Informational** | 架构观察、行业趋势判断 | 归入"总结与趋势" |

**CSO 判定示例（本次已判定，写入报告）**：
- 特斯拉 Fleet API 中 `vehicle_specs` / `vehicle_pricing_info` **仅 Partner Token 可用且对任意车辆无需车主授权** → 归为 **High**（授权控制例外，需在报告中显式标注为"退出逐车主同意模型"的路径，并建议以契约与审计补偿）。
- `granular_access.hide_private` 在已授予 `vehicle_location` 的前提下仍拒绝位置字段（403） → 归为 **Informational→正面控制案例**（**双层授权控制**的良好实践，建议其他车企对标）。

## 4. 分析方法论（本委托采用）

1. **分层解构法**：把"车云安全"解构为 5 层（硬件根信任 → 通信 → 授权 → 应用与平台 → 生命周期/合规），逐层定义"可信基、威胁面、控制点、可验证证据"。
2. **授权优先权重法**：因委托方明确要求授权章节 ≥300K，授权层按"机制 → 令牌 → 资源级 → 威胁 → 工程 → 逐家实践 → 合规 → 参考表"8 个切面展开，其余层用总纲厚度。
3. **控制-威胁映射法**：每条控制点反向标记其缓解的威胁（STRIDE / OWASP API Security Top 10 / GB 44495 要求域），确保不出现"无威胁来源的控制"与"无控制的威胁"。
4. **证据分层写作法**：先写"文档明载"部分，再写"合理推测"部分，两者物理分段。读者可一眼区分。
5. **对标基准法**：以 **Tesla Fleet API**（公开文档最完整）与 **Mercedes-Benz Developer Platform** 为"已公开实现的标尺"，其他车企与通用方案均与此对标，量化差异（scope 命名空间、令牌 TTL、轮换策略、同意模型、密钥模型）。
6. **缺口显式化**：所有"未找到公开来源"汇总为待补证清单，并给出补证动作（RFI / 沙箱申请 / 代理重跑 / 采购白皮书）。

### 6.3 提交纪律

- 分支 `main` 为共享分支，**多 Agent 并行提交**。提交前先 `git log --oneline -3` 观察他人进度；**只 `git add` 自己拥有的文件**。
