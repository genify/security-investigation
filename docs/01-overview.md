## 01.0 本报告是什么、不是什么

在开始之前必须把边界钉死，因为车云安全这个题目极易被写成两份都不准确的文档：一份是厂商宣传语的汇编，一份是缺乏证据的猜测合集。本报告两者都不是。

**本报告是什么**

本报告是一份**基于公开信息、按统一证据分级写的车云安全技术方案调研**。它的分析对象是"技术方案"——即某一层用了什么机制、这个机制解决什么威胁、它在规范上如何定义、在已公开的实践中如何体现、还缺什么。它的产出是**可核对的架构描述与分析判断**，每条断言都带证据等级，每条推测都显式标注。

**本报告不是什么**

| 不是 | 原因 | 依据 |
|---|---|---|
| 实车渗透测试报告 | 本委托为公开信息调研，未对任何在售车型做主动测试、逆向或攻击 | 00-engagement-plan.md §1 范围外声明 |
| 漏洞披露文件 | 未披露任何未修复漏洞；对齐行业披露伦理与各厂 SRC 规则 | 同上；Tesla 赏金规则"未经批准不得公开披露已确认未修复漏洞" |
| 合规符合性认证结论 | 本次未取得多数标准正文，不给条款号、不下"合规/不合规"判定 | 本次取证限制（见 §01.5） |
| 厂商能力排名 | 证据密度在主体间极不均衡；"未找到公开来源"绝不等于"不具备该能力" | AC-11 中立性红线 |
| 完整的实现逆向 | 车端硬件、密码实现、供应链细节绝大多数厂商未公开 | 同上 |

**方法论声明（写入正文，影响全部结论的可信度断言）**：本次调研在检索工具额度耗尽、部分站点区域封锁的条件下完成，采用"权威 URL 直取 + 逐条标注证据等级"的方法，并把所有缺口显式化为待补证清单。**覆盖度的不均衡是本报告最重要的元事实**，读者必须带着它阅读每一章的对比结论。

## 01.1 委托背景与问题定义

### 01.1.1 背景陈述（委托方原文要点）

随着电动车网联化与智能化落地，越来越多车企在车内提供在线服务并开放更多车控能力。车云之间的安全因此被越来越重视。委托方要求：深入分析车云安全技术方案，并对国内外主要新能源车企在车云安全方面的**实践落地技术方案**做深度调研，分析其与通用分层技术方案的差异。

### 01.1.2 把背景转成可回答的技术问题

| 委托背景中的表述 | 转成的技术问题 | 本报告的回答位置 |
|---|---|---|
| "开放更多车控能力" | 车控能力通过什么接口暴露？授权粒度能细到什么程度？ | 11 章、13 章、16 章、17 章 |
| "车云之间的安全" | 车与云之间到底有几段链路？每段的信任根是什么？ | 02 章 §02.1、§02.3；11 章 §11.8 |
| "实践落地技术方案" | 有哪些可公开核对的实现？参数是什么？ | 16 章、17 章、20 章、21 章、19 章 §19.5 |
| "与通用分层技术方案的差异" | 通用方案应有什么控制？实际取证到了什么？差在哪？ | 02 章、30 章 §30.9 |
| "授权与访问控制"（重点要求） | 该切面必须展开到 ≥300K 字符 | 第 3 部分（10–19 章，合计已远超该下限） |

### 01.1.3 为什么"授权与访问控制"是这份委托的真正重心

委托方在输出要求里单列了一条硬指标：授权与访问控制部分的篇幅不得少于 300K。这不是篇幅偏好，而是一个技术判断的体现。原因是：**车云系统的链路安全（mTLS、TLS 1.3、证书）在今天已经是可工程化交付的成熟能力，而"某个调用者是否有权对这台车的这个能力做这个动作"才是真正会产生事故的地方。**

本报告在 14 章用结构化威胁模型论证了这一点，在 15 章给出了工程参考架构，在 16/17 章逐家核对了实现证据，在 18 章把它映射到合规与审计程序，在 19 章汇总成可查询的参考表。

## 01.4 调研方法与证据分级

### 01.4.1 六级证据分级（本报告统一口径）

| 等级 | 定义 | 允许的表述措辞 |
|---|---|---|
| **[A] 一手** | 标准正文（openstd.samr.gov.cn / RFC Editor / 官方规范库）、OEM 官方开发者文档、官方白皮书、官方漏洞政策、官方年报 | "**文档明载**…" |
| **[B] 权威第三方** | 学术论文、检测认证机构、权威媒体、官方 SDK 仓库、行业联盟规范页 | "**据 …（第三方）**…" |
| **[C] 二手** | 自媒体、博客、论坛、聚合站 | "**有报道称**…（未经一手核实）" |
| **[未验证]** | 站点可达性已确认但正文未取到 | "**尚未取证**，URL 结构待复核" |
| **[合理推测]** | 由已知架构/规范推导 | "**本报告判断**…（推测，非事实）" |
| **未找到公开来源** | 已检索指定对象无果 | "该方向**未找到公开来源**，不等同于能力缺失" |

### 01.4.2 四条写作红线（违反即退回重写）

1. 禁止把 [合理推测] 写成陈述句事实。
2. 禁止为凑字数引入无关内容、重复段落、无信息量的填充。所有体量来自真实的对照表、机制剖析、工程片段、逐家拆解。
3. 禁止编造 URL、标准编号、条款号、数字、时间。凡 `[未验证]` 者不得作为事实断言使用。
4. 禁止把"未找到公开来源"反向表述为"该企业不具备"。这是中立性红线（AC-11）。

### 01.4.3 分析方法（五法并用）

1. **分层解构法**：把车云安全解构为 5 层，逐层定义"可信基、威胁面、控制点、可验证证据"（02 章落地）。
2. **授权优先权重法**：授权层按"总论 → 协议族 → 令牌与密钥 → 资源级授权 → 威胁模型 → 工程实现 → 逐家实践 → 合规审计 → 参考表"10 个切面展开。
3. **控制-威胁映射法**：每条控制点反向标记其缓解的威胁，避免"无威胁来源的控制"与"无控制的威胁"（14 章 §14.2/§14.5、02 章 §02.7、18 章 §18.4 落地）。
4. **证据分层写作法**：先写"文档明载"部分，再写"合理推测"部分，两者物理分段，读者可一眼区分。
5. **对标基准法**：以 Tesla Fleet API（公开文档最完整）与 Mercedes-Benz Developer Platform 为"已公开实现的标尺"，量化差异（scope 命名空间、令牌 TTL、轮换策略、同意模型、密钥模型）。

## 01.5 取证条件与覆盖度偏置声明（必读）

本节的每一条都会削弱或限定后续章节的结论强度，因此不能略读。

### 01.5.1 本次取证的客观限制

| 限制 | 具体表现 | 对报告的影响 |
|---|---|---|
| 开放检索不可用 | 检索类工具全程返回额度不足；公开搜索引擎在本运行环境亦不可用（地理重定向、验证码、机器人墙） | 无法做开放网络发现，只能直取已知权威 URL；**证据密度向"文档公开可达"的主体倾斜** |
| 区域/网络封锁 | 部分车企官网与标准组织站点被边缘节点区域封锁或超时拦截 | 宝马、Rivian 的开发者文档本次不可得；部分国际标准正文未取到 |
| 平台侧拒绝服务 | 个别车企开放平台对全部请求返回 403 | 该平台鉴权机制、scope、令牌参数无法核实 |
| 文档需登录/JS 渲染 | 部分厂商文档站为 JS 空壳或需登录 | 正文不可取，只能记录"站点存在" |

### 01.5.2 覆盖度偏置的诚实表述

- **证据最厚**：Tesla（全部来自其官方开发者文档，[A]）、Mercedes-Benz（[A]）、以及中国国家标准全文公开系统（[A]）。
- **证据中等**：比亚迪（i迪桥平台接口级文档，[A]）、蔚来（Open NSC 文档，[A] 但内容陈旧）、小米（开发者平台与信任中心，[A]）。
- **证据薄弱或为零**：小鹏、理想、零跑、极氪、奇瑞、华为鸿蒙智行（车云授权与硬件方向均为"未找到公开来源"）；宝马、Rivian（被网络封锁）。

**因此**：本报告在对比章节（30 章）中把"证据可见度"与"安全水平"严格分离，只比较**可观测到的技术方案形态**，绝不比较**安全水平**。任何人试图从本报告的对比表推出"某企业更安全"的结论，都是对本报告方法的误用。

### 01.5.3 "未找到公开来源"的正确读法

> **未找到公开来源 ≠ 不具备该能力。** 它表示：在本次的检索条件与公开渠道下，没有取得可核验的一手材料。车云安全（尤其是车端硬件、密码实现、供应链）本身就是公开披露极少的领域，且中国车企的开放平台多以商务对接为入口，不对公众开放技术文档。

对每一个"未找到公开来源"的条目，本报告在 19 章 §19.11 缺口台账与各章待补证清单中给出了**补证动作**（RFI 问卷、商务申请沙箱、专利与招标检索、T-BOX 拆解、白皮书采购、标准正文获取）。

## 01.7 核心结论速览

以下 12 条是本报告在事实层最值得先读的结论。每条标注证据等级与承载章节；**不含推测**（推测型结论集中在 30/31 章并单独标注）。

| # | 结论（事实层） | 等级 | 章节 |
|---|---|---|---|
| F-1 | 授权层是车云安全中"规范最成熟、实现最不统一"的一层：OAuth 2.x 与其扩展已覆盖资源级授权、发送方约束、令牌交换、步进认证等全部关键需求 | [A] | 11 章、13 章 |
| F-2 | 以"可复制凭证"（Bearer 令牌）为核心的传统模型，在车控场景必须叠加发送方约束或车端验签才能把"令牌泄露"的后果限制住 | [A]+[合理推测] | 12 章 §12.3、17 章 §17.2.4 |

## 01.8 三个结构性判断（事实与推测分离）

以下三条是本报告认为对委托方决策最重要、但**包含推测成分**的判断。为遵守红线，此处把事实依据与推测结论物理分开陈述。

### 判断一：车云安全的短板已经不在链路，而在"授权决策的可撤销性与可归因性"

- **事实依据**：链路段所需的规范与工程手段完全成熟（TLS 1.3、X.509 PKI、OCSP、ACME 自动化轮换均有标准可依）；而授权侧出现了"授权被授予但资源仍被拒"（F-5）与"绕过逐车主同意"（F-6）并存的真实实现，且撤销链路必须贯穿到车端（虚拟密钥由车主在车辆界面删除、推流配置随 scope 撤销被移除）。
- **推测结论（本报告判断，推测）**：在多主体开放生态里，出现事故的位置大概率是"某个被授予的权限没有被及时、彻底地收回"，而不是"链路上被解密"。

### 判断二：国内与国际路线的分叉首先是"合规起点"的分叉，其次才是技术选型的分叉

- **事实依据**：中国的强制性与推荐性国标族已把平台防护、管理接口、异常行为检测、数据分析处理、数字钥匙参考架构分别固化成标准；国际侧则以型式认证体系（UN R155/R156）加 GDPR 与数据可携权立法驱动（后三者的正文本次未取证，仅名称与方向可用）。
- **推测结论（本报告判断，推测）**：两条路线会长期共存并产生互操作压力（尤其国密栈与国际 PKI 栈），但这属于"可工程化处理的差异"，不是能力差距。

### 判断三：本次调研最重要的产出之一是"缺口地图"，而不是"结论清单"

- **事实依据**：9 家国内车企在硬件与通信切面的官方一手证据为零；宝马与 Rivian 的开发者文档本次不可达；多数国际标准正文未取到。
- **推测结论（本报告判断，推测）**：任何基于本次证据的"技术路线优劣比较"都会受证据可见度污染，因此本报告的对比章节只做"形态比较"，并把"安全水平比较"留给后续通过 RFI 与沙箱实测补齐证据的工作包（31 章 §31.6）。

## 01.10 术语与阅读约定

| 术语 | 本报告用法 |
|---|---|
| 车云 | 车辆侧（车机/T-BOX/网关/ECU）与其后端云平台之间的通信与授权关系 |
| 授权（Authorization） | 判定"某主体能否对某资源执行某动作"的过程与机制；与"认证（Authentication，判定身份）"严格区分 |
| 资源级授权 | 授权粒度细化到单个资源实例（如某台 VIN 车辆）而非资源类型 |
| 同意（Consent） | 数据主体/车主对特定用途与范围的授权表示，是授权链的起点事实 |
| 令牌（Token） | 授权的可传递凭证；区分访问令牌、刷新令牌、授权码、设备码、客户端断言 |
| 发送方约束令牌 | 与持有者身份绑定、复制后不可用的令牌（mTLS 证书绑定、DPoP） |
| 撤销传播 | 撤销动作从授权服务器传导到最末端执行点（含车端）的完整链路 |
| 证据等级 | 见 §01.4.1 的六级口径 |
| 影响范围（Blast Radius） | 单一凭证/应用/服务被攻破后可波及的资产范围 |
