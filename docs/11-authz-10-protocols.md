## 11.0 本章方法与覆盖度声明

### 11.0.1 唯一事实底座与「不新增」纪律

本章全部事实性断言，均取自本仓库的 `docs/sources/source-dossier.md`（下称「信源档案」）。信源档案 §0 已声明本次调研的采集方法：**检索工具不可用**（`web_search` / `web_extract` 全程返回额度耗尽），采集方式退化为「直取已知权威 URL」（`terminal + curl` 与浏览器直连）。因此本章**不引入任何信源档案之外的 URL、标准编号、条款号、数字或日期**。

这条纪律在本章尤其重要，原因是协议族章节天然倾向于「凭记忆补全细节」：RFC 之间互相引用、条款编号密集、参数名繁多，一旦放开记忆，极易产生看似合理但不可核验的断言。本章的处理方式是：

1. 凡规范类断言，**只写信源档案 §2、§3 已逐条取证（HTTP 200）的 RFC 编号与主题**，并在正文中以 `RFC 编号 §节` 形式标注；对未取证到正文的条目（如 IEEE 1609.2、SCMS、ISO 15118），一律降级标注，绝不以「通行认知」冒充文档明载。
2. 凡车企实现类断言，**只写信源档案 §7 已取证页面的内容**，且明确指向具体页面；车企实现的全景拆解属 `16-authz-60-cn-oem.md` 与 `17-authz-70-global-oem.md`，本章仅在需要「已公开实现标尺」时引用其 `[A]` 条目。
3. 凡工程建议、参数取值、部署阈值，**一律标注为「本报告判断（推测，非事实）」**，与「文档明载」物理分段，读者可一眼区分。

## 11.1 协议选型全景图

### 11.1.1 为什么授权必须谈「协议族」而不是「一个协议」

车云授权场景的形态差异极大：车主在手机上让第三方 App 读一次电量、车机在无浏览器环境下登录账户、车企云代表车主去调第三方充电网络、车辆与云之间长期双向认证、充电桩在插枪瞬间完成身份与计费绑定、V2X 车队广播必须使用匿名假名证书、OTA 包必须能被车端离线验签……这些场景**没有一个协议能全部覆盖**。

因此工程上的正确姿势不是「选 OAuth」或「选 mTLS」，而是：**先按场景确定信任模型（谁是资源所有者、谁是客户端、谁是资源服务器、是否存在人机交互），再从规范族里选取与该信任模型匹配的协议组合**。选型错误的典型后果不是「不能用」，而是「能用的同时把一个设计上不该出现的攻击面引进来」——例如把 Bearer 令牌放在 URI 查询参数里、用内嵌 WebView 承载授权码流、或把长期静态 API Key 当作车控凭证。

### 11.1.2 场景 → 适用协议 → 规范依据 → 为什么（主选型表）

下表是本节的骨架。**「规范依据」列只列信源档案已取证条目**；「为什么」列说明该协议与场景信任模型的匹配机理，而非罗列特性。

### 11.1.3 选型的三个判据（本报告判断）

面对上表的 18 个场景，**本报告判断**（推测，非事实）可以归约为三个判据，用于在工程评审中快速定协议组合：

1. **是否存在「人类资源所有者」？** 若有，则必须使用能承载人机同意的流（授权码 / 设备授权），且同意界面必须展示授权粒度（对应 RFC 9396 的结构化描述与合规侧的知情同意要求）。若无，则走客户端凭证或 mTLS，把信任基放在客户端认证强度上。
2. **令牌是否可能被复制？** Bearer 令牌在规范语义上就是「持有即有权」。若链路经过不信任的中间件、或被复制后可用性会造成不可接受后果，则必须升级为发送方约束令牌（RFC 8705 证书绑定或 RFC 9449 DPoP）。
3. **授权决策是否需要「物理在场」？** 数字钥匙是唯一以物理在场为信任基的场景，因此它不通过云颁发短期令牌，而是把长期凭证（密钥）预置到安全元件，由近距信道（BLE/UWB/NFC）触发本地验证。

这三条判据并非规范条文，而是本章为后续 `13`/`14`/`15` 号文件提供的分类坐标。**读者应将其理解为分析工具，而非标准要求。**

## 11.2 OAuth 2.x 核心与演进

### 11.2.1 RFC 6749 四类授权（+ 刷新）在车云场景的映射

RFC 6749 定义了四种授权许可类型（grant type）与刷新令牌机制。`draft-ietf-oauth-v2-1-16` 在演进方向上对其中两类做了废弃处理（信源档案 §2.1 照录为「强制 PKCE、废弃隐式流与密码模式」）。下表给出**逐类的车云映射：适用性 → 风险 → 替代方案**。

| 授权类型 | 规范出处 | 车云适用性 | 主要风险 | 替代/加固方案 |
|---|---|---|---|---|
| 授权码 authorization_code | RFC 6749 | **高**。车主授权第三方、车主登录车企 App 的主路径 | 授权码被拦截后重放换码（公共客户端尤其严重） | 强制 PKCE（RFC 7636）+ `state` 校验 + 精确 `redirect_uri` 匹配；OAuth 2.1 已将其列为强制 |
| 隐式 implicit | RFC 6749 | **低**（`draft-ietf-oauth-v2-1-16` 已废弃） | 令牌经前端信道（URL fragment）直接暴露，无法绑定客户端，易被历史记录/Referer/日志泄露 | 一律改为授权码 + PKCE；车机 WebView 场景尤其不应使用 |
| 资源所有者密码 password | RFC 6749 | **低**（`draft-ietf-oauth-v2-1-16` 已废弃） | 客户端直接接触车主账号密码，破坏「凭证不离开授权服务器」的原则；无法表达细粒度同意 | 改为设备授权流（RFC 8628）或授权码 + 系统浏览器 |
| 客户端凭证 client_credentials | RFC 6749 §4.4 | **中-高**。车机自身鉴权、服务间调用、车队批量管理 | 信任全部押在客户端认证上；若用静态 secret，泄露即可无差别调用 | 叠加 mTLS（RFC 8705）、客户端断言（RFC 7523）、短 TTL、按资源结构化授权（RFC 9396） |
| 刷新令牌 refresh_token | RFC 6749 §6 | **高**。所有需要「免重复登录」的场景 | 刷新令牌寿命长，一旦泄露可长期续命 | 一次性使用 + 轮换（Tesla 文档明载其刷新令牌 single use 且 3 个月过期 `[A]`）；OAuth 2.1 要求刷新令牌须为发送方约束或轮换 |
| 设备授权 device_code | RFC 8628 | **高**。车机/受限 UI/无浏览器 | user_code 可被社工；轮询接口暴露为穷举面 | 短 `expires_in` + `interval` + `slow_down`；见 11.2.6 |
| 断言授权 JWT bearer | RFC 7523 | **中-高**。服务账号在无用户在场时代表组织 | 断言重放窗口；错误信任 `aud` 会导致跨服务冒用 | 短有效期 + `jti` 去重 + 严格 `aud` 校验 |
| 令牌交换 token exchange | RFC 8693 | **高**。车企云代理第三方访问车辆 | 主体/代理混淆，审计链断裂 | 显式 `subject_token` + `actor_token`；见 11.2.7 |

#### 11.2.1.1 逐类「适用性 / 风险 / 替代」的展开

**授权码流（authorization_code）——车云的主干**。它的核心价值是：**车主的凭证只在授权服务器端输入一次，第三方客户端从头到尾只见到「授权码」与「令牌」，见不到密码**。这正是信源档案 §7.2 记录的 Mercedes-Benz 文档所要求的形态：文档明载客户端凭证必须保存在后端服务器，应用**不得**向客户端暴露任何客户端凭证（client id、client secret、访问令牌）`[A]`。同一原则在 Tesla 文档中的体现是：第三方令牌使用 OAuth `authorization_code` 授权流代表车主行事 `[A]`。

车云场景的特殊之处在于客户端的「形态」比常规 Web 更杂：手机 App（公共客户端）、车机（受限 UI）、车企后端（机密客户端）、第三方服务（机密客户端）都会参与。同一套授权码流必须覆盖这四种形态，而它们能安全保存 `client_secret` 的能力完全不同——这正是公共客户端必须叠加 PKCE 的原因（见 11.2.3）。

**隐式流——规范上已废弃，工程上仍有残留**。隐式流的历史动机是「纯前端 SPA 无法安全保存 secret」，于是把令牌直接经 URL fragment 返回。结果是令牌进入浏览器历史、可能被 Referer 泄露、无法绑定客户端，且没有任何换码环节可插入 PKCE。`draft-ietf-oauth-v2-1-16` 已废弃隐式流（信源档案 §2.1），替代路径是「授权码 + PKCE」，此时 SPA 不需要 secret，PKCE 的 `code_verifier` 由浏览器端生成并保存。

**密码模式——规范上已废弃**。密码模式的根本问题是它把「客户端」与「资源所有者凭证」直接对接，客户端能看见并可能留存车主密码。对于车云，这等于让第三方 App 或车机固件持有车主账号密码，一旦客户端被逆向或固件被提取，攻击者即获得车主全量账户权限。替代路径是设备授权流（车机）或授权码 + 系统浏览器（手机）。

**客户端凭证——车机制造商最常误用的类型**。它本身没错，错在把它当成「万能后端鉴权」。车机作为客户端访问云服务、服务间互调、车队批量操作都适合它；但如果客户端认证只有静态 secret，那么任何能读出固件里 secret 的人都能冒充任意车辆。加固的规范路径清晰：mTLS 客户端认证（RFC 8705）把「持有 secret」升级为「持有客户端私钥并完成 TLS 双向握手」。

**刷新令牌——车云风险的集中地**。刷新令牌的寿命通常远长于访问令牌；信源档案 §7.1 记录 Tesla 文档明载其刷新令牌**一次性使用（single use only）且在 3 个月后过期**，且最近一次使用的刷新令牌在 **24 小时内仍有效**（宽限期，用于覆盖「应用未能持久化轮换后令牌」的失败场景）`[A]`；信源档案 §7.2 记录 Mercedes-Benz 刷新令牌同样**一次性使用**，授权服务器返回新的访问令牌与新的刷新令牌 `[A]`。这两个 `[A]` 事实合起来说明：**主流车企的公开实现已经在用「轮换 + 一次性」削弱刷新令牌泄露的长期价值**。OAuth 2.1 草案把「刷新令牌必须发送方约束或轮换」列为强制性变更（信源档案 §2.1），与这些实现方向一致。

**设备授权流——车机场景的规范答案**，见 11.2.6。

**断言授权与令牌交换**——见 11.2.7。

#### 11.2.1.2 一个必须澄清的概念边界

RFC 6749 的四类「授权许可」与 RFC 6750 的「令牌使用方式」是两个正交维度：前者决定「令牌怎么被拿到」，后者决定「令牌怎么被携带」。此外 RFC 8705 / RFC 9449 决定「令牌是否被绑定到持有者」。工程评审中常见的混淆是把它们当同一层讨论，从而得出「用了授权码流就安全」的错误结论——**授权码流只解决「拿令牌的过程」，不解决「令牌拿到后被复制怎么办」**。后者必须由令牌绑定机制（11.3）回答。

### 11.2.2 授权码流完整报文级时序（含每步参数与可攻击位置）

#### 11.2.2.1 参与方与信道

授权码流的参与方有四个：**资源所有者**（车主，操作浏览器）、**客户端**（第三方 App 或车企 App）、**授权服务器**（车企 SSO）、**资源服务器**（车企业务 API）。规范上还有第五个隐含角色：**用户代理**（浏览器）。RFC 8252 要求原生 App 使用**外部用户代理**（系统浏览器），禁止内嵌 WebView（信源档案 §2.1 照录）——这一点在 11.2.5 展开。

      |                    |<----(4)登录页/同意页(展示scope)----------------|                    |
      |--(5)认证+同意----->|                        |                        |                    |
      |                    |--(6)POST 同意--------->|                        |                    |

#### 11.2.2.4 `state` 与 `nonce` 的语义差异（易混淆点）

工程上最常见的错误是把 `state` 与 `nonce` 当同一件事，或只实现其一。**它们的防护目标不同**：

- `state` 防的是**授权请求/回调的 CSRF 与错绑**：它绑定「本次授权请求」与「本次回调」，保证回调是客户端自己发起的那次授权的响应。Tesla 文档将其描述为「用于校验的随机值」`[A]`。
- `nonce` 防的是**ID 令牌重放**：它随 OIDC 认证请求发出、随 `id_token` 回传，客户端校验二者一致，保证这个 `id_token` 是本次认证的产物而非旧令牌被重放。Tesla 文档将其描述为「用于防重放的随机值」`[A]`。

因此「有 `state` 无 `nonce`」在纯 OAuth 2.0 下可以接受，但在使用 `id_token` 的 OIDC 场景下是**不完整**的。**本报告判断**（推测，非事实）：车云场景中，凡第三方应用以 `openid` scope 获取 `id_token` 并据此识别车主身份的集成，应同时实现 `state` 与 `nonce`。

### 11.2.3 RFC 7636 PKCE：授权码拦截的规范对策

#### 11.2.3.1 问题陈述

授权码流对机密客户端是安全的：换码时需要 `client_secret`，拦截到 code 的攻击者换不到令牌。但对**公共客户端**（手机 App、SPA、车机应用）而言，没有 secret 可依赖——任何能截获 code 的人都能换到令牌。PKCE（Proof Key for Code Exchange，RFC 7636）就是为了堵住这个口子。

#### 11.2.3.2 机制：`code_verifier` 与 `code_challenge`

流程分两步：

1. **授权请求前**：客户端生成一个高熵随机串 `code_verifier`（规范要求其长度在 43–128 个字符之间，字符集受约束），保存在本地；再按选定方法计算 `code_challenge`，连同 `code_challenge_method` 一起放进授权请求。
2. **换码时**：客户端把原始 `code_verifier` 放进 `/token` 请求；授权服务器按同样方法重算 challenge，与授权请求阶段保存的值比对，一致才签发令牌。

两种方法：

| 方法 | 计算方式 | 规范地位（本章判断依据） |
|---|---|---|
| `plain` | `code_challenge = code_verifier` | 规范中保留但**不建议**用于公共客户端；对能读取授权请求的攻击者无防护价值 |
| `S256` | `code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))` | **应强制**。挑战值单向派生自 verifier，攻击者即使截获 challenge 也无法反推 verifier |

```
 客户端本地                     授权服务器
   |                              |
   | 生成 code_verifier (43..128字符)
   | 计算 code_challenge = S256(code_verifier)
   |--GET /authorize?...&code_challenge=...&code_challenge_method=S256--->|
   |                              | 保存 challenge 与本次授权会话绑定
   |<----302 redirect_uri?code=...&state=...------------------------------|
   |--POST /token  code=...&code_verifier=...&client_id=...-------------->|
   |                              | 重算 S256(code_verifier) 与保存值比对
   |<----access_token-----------------------------------------------------|
```

#### 11.2.3.3 为什么 PKCE 能挡住授权码拦截

关键在**「授权请求阶段暴露的值不能反推出换码阶段需要的值」**。攻击者可能截获授权请求中的 `code_challenge`，也可能截获回调中的 `code`，但他拿不到 `code_verifier`——因为 verifier 只在客户端本地保存、仅在换码请求中沿 TLS 发给授权服务器。于是攻击者持有 code 却无法通过 challenge 校验。

进一步地，PKCE 还把授权码「绑定」到了最初发起授权请求的那个客户端实例：即使 code 被窃取，窃取者也没有对应的 verifier。**本报告判断**（推测，非事实）：这条性质对车云场景的价值在于，第三方应用即使以公共客户端形态运行，也能获得与机密客户端接近的换码安全强度。

#### 11.2.3.4 对车云集成的工程含义

- **S256 应作为唯一允许的方法**（OAuth 2.1 草案已把强制 PKCE 列为变更，见 11.2.4）；`plain` 应仅在无法做 SHA-256 的极端受限设备上用，且需单独风险评估。
- **`code_verifier` 的存储位置**：在手机端应置于平台安全存储；在车机端若无法安全存储，应重新评估是否适合授权码流（可能更适合设备授权流，见 11.2.6）。
- **`code_verifier` 生命周期**：与授权请求会话同寿命，换码完成或会话过期即销毁。
- **与 `state` 的关系**：PKCE 不替代 `state`——PKCE 防「code 被拦截换码」，`state` 防「code 被注入错绑」，两者正交，应同时实现。

### 11.2.4 OAuth 2.1 草案 `draft-ietf-oauth-v2-1-16` 的强制性变更与迁移影响

信源档案 §2.1 照录该草案的要点为「**强制 PKCE、废弃隐式流与密码模式、Bearer 令牌最小化**」。下表逐条给出「变更 → 对存量车云集成的迁移影响」。**注意：草案仍在演进，具体条号可能变化，本章不引用条号，只引用档案照录的主题。**

| # | 变更（档案照录） | 变更实质 | 对存量车云集成的迁移影响 |
|---|---|---|---|
| 1 | 强制 PKCE | 所有客户端（含机密客户端）在授权码流中都必须使用 PKCE | 车企 SSO 需在校验逻辑上把 `code_challenge` 改为必备；已有第三方集成若不发 challenge 会在切换后直接报错。**迁移动作**：SSO 侧提供灰度开关，第三方 SDK 强制升级 |
| 2 | 废弃隐式流 | 不再允许 `response_type=token`（前端直返令牌） | 任何仍在用纯前端拿令牌的车主门户/车机网页需改为「授权码 + PKCE」；这类集成往往历史久、缺乏维护，是最大迁移风险来源 |
| 3 | 废弃密码模式 | 不再允许 `grant_type=password` | 车机/旧版 App 若把车主账号密码直接交给客户端换令牌，必须重写为设备授权流或授权码流；**这通常是改动量最大的一条** |
| 4 | 刷新令牌必须发送方约束或轮换 | 刷新令牌要么绑定持有者（mTLS/DPoP），要么每次使用即轮换 | 已有「长效刷新令牌 + 不轮换」的实现需迁移。Tesla（一次性 + 3 个月 + 24h 宽限）与 Mercedes（一次性 + 返回新刷新令牌）的公开实现已符合方向 `[A]`；未采用轮换的集成需补轮换逻辑与「轮换失败」的容错（参考 Tesla 的 24 小时宽限设计） |
| 5 | 重定向 URI 精确匹配 | `redirect_uri` 必须精确匹配注册值，禁止通配/前缀 | 依赖宽松匹配的多环境（测试/生产共用客户端）集成需为每个回调地址单独注册；移动端的自定义 scheme 更需逐条登记 |
| 6 | Bearer 令牌最小化 | 减少 Bearer 令牌在 UI、日志、URI 中的暴露面 | 需要全面审计令牌的日志埋点、错误上报、前端存储；把「令牌出现在 URL」的实现全部改为头传递（RFC 6750 §2.1） |

**本报告判断**（推测，非事实）：对车企而言，OAuth 2.1 迁移的成本主要不在协议本身，而在**存量第三方生态**——第三方开发者分散、更新节奏不受车企控制。因此务实的迁移策略是「新客户端强制 2.1、存量客户端设并行期并给出明确废弃时间表」，而不是一次性切换。

### 11.2.5 RFC 8252 原生 App 要求与车机推论

#### 11.2.5.1 规范要求

信源档案 §2.1 照录 RFC 8252 的核心要求：**原生 App 必须使用系统浏览器/外部用户代理，禁止内嵌 WebView**。

这条要求背后是三个具体风险：

1. **宿主进程可读**：内嵌 WebView 由 App 自身进程控制，App 能读取 URL（含 code）、注入脚本、截取输入。外部系统浏览器则运行在独立进程与独立信任域中。
2. **凭证输入被伪造界面窃取**：内嵌 WebView 可被伪装成「车企登录页」，实际是钓鱼页面，车主无法通过地址栏/锁标识分辨。
3. **会话与 SSO 状态污染**：内嵌 WebView 的 Cookie 存储通常不共享系统 SSO，反而可能残留或错误共享，导致会话错绑。

#### 11.2.5.2 对车机的推论（本报告判断）

车机（IVI）不是手机，它有两个特殊约束：屏幕/输入受限；且它既是「客户端」（访问云服务），也可能被要求承载「车主登录」界面以授权第三方。**本报告判断**（推测，非事实）：

- 车机**不应**用内嵌 WebView 承载车主登录以获取第三方授权——这既违反 RFC 8252 的精神，也把车机固件拉进「接触车主凭证」的信任域，扩大攻击面。
- 车机更合适的路径是 **RFC 8628 设备授权流**：车机只展示一个 `user_code`，车主在手机上完成认证与同意，车机仅轮询结果，全程不接触车主凭证。这是规范提供、且与车机形态天然匹配的方案。
- 若车机确实需要浏览器（如内嵌 Chromium 车机版），它**不应**被当作 RFC 8252 意义上的「外部用户代理」，因为它仍受车机固件控制。此时若必须用授权码流，应额外叠加 PKCE + 应用间回调验证，并接受其安全强度低于「系统浏览器 + 自定义 App」组合的事实。

### 11.2.6 RFC 8628 设备授权流：报文时序与轮询风险

#### 11.2.6.1 流程

```
 车机(设备客户端)              车主手机(浏览器)           授权服务器            资源服务器
   |                              |                        |                    |
   |--(1)POST /device_authorization  client_id/scope---->|                    |
   |<--(2)device_code,user_code,verification_uri,-------|                    |
   |      expires_in,interval                            |                    |
   |--(3)展示: 请访问 verification_uri 并输入 user_code->车主               |
   |                              |--(4)访问 verification_uri 认证+输入user_code->|
   |                              |<--(5)确认授权------------------------|     |
   |--(6)POST /token grant_type=urn:ietf:params:oauth:grant-type:device_code-->|
   |     device_code=...          |                        |                    |
   |<--(7)a)authorization_pending(继续轮询)               |                    |
   |     b)slow_down(降频)       |                        |                    |
   |     c)access_token(+refresh_token)                  |                    |
   |--(8)GET /api  Authorization: Bearer <access_token>------------------->|
   |<--(9)业务响应--------------------------------------------------------|
```

#### 11.2.6.2 关键参数与语义

| 参数 | 方向 | 语义与工程要点 |
|---|---|---|
| `device_code` | 服务器→设备 | 设备专用的长随机码，**仅设备持有**，用于轮询换码；不可暴露给用户 |
| `user_code` | 服务器→设备 | **人可读、人可输入**的短码（如 8 位分组），由车主在手机上输入；因此它是可被社工/肩窥/暴力猜测的目标 |
| `verification_uri` | 服务器→设备 | 车主完成授权的人机界面地址 |
| `expires_in` | 服务器→设备 | 整个设备授权的有效期；**过期后 device_code 与 user_code 同时作废** |
| `interval` | 服务器→设备 | 设备轮询 `/token` 的最小间隔；设备不得比它更快 |
| `authorization_pending` | 服务器→设备 | 「车主尚未完成」；设备应继续按 `interval` 轮询 |
| `slow_down` | 服务器→设备 | 「你轮询太快了」；设备**必须增大轮询间隔**（规范建议在 `interval` 基础上增加固定步长并持续累积），否则视为违约 |
| `access_denied` | 服务器→设备 | 车主拒绝授权；设备应停止轮询并放弃 |
| `expired_token` | 服务器→设备 | 授权会话已过期；设备应重新发起 |

#### 11.2.6.3 轮询穷举风险与边界

`user_code` 短且可读，天然是暴力猜测目标。风险面有三层：

1. **`user_code` 猜测**：攻击者若能高速请求 `verification_uri`，可能猜中某个正在等待的 user_code，从而把自己的设备授权挂到受害者会话上（或反向）。缓解：短 `expires_in`、限制单 IP/单会话尝试次数、把失败尝试计入风控、提高 user_code 熵（但受「人可读」约束）。
2. **设备码轮询接口滥用**：`/token` 在设备码流程中是「未认证的轮询端点」，若无限流可被用于枚举。缓解：`interval` + `slow_down` + 服务端限流与封禁。
3. **肩窥/社工**：`user_code` 显示在车机屏上，旁观者可读取并抢先授权到自己的账号。缓解：车机应提示不要泄露；服务器侧对「同一 user_code 被不同会话抢先确认」做告警。

**本报告判断**（推测，非事实）：对车云场景，设备授权流的合理参数取向是「**短有效期、较长轮询间隔、低频失败容忍**」——因为车主在车机上完成授权的窗口很窄，长有效期只会扩大猜测窗口而不提升可用性。

### 11.2.7 RFC 8693 令牌交换与 RFC 7523 客户端断言：两层代理与审计归属

#### 11.2.7.1 问题：车云里「谁在替谁做事」

典型车云链路是**两层代理**：

```
 车主 → 第三方服务(应用A) → 车企云(应用B) → 车辆/车辆数据API
```

- 第三方应用持有的是**代表车主**的令牌（subject = 车主）。
- 车企云在调内部资源服务器时，可能还需要一个**代表自己**的凭证（actor = 第三方服务 / 车企云）。
- 资源服务器最终要回答两个问题：**这次访问代表谁**（subject）、**通过谁发起的**（actor）。

如果没有显式的「主体/代理」分离，审计日志里只会留下「车企云调用了 API」，无法回答「这是代表哪个车主、经由哪个第三方」。

#### 11.2.7.2 RFC 8693 令牌交换的机制

RFC 8693 定义令牌交换：客户端拿一个令牌（`subject_token`）去换一个新令牌，并可附带 `actor_token` 表示「代理方」。签发的新令牌中会携带 `act`（actor）声明，通常以嵌套形式表达代理链。

```
 第三方服务                     车企云授权服务器              资源服务器
   |                                |                        |
   |--POST /token                  |                        |
   |  grant_type=urn:ietf:params:oauth:grant-type:token-exchange
   |  subject_token=<代表车主的令牌> |                        |
   |  subject_token_type=...        |                        |
   |  actor_token=<代表第三方的令牌>  |                        |
   |  audience=<车云内部资源>        |                        |
   |------------------------------->|                        |
   |<--新令牌(sub=车主, act=第三方)---|                        |
   |--GET /vehicle/...  Authorization: Bearer <新令牌>----->|
   |                                |   校验 sub/act/aud      |
   |<--业务响应------------------------------------------------|
```

| 概念 | 字段 | 语义 | 审计价值 |
|---|---|---|---|
| 主体 | `sub` | 资源所有者（车主） | 回答「这是谁的数据」 |
| 代理 | `act` | 代理方（第三方/车企云） | 回答「经由谁发起」 |
| 受众 | `aud` | 预期资源服务器 | 防止令牌被拿到别的服务复用 |
| 令牌类型 | `subject_token_type` / `actor_token_type` | 声明 token 的格式 | 防止类型混淆（把 id_token 当 access_token 用） |

#### 11.2.7.3 RFC 7523 客户端断言

RFC 7523 定义「用 JWT 做客户端认证或作为授权许可」。它解决的是**服务间无用户在场时的身份证明**：服务用自己的私钥签一个短时 JWT 作为 `client_assertion`，授权服务器验签并核对 `aud`/`exp`/`jti`。

对车云的意义有三点：

1. **消除共享密钥**：客户端不必持有对称 secret，改为持有私钥，泄露面收窄。
2. **可与 mTLS 叠加**：客户端断言 + mTLS 是「服务间零信任」的常见组合（见 11.8.B）。
3. **`jti` 去重是防重放的关键**：断言寿命极短，但若授权服务器不记录已用 `jti`，在有效窗口内仍可重放。**本报告判断**（推测，非事实）：车云内部的授权服务器应对客户端断言的 `jti` 做去重缓存，缓存时长 ≥ 断言有效期。

#### 11.2.7.4 审计归属的落地要求（本报告判断）

**本报告判断**（推测，非事实）：为了让 `act`/`sub` 链真正可用，车企云需要满足三个工程前提：其一，所有跨主体调用都必须经令牌交换而非「用自己的令牌裸调」；其二，资源服务器的日志必须同时记录 `sub` 与 `act`（并保留整个代理链而不只是最内层）；其三，令牌签发时即固定 `aud`，禁止「一个令牌打多个服务」。

### 11.2.8 RFC 9396 RAR 与 RFC 9635 GNAP：结构化授权 vs 可协商授权

#### 11.2.8.1 RFC 9396 Rich Authorization Requests（富授权请求）

传统 OAuth 的 `scope` 是裸字符串（如 `vehicle_cmds`），无法表达「对哪辆车、哪个字段、多长时间、什么条件下」。RAR 引入 `authorization_details` 结构化对象，用于描述细粒度授权请求。

| 维度 | 裸 `scope` | `authorization_details`（RAR） |
|---|---|---|
| 表达力 | 字符串标签，语义靠文档约定 | 结构化对象，可含资源类型、资源 ID、动作、约束 |
| 同意界面 | 只能展示标签 | 可据结构渲染「允许访问您的 X 车辆的 Y」 |
| 审计 | 只能记 scope 字符串 | 可记结构化授权决策依据 |
| 车云映射 | Mercedes 的 `mb:vehicle:mbdata:fuelstatus` 命名空间式 scope `[A]` | 可表达「仅 A 车、仅位置字段、仅 24 小时」 |

信源档案 §2.1 将 RFC 9396 标注为「**车控场景『资源级授权』的规范依据**」。本章与之呼应，具体资源级模型在 `13-authz-30-resource-authz.md` 展开。

**与车企实践对照**：信源档案 §7.1 记录 Tesla 已实现「双层控制」的雏形——即使授予了 `vehicle_location`，带 `granular_access.hide_private=true` 的共享车辆仍拿不到任何位置、且无法流式传输位置字段 `[A]`。这是「**授权先被授予、再被资源级策略进一步收窄**」的实例，与 RAR「用结构化描述表达约束」的方向一致，但 Tesla 的实现形态是否使用 `authorization_details` 在本次已读页面中**未见明载**，故不作断言。

#### 11.2.8.2 RFC 9635 GNAP

信源档案 §2.1 将 RFC 9635（Grant Negotiation and Authorization Protocol，Standards Track，2024-10）标注为「**下一代授权协议，面向『细粒度 + 可协商』授权，代表演进方向**」。

与 OAuth 2.x 的**设计差异**（本报告基于规范定位的对照分析，非逐条条款引用）：

| 维度 | OAuth 2.x（含 RAR） | GNAP |
|---|---|---|
| 授权获取 | 客户端通过 `grant_type` 静态枚举的流获取令牌 | 客户端与授权服务器**协商**访问权限 |
| 令牌模型 | 相对固定的 access/refresh 二元结构 | 一个 grant 可产出多种、结构化的访问权限 |
| 交互协商 | 基本单向请求 | 强调客户端与 AS 的多轮交互与「key proof」 |
| 演进定位 | 成熟生态、广泛部署 | 前沿方向，生态仍在建设 |

**本报告判断**（推测，非事实）：GNAP 在车云场景的潜在价值在于「协商」二字——车控授权往往需要「先申请宽泛权限、再按实际情况收窄」或「资源所有者与请求方来回调整」，OAuth 的静态 grant_type 模型对这种多轮协商支持较弱。但考虑到生态成熟度，短期车云落地仍以 OAuth 2.1 + RAR 为主，GNAP 更适合作为架构演进观察项（与 `13` 号文件互引）。

## 11.3 令牌传输与绑定协议

### 11.3.1 RFC 6750 Bearer 令牌的三种传输位置

RFC 6750 规定 Bearer 令牌可在三种位置携带（信源档案 §2.1 照录为「Bearer 令牌在 HTTP 中的使用、`WWW-Authenticate` 错误语义」）。三种位置的**安全强度差异极大**，这是车云集成中最常被低估的一点。

| # | 位置 | 形态 | 规范态度 | 主要风险 | 车云适用性 |
|---|---|---|---|---|---|
| 1 | `Authorization` 请求头 | `Authorization: Bearer <token>` | 推荐 | 令牌可能进入服务端访问日志（可通过日志脱敏缓解） | **应作为唯一默认选择**；Tesla 文档明载使用该头 `[A]` |
| 2 | 表单体参数 | `access_token=<token>`（`application/x-www-form-urlencoded`） | 仅在无法使用头时用 | 令牌进入请求体日志、代理缓存、WAF 记录 | 仅限确实无法设置头的受限设备；车机应避免 |
| 3 | URI 查询参数 | `?access_token=<token>` | **不推荐**（规范明确弃用倾向） | 令牌进入浏览器历史、Referer 头、中间代理日志、CDN 日志、截图与分享链接 | **不应用于车云任何链路** |

#### 11.3.1.1 为什么 URI 查询参数最危险

URI 会被「记录在很多与安全无关的地方」：访问日志、代理日志、CDN 缓存键、浏览器历史、书签、错误上报、截图。Bearer 令牌是「持有即有权」的凭证，任何一处泄露即等价于凭证泄露，且**泄露点往往不在授权体系的监控范围内**。规范因此对查询参数位置采取抑制态度（信源档案 §2.1 概括为「Bearer 令牌最小化」，OAuth 2.1 亦朝此方向）。

#### 11.3.1.2 错误语义与 `WWW-Authenticate`

RFC 6750 还规定了资源服务器在令牌无效/权限不足时的响应语义（`WWW-Authenticate` 头携带错误码，如令牌缺失、过期、scope 不足等）。对车云的工程意义在于：**客户端据此可以区分「该刷新令牌」与「该重新授权」**，从而避免「一遇 401 就无限重试」。信源档案 §7.1 记录 Tesla 的刷新失败会返回 `401 login_required`（两种触发场景：刷新令牌过期/被挤出，或用户已重置密码）`[A]`——这是「用错误语义驱动客户端状态机」的已公开实现实例。

### 11.3.2 RFC 8705 mTLS 与证书绑定令牌

#### 11.3.2.1 两个能力

RFC 8705 提供两个相互独立但常配套使用的能力：

1. **mTLS 客户端认证**：客户端在 TLS 握手中出示客户端证书，授权服务器据此认证客户端（替代/加强 `client_secret`）。
2. **证书绑定访问令牌**：签发令牌时，把令牌绑定到客户端证书，令牌中记录绑定信息；后续使用该令牌时，资源服务器校验「出示令牌的 TLS 连接所使用的证书」与令牌绑定值是否一致。

信源档案 §2.1 将其概括为「mTLS 客户端认证 + 证书绑定令牌，即『持有的令牌不可被复制盗用』」，并标注为「**车云链路最关键的授权规范**」。

#### 11.3.2.2 `cnf` 绑定结构

绑定信息通过令牌中的 `cnf`（confirmation）声明承载。对 mTLS 场景，绑定的是客户端证书的指纹（规范使用 `x5t#S256`，即证书的 SHA-256 指纹的 base64url 编码）。

```
 授权服务器                                资源服务器
   |                                          |
   | 签发令牌时写入:                           |
   |   cnf: { "x5t#S256": "<客户端证书SHA-256指纹>" }
   |                                          |
   |                                          | 收到请求:
   |                                          |  1) TLS 握手已获得对端客户端证书
   |                                          |  2) 计算其 SHA-256 指纹
   |                                          |  3) 与令牌 cnf.x5t#S256 比对
   |                                          |  4) 不一致 → 拒绝
```

**关键性质**：攻击者即使截获令牌字符串，若无对应客户端私钥，就在 TLS 握手中出示不了匹配的证书，绑定校验必然失败。这就是「不可被复制盗用」的机理。

#### 11.3.2.3 与 TLS 会话的关系

绑定的是**客户端证书**，不是某条 TLS 会话。因此同一客户端私钥可在不同会话、不同连接中复用（HTTP/2 多路复用、连接池重连都不影响绑定有效性）——只要每次连接都出示同一证书。**本报告判断**（推测，非事实）：这使 RFC 8705 比「会话级绑定」更适配车云高频、长连接、连接复用的形态。

#### 11.3.2.4 车云双向证书场景的部署要求（本报告判断）

**本报告判断**（推测，非事实）——以下为工程建议，非任何车企的文档明载事实：

- 客户端证书应由车企自建 PKI 或受信 CA 签发，**车端私钥应存放于安全元件/TEE**（信源档案 §4 列出 GlobalPlatform TEE、Secure Element 分类、FIPS 140-3 等条目，属 `[A]` 规范类；但**车企是否实际采用，本章不得断言**）。
- 证书吊销必须实时可达（OCSP/CRL，见 11.6.4），否则「吊销的车端证书」仍能通过 mTLS。
- 绑定校验要做到「令牌的 `cnf` 与当前连接证书一致」，而非「连接证书可信即可」——后者会让任何持有合法证书的客户端都能使用他人的绑定令牌。
- 需配套短周期证书与自动化轮换（RFC 8555 ACME），否则长期证书的吊销与更新会成为运维瓶颈。

### 11.3.3 RFC 9449 DPoP：发送方约束令牌

#### 11.3.3.1 与 mTLS 的定位差异

mTLS 绑定需要「客户端有证书 + TLS 双向握手」，在**没有客户端证书的场景**（如公共客户端、浏览器内的 SPA）无法使用。DPoP（Demonstrating Proof of Possession，RFC 9449）提供了另一条路：用「客户端持有的密钥对」证明请求来自令牌合法持有者，而不依赖 TLS 客户端证书。

信源档案 §2.1 照录其要点为「发送方约束令牌，`DPoP` 头 + JWK 指纹绑定」，标注 `[A]`。

#### 11.3.3.2 机制

1. **客户端生成密钥对**：客户端本地生成一个非对称密钥对（如 ECDSA），私钥不出本地。
2. **换码时声明公钥**：客户端在令牌请求中携带证明，授权服务器把签发令牌绑定到该公钥的指纹（`jkt`，JWK SHA-256 thumbprint）。
3. **每次请求携带 `DPoP` 头**：客户端为每个请求构造一个 DPoP 证明（一个用私钥签名的 JWT），放入 `DPoP` 头；该 JWT 含请求方法、URL、`jti`、`iat` 等。
4. **资源服务器校验**：验签 DPoP 证明 → 提取其公钥指纹 `jkt` → 与令牌绑定的 `jkt` 比对 → 校验请求方法/URL 与证明一致 → 校验 `jti` 未重放。

```
 客户端(持有私钥K)                         授权服务器
   | 生成密钥对 (私钥K 不出本地)              |
   |--POST /token + DPoP 证明(签名含公钥)---->|
   |<--access_token (cnf/jkt = JWK指纹(K))----|
   |
   |                                           资源服务器
   |--GET /api  Authorization: DPoP <token>    |
   |   DPoP: <本请求的签名证明(jti,iat,htm,htu)>->
   |                                          | 1) 验 DPoP 证明签名
   |                                          | 2) jkt(证明公钥) == 令牌绑定 jkt ?
   |                                          | 3) htm/htu 与真实请求一致 ?
   |                                          | 4) jti 未见过 ?
   |<--业务响应--------------------------------|
```

#### 11.3.3.3 `jkt` 绑定与「证明中包含请求参数」的价值

DPoP 比 mTLS 多一层保护：证明里包含 `htm`（HTTP 方法）与 `htu`（HTTP URI）。因此一个为 `GET /vehicle/status` 签的证明**不能被拿去签发** `POST /vehicle/unlock`——即使攻击者窃取了某次请求的 DPoP 证明。**本报告判断**（推测，非事实）：这一性质对车控场景价值显著，因为车控接口的「读」与「写」风险等级差异极大，把证明绑定到具体方法/URL 可以显著抬高「重放一个读请求的证明去触发写操作」的门槛。

#### 11.3.3.4 nonce 挑战与重放窗口

RFC 9449 支持授权服务器/资源服务器下发 **nonce 挑战**：服务器可以要求客户端在下一个 DPoP 证明中包含服务器提供的 nonce，从而进一步压缩重放窗口与绑定证明的新鲜度。配合 `jti` 去重，构成「时间 + 唯一性」双重防重放。

**本报告判断**（推测，非事实）：车云场景中，nonce 挑战会增加一次往返（客户端需先收到挑战再重发请求），对高频遥测上报不友好；更务实的做法是「对读接口用 `jti` 去重 + 短证明有效期，对车控写接口叠加 nonce 挑战」。具体阈值属设计建议，需与 `15-authz-50-engineering.md` 的工程方案协同确定。

### 11.3.4 三种令牌携带形态的防重放强度与工程成本对照

下表对「裸 Bearer + 头传递」「mTLS 证书绑定令牌（RFC 8705）」「DPoP 发送方约束令牌（RFC 9449）」做全维度对照。**评分为本章分析标注（本报告判断），非规范条款。**

| 维度 | 裸 Bearer（RFC 6750 头） | mTLS 证书绑定（RFC 8705） | DPoP（RFC 9449） |
|---|---|---|---|
| 令牌被复制后可用性 | **可用**（持有即有权） | 不可用（无对应私钥无法完成握手） | 不可用（无法伪造证明） |
| 防重放机理 | 无（依赖短 TTL） | 证书持有证明（握手级） | 每请求签名 + `jti` + 可选 nonce |
| 是否绑定请求方法/URL | 否 | 否 | **是**（`htm`/`htu` 在证明内） |
| 是否需客户端证书 | 否 | **是** | 否 |
| 是否需双向 TLS | 否 | **是** | 否（普通 TLS 即可） |
| 公共客户端可用性 | 可用 | 通常不可用（无证书） | **可用** |
| 每次请求的额外开销 | 无 | 无（握手期完成） | 一次签名与验签 |
| 服务端校验复杂度 | 低 | 中（需取值证书指纹比对） | 中-高（验签 + jti 去重 + 可选的 nonce 管理） |
| 密钥/凭证轮换难度 | 低（换 secret 即可，但影响面大） | 中（证书签发与吊销链路） | 中（客户端密钥轮换 + 令牌重绑） |
| 与内省（RFC 7662）的配合 | 可 | 可 | 可 |
| 对离线/弱网车端的友好度 | 高 | 中（握手成本高，弱网易失败） | 中（每请求签名，弱网无明显额外往返） |
| 车云推荐度（本报告判断） | 基线，不单独使用 | 车-云长期信道首选 | 第三方 App / 无客户端证书场景首选 |

> 表注：本表「车云推荐度」为**本报告判断**（推测，非事实）。信源档案 §2.1 仅将 RFC 8705 标注为「车云链路最关键的授权规范」；对 DPoP 未作车云适用性评价。因此 DPoP 在车云的实际采用情况**本次未找到公开来源**，不得据本表推断某车企已采用。

## 11.4 OIDC 与身份层

### 11.4.1 认证与授权的分离

OAuth 2.0 的原始定位是**授权**（access delegation），不是**认证**（identity）。把 OAuth 的访问令牌当「登录凭证」用是一个经典的反模式：访问令牌的受众是资源服务器，其语义是「可以做什么」，而不是「你是谁」。

OpenID Connect（OIDC Core 1.0，信源档案 §2.1 标注为「`id_token`、UserInfo、认证与授权分离」）在 OAuth 之上补了身份层：新增 `openid` scope、`id_token`（一个签名的 JWT，含认证事件信息）与 UserInfo 端点。这一分离对车云尤其重要，因为车云的资源服务器需要做的是「校验这个令牌能否访问这辆车的数据」，而不是「从令牌里猜车主是谁」。

### 11.4.2 `id_token` 与 UserInfo

| 元素 | 载体 | 用途 | 车云注意点 |
|---|---|---|---|
| `id_token` | 签名的 JWT | 断言「认证发生了什么」（签发者、受众、认证时间、`nonce`） | **受众是客户端**，不是资源服务器；不得拿去调 API |
| UserInfo | 端点返回 | 返回用户属性（姓名、邮箱等） | 属个人数据，须按最小必要与同意范围约束访问 |
| `openid` scope | 授权请求参数 | 触发 OIDC 行为 | 信源档案 §7.2 记录 Mercedes 明载 `openid` scope 为获得有效令牌所必需 `[A]` |

**证据对照**：信源档案 §7.2 记录 Mercedes 令牌响应示例 JSON 含 `access_token`、`refresh_token`、`id_token` `[A]`，且文档明载 `openid` scope 为获得有效令牌所必需、`offline_access` 为获得刷新令牌所必需 `[A]`。信源档案 §7.1 记录 Tesla 的 scope 清单含 `openid`（描述为「Sign in with Tesla」，允许车主用 Tesla 凭证登录第三方应用）与 `offline_access`（获取刷新令牌以免重复登录）`[A]`。这两家公开文档共同支撑一个结论：**`openid` + `offline_access` 已成为车云第三方授权的通用最小 scope 组合**。

### 11.4.3 一个高风险反模式：把 `id_token` 当访问令牌用

若资源服务器接受 `id_token` 作为访问凭证，则攻击者可以从任意一个自己的 OIDC 客户端拿到一个「合法签发但受众不是该资源服务器」的 `id_token` 去调 API，导致越权。**规范上的防线是 `aud`/`iss` 校验**；`15-authz-50-engineering.md` 会从工程侧展开。这里只强调原则：**`id_token` 只用于客户端确认认证结果，访问令牌只用于访问资源，两者不可互换**。

### 11.4.4 Discovery：`/.well-known` 的两种路径

信源档案 §2.1 列出两条发现路径：

| 规范 | 发现地址形态 | 内容 |
|---|---|---|
| RFC 8414 OAuth 2.0 Authorization Server Metadata | `/.well-known/oauth-authorization-server` | 授权端点、令牌端点、支持的 `grant_types`、`code_challenge_methods`、签名算法等 |
| OIDC Discovery 1.0 | `/.well-known/openid-configuration` | OIDC 相关元数据（含 `issuer`、`jwks_uri`、UserInfo 端点等） |

**证据对照**：信源档案 §7.1 记录 Tesla 的授权服务器元数据发布在 `https://fleet-auth.prd.vn.cloud.tesla.com/oauth2/v3/thirdparty/.well-known/openid-configuration` `[A]`——这是一个 `[A]` 级实例，说明车企云的 OAuth/OIDC 元数据确实通过 `.well-known` 暴露，对应 RFC 8414 / OIDC Discovery。

#### 11.4.4.1 对客户端配置安全的意义

Discovery 的价值是「客户端不硬编码端点与算法」，从而避免配置漂移（例如授权服务器升级了签名算法，硬编码客户端却还在用旧算法）。但它同时引入新的风险面：

1. **元数据被篡改**：若客户端对 `.well-known` 的获取不经严格 TLS 校验，或信任锚被替换，攻击者可用伪造元数据把客户端引向自己的授权服务器。缓解：元数据必须经 TLS 获取（RFC 8446）+ `issuer` 必须与预期一致 + 关键客户端可固定信任锚。
2. **`issuer` 混淆**：客户端必须校验 `issuer` 与令牌 `iss` 一致，防止不同类型/环境（沙箱与生产）的元数据混用。
3. **降级攻击**：若元数据声明支持多种算法，客户端应只接受白名单内的强算法（如拒绝 `none`）。

**本报告判断**（推测，非事实）：车云场景中，`iss`/`issuer` 的严格校验应作为**上线阻断项**——因为车企通常同时运行生产与测试环境，且第三方开发者极易把测试环境配置带入生产。

## 11.5 强认证：FIDO2 / WebAuthn 与步进认证

### 11.5.1 FIDO2 / WebAuthn 在车云中的两个位置

信源档案 §2.1 列出 W3C WebAuthn Level 2（`[A]`）与 FIDO Alliance 规范（`[B]`）。在车云场景中，强认证设备（手机的安全芯片、车机的生物识别）有两个明确位置：

1. **车主身份确认（登录/再认证）**：用抗钓鱼的凭证替代密码，降低凭证被窃取后「冒充车主登录车企 App」的风险。WebAuthn 的凭证绑定到具体的源（origin），因此能抵御钓鱼站点的凭证转发——这是密码与短信验证码做不到的。
2. **高风险车控二次认证**：解锁、远程启动、添加/移除驾驶员等动作，风险显著高于「读电量」。可要求在该动作前完成一次强认证。

**证据边界**：信源档案未记录任何车企在车控二次认证中使用 WebAuthn 的公开文档。因此本节讨论的是**规范能力与设计推论**，不是「某车企已采用」的事实。凡涉及具体实现，一律标注推测。

### 11.5.2 与 RFC 9470 步进认证的配合

RFC 9470（OAuth 2.0 Step Up Authentication Challenge Protocol，信源档案 §2.1 标注为「`acr`/`amr` 步进认证挑战」）定义了「资源服务器要求更高认证强度」的挑战协议：当访问某资源需要更高保证级别时，资源服务器返回挑战，客户端据此回到授权服务器完成更强的认证，再重试请求。

```
 客户端                       资源服务器              授权服务器
   |                              |                       |
   |--GET /vehicle/unlock-------->|                       |
   |<--401 需要更高认证(acr 要求)--|                       |
   |--携带更高 acr 的授权请求----------------------------->|
   |<--完成强认证(WebAuthn/FIDO2)--- 新令牌(acr 已提升)----|
   |--GET /vehicle/unlock (新令牌)->|                       |
   |<--业务响应---------------------|                       |
```

**本报告判断**（推测，非事实）：把 WebAuthn 与 RFC 9470 组合，可以得到一个「分级车控授权」的设计——

| 车控动作类别 | 建议认证要求（设计建议值，非事实） | 依据 |
|---|---|---|
| 读状态（电量、胎压、里程） | 普通访问令牌即可 | 默认 `acr` |
| 定位/行车轨迹 | 普通令牌 + 资源级策略（参考 Tesla `hide_private` 双层控制 `[A]`） | Tesla 已公开实现实例 |
| 解锁/上锁 | 步进认证（要求较高 `acr`） | RFC 9470 |
| 远程启动/添加驾驶员/虚拟密钥配对 | 步进认证 + 强认证设备（WebAuthn/FIDO2） | RFC 9470 + WebAuthn L2 |

> 上表右列「依据」中，Tesla 一行为 `[A]` 事实（信源档案 §7.1 明载 `granular_access.hide_private=true` 的车辆即使被授予 `vehicle_location` 也拿不到位置，返回 403）；其余各行均为**本报告判断**（推测，非事实），是规范能力与风险等级的推导，不构成对任何车企实现的描述。

### 11.5.3 抗钓鱼为何对车云特别重要

**本报告判断**（推测，非事实）：车云的凭证一旦被窃，攻击者获得的不只是「数据」，而可能是「对实体车辆的操控能力」。这与普通 SaaS 的「账号被盗」后果不在同一量级。因此「抗钓鱼」在车云的价值高于一般互联网场景：密码 + 一次性验证码可被钓鱼代理（实时转发）绕过，而 WebAuthn 的凭证绑定到源、且私钥不出认证器，因此实时钓鱼代理拿不到可用于其他源的凭证。

## 11.6 车端特有协议面

前五节讨论的是「通用互联网授权协议族」在车云场景的映射。本节转向**只在车端出现、或形态被车端显著改变**的四类协议面：数字钥匙、V2X、充电与能源、服务间通信。这四类的共同点是：**授权主体不再是「云端的一个账号」，而是「一个物理实体 + 一段物理在场」**。

### 11.6.1 数字钥匙：近场授权的三通道模型

#### 11.6.1.1 CCC Digital Key Release 3.0 的模型（`[A]`）

信源档案 §5 记录：CCC Digital Key Release 3.0 发布公告（2021-04-21）**新增 BLE + UWB 实现被动无钥匙进入与启动，NFC 保留为强制备用方案，密钥存储于 Secure Element**，来源为 Car Connectivity Consortium（`[A]`）。信源档案 §5 另记录 CCC Digital Key 主页面（**跨 OS 生态、认证计划**，`[A]`），以及 CCC Digital Key Release 3 v1.1 规范向公众开放（`[B]`）。

由这些 `[A]`/`[B]` 事实可归纳出数字钥匙授权的三个关键设计选择（**归纳本身为本报告分析，非规范原文**）：

| 设计选择 | 内容 | 为什么这样设计（本报告判断，推测） |
|---|---|---|
| 三通道并行 | BLE + UWB 实现被动进入与启动；NFC 作为强制备用 | 三通道覆盖不同可用性条件：BLE 功耗低、UWB 可精确测距、NFC 无电/无网亦可用 |
| 密钥存于安全元件 | 密钥不落普通 OS 存储 | 数字钥匙是长期凭证，一旦被提取即等价于「复制一把车钥匙」，必须防提取 |
| 强制备用通道 | NFC 是「强制」而非可选 | 避免钥匙在主通道故障/手机没电时完全不可用 |

#### 11.6.1.2 UWB 与 relay 攻击：为什么需要测距

传统无钥匙进入（RKE/PEPS）依靠射频信号强度判断钥匙是否在车附近，这一判断可被 **relay 攻击**（中继攻击）欺骗：攻击者用一对收发器把车与钥匙之间的信号「拉长」，让车以为钥匙就在身边。**本报告判断**（推测，非事实）：UWB 的价值在于它能做**精确测距**（而不仅是信号强度），使「钥匙是否真的在物理距离内」成为可测量的事实，从而把 relay 攻击的门槛从「转发信号」抬高到「必须在测距上欺骗」。

**证据边界**：信源档案 §5 记录 CCC 与 FiRa Consortium 就 UWB 技术合作（`[B]`），FiRa Core 2.0（2023-11）、3.0（2025-01）、4.0（2025-12）规范与认证（均为 `[B]`，新闻稿页面）。IEEE 802.15.4z（UWB 物理层增强）在信源档案 §5 标注为 `[未验证]`（未取得可核验官方 URL）。因此**本节不给出任何 UWB 测距的具体参数、消息名或安全机制名**——凡超出「测距用于抗 relay」这一体系性描述的细节，本章一律不作断言。

#### 11.6.1.3 FiRa 规范演进（`[B]`）

信源档案 §5 记录三条 FiRa 新闻稿条目，均为 `[B]`：

| FiRa 2.0 技术规范 | 2023-11 | 据 FiRa 新闻稿（第三方），规范版本发布 |
| FiRa Core 3.0 规范与认证 | 2025-01 | 据 FiRa 新闻稿（第三方），规范与认证计划发布 |

**本章的严谨边界**：本次取证只确认了该标准的**编号、名称、发布/实施日期与标题所表达的定位**（「参考架构」）；信源档案未记录其正文内容。因此本章**不给出**该标准定义的角色名、接口名、协议名或密钥层级——任何此类细节都需要正文取证，属待补证项（见 11.10）。

#### 11.6.1.5 两条钥匙交付路径：手机厂商钱包 vs 车企 App

数字钥匙的「钥匙」如何从车企交付到用户设备上，存在两条不同的路径。**本节对两者的安全差异分析为「本报告判断」（推测，非事实）**，因为信源档案记录的是 CCC 的跨 OS 生态定位（`[A]`）与国标参考架构的存在（`[A]`），并未记录任何具体手机厂商或车企的钥匙交付实现文档。

| 对比维度 | 路径一：手机厂商钱包（推测分析） | 路径二：车企 App（推测分析） |
|---|---|---|
| 钥匙载体 | 手机厂商钱包应用内的数字钥匙 | 车企自有 App 内的数字钥匙 |
| 跨平台性 | 受限于厂商生态（CCC 定位为跨 OS，见 `[A]`） | 车企自控，可跨平台 |
| 安全元件访问 | 由手机厂商控制 SE 访问路径 | 需通过平台提供的 SE 接口 |
| 车企可见性 | 车企对钥匙生命周期可见性较低 | 车企对钥匙生命周期完全自控 |
| 信任链长度 | 更长（车企云 → 手机厂商 → SE） | 较短（车企云 → App → SE） |
| 用户更换手机 | 依赖厂商账号迁移能力 | 依赖车企账号迁移能力 |
| 车企侧控制力 | 弱（受平台规则约束） | 强 |

**本报告判断**（推测，非事实）：

1. 路径一的**优势是「钥匙与设备强绑定、用户摩擦低」**，代价是**车企必须把钥匙生命周期的一部分控制权让渡给手机厂商**，且信任链更长、可观测性更差。
2. 路径二的**优势是车企自控**，代价是**必须自行解决 SE 访问、密钥迁移、丢失手机后的吊销**等全部工程问题，且用户需安装并保持车企 App。
3. 两条路径都面临同一个根本问题：**数字钥匙是长期凭证，一旦泄露即等价于钥匙被复制**。因此无论哪条路径，**吊销能力（远程废钥匙）与「丢失设备的即时失活」**都是必要的控制点。

**中立性声明**：上述对比是基于「信任链长度与控制权归属」的一般化分析，**不指向任何具体手机厂商或车企**。信源档案未记录任何一方的钥匙交付实现细节，因此本章不作「某厂商更安全」或「某车企更弱」的判断。

### 11.6.2 V2X 证书体系与车云业务证书不是同一体系

#### 11.6.2.1 可陈述的事实（`[A]`）

信源档案 §1.2 记录：**GB/T 45112-2024《基于 LTE 的车联网无线通信技术 安全证书管理系统技术要求》**——发布 2024-12-31，实施 2025-04-01，来源为国家标准全文公开系统（`[A]`），并标注为「**中国 C-V2X 证书管理体系，是『车-云-车』证书体系的国家级规范**」。

信源档案 §3 记录 IEEE 1609.2（WAVE 安全服务 / 证书格式）为 `[C]`（HTTP 200，正文未解析）；美国 SCMS（V2X 安全证书管理体系）为 `[未验证]`（未取得可核验官方 URL）。

#### 11.6.2.2 两类证书的目标差异（本报告判断）

**本报告判断**（推测，非事实）——这是一个**概念性区分**，用于解释为什么 V2X 证书与车云业务证书不能混为一谈：

| 维度 | V2X 证书（车-车/车-路广播） | 车云业务证书（车-云/服务-服务） |
|---|---|---|
| 主要目标 | 让接收方能验证「这条广播来自一个合法 V2X 参与者」，同时**保护发送者的长期身份不被链接** | 让云端能确认「这是哪辆车/哪个服务」，且**可追责** |
| 身份可见性 | 通常使用**短时、可轮换的临时身份**（行业常见的「假名证书」思路） | 长期稳定的设备/服务身份 |
| 追责方式 | 通过「由谁签发、能否被授权机构关联」的体系设计实现（行业常见的「注册证书 + 假名证书」分层思路） | 直接可识别主体 |
| 证书寿命 | 短（以支持轮换与不可链接性） | 相对长（或以短周期证书 + 自动轮换实现） |
| 通信对端 | 其他车辆/路侧设备 | 车企云 |

**为什么不能混用**：V2X 证书的**匿名性目标是刻意为之**——如果车-车广播使用可长期链接的身份证书，则任何人都能追踪某辆车的位置轨迹。而车云业务证书的**可追责性是刻意为之**——云端必须知道在操作哪辆车。**这两个目标在密码学与体系设计上是相互冲突的**，因此把两者合并成一个证书体系会同时破坏匿名性与可追责性。

**严谨边界**：信源档案**未记录**「假名证书」「注册证书」「短期证书」等具体角色名，也未记录 SCMS 的任何具体机制。因此上表右列使用的是「行业常见的思路」式表述，**不是对 GB/T 45112-2024 或 SCMS 正文的引用**。凡需要具体角色名、期限、字段的场景，均为待补证项（见 11.10）。

### 11.6.3 充电与能源授权

#### 11.6.3.1 OCPP（`[A]`）

信源档案 §6 记录：**OCPP 1.6 / 2.0.1 / 2.1**（充电侧协议族，授权与计量），来源为 Open Charge Alliance 协议页（`[A]`）。

从「授权」角度看，OCPP 解决的是**充电桩与充电网络管理云（CSMS）之间**的交互，其中与授权直接相关的环节是：

| 环节 | 内容（本章的体系性描述） | 为何与授权有关 |
|---|---|---|
| 桩身份认证 | 桩与 CSMS 之间的连接必须双向可验证 | 防止伪冒桩接入网络、防止桩被劫持后伪造计量 |
| 授权请求 | 桩在开始充电前向 CSMS 确认该用户/该令牌是否被授权 | 这是「充电会话授权」的决策点 |
| 计量上报 | 桩向 CSMS 上报电量/功率等计量数据 | **计费的数据基础**；计量一旦可被伪造，计费即可被操纵 |
| 远程控制 | CSMS 可远程启停/限功率 | 控制指令必须来自已授权实体 |

**证据边界**：信源档案只记录了 OCPP 的**协议族版本号存在**（1.6 / 2.0.1 / 2.1）与「授权与计量」这一主题，**未记录任何消息名、字段名或具体安全机制**。因此本章不给出任何 OCPP 消息或字段的具体名称。

#### 11.6.3.2 ISO 15118-2 / -20 与 Plug & Charge（`[未验证]`）

信源档案 §6 记录：**ISO 15118-2 / -20（Plug & Charge，TLS + contract certificate，充电授权的证书模型）**——来源 https://www.iso.org/standard/55366.html，标注为 **`[未验证]`（iso.org Cloudflare 拦截，标准号需复核）**。

**这是本章最需要克制的部分**。信源档案已在括号中写明了「TLS + contract certificate」这一主题性描述，但**明确标注为「未验证」**，且 ISO 标准号本身「需复核」。因此本章的处理是：

| 内容 | 本章是否陈述 |
|---|---|
| ISO 15118-2 / -20 存在且与 Plug & Charge 相关 | 可以（信源档案已记录该条目，并注明标准号需复核） |
| 其安全模型涉及 TLS 与合同证书（contract certificate）这一主题 | 可以，但必须标注 `[未验证]`，并说明「合同证书」的字段、层级、签发主体**本次未取证** |
| TLS 版本、证书字段、消息名、状态机、具体流程 | **不陈述**（超出证据） |

**本报告判断**（推测，非事实）：从体系定位看，Plug & Charge 的「合同证书」思路与车云业务证书的问题域相似——它要把「这辆车与这个充电合同绑定」变成可验证的命题，从而让「插枪即充、离场结算」成为可能。但这一判断是对主题的类推，**不是对 ISO 15118 正文的引用**。

#### 11.6.3.3 三条充电授权链的分离（本报告判断）

**本报告判断**（推测，非事实）：充电场景中存在三条彼此独立、但必须协同的信任链——

1. **桩-云链（OCPP）**：桩的身份与计量数据的可信。
2. **车-桩链（ISO 15118）**：车辆身份的验证与充电会话的建立。
3. **车-云链（OAuth 等）**：用户在车企 App/账户层面看到的充电记录与账单。

工程风险在于：**这三条链的授权决策如果不一致，就会出现「桩认为已授权、云认为未授权」的错配**，从而产生「免费充电」「重复计费」或「越权充电」类问题。因此**本报告判断**（推测，非事实）：充电授权的关键控制点是「会话标识的贯通」——即同一笔充电会话在三条链上必须能被关联到唯一标识，供审计与对账。

### 11.6.4 服务间通信：mTLS + 证书链 + OCSP + ACME

#### 11.6.4.1 规范族

信源档案 §3 记录四条与服务间通信直接相关的 `[A]` 规范：

| 规范 | 主题（档案照录） | 在服务间通信中的位置 |
|---|---|---|
| RFC 8446 | TLS 1.3（1-RTT 握手、0-RTT 重放风险、前向保密） | 信道基座 |
| RFC 5280 | X.509 PKI 证书与 CRL 规范（证书链、扩展、吊销列表） | 证书语义与链验证 |
| RFC 6960 | OCSP（在线证书状态查询） | 吊销状态的实时查询 |
| RFC 8555 | ACME（自动化证书签发/轮换，短周期证书的工程前提） | 无人工干预的证书生命周期 |

#### 11.6.4.2 四者如何构成一个闭环

```
   ACME(RFC 8555)                      X.509 PKI(RFC 5280)
   自动签发/续期 ──────────► 证书 ──────────► 证书链验证
        ▲                                              │
        │                                              ▼
   短周期(减少吊销压力)                        OCSP(RFC 6960)
        │                                      实时吊销状态
        │                                              │
        └──────────── 服务间 TLS 1.3(RFC 8446) ◄────────┘
                        mTLS 双向认证
```

**为什么短周期证书需要 ACME**：证书寿命越短，「吊销」的必要性越低（因为证书很快自然过期），但也意味着**续期频率极高**。若续期靠人工，运维规模不可承受；因此 RFC 8555 被信源档案标注为「短周期证书的工程前提」。**本报告判断**（推测，非事实）：车云场景中服务间证书若采用短周期（如按天级轮换），必须有 ACME 类自动化与产线化的失败告警，否则一次续期失败即导致服务间通信雪崩。

#### 11.6.4.3 0-RTT 的重放风险（易忽略点）

信源档案 §3 明确指出 RFC 8446 涉及「**0-RTT 重放风险**」。0-RTT 允许客户端在恢复会话时「第一轮就发数据」，代价是这部分数据**缺乏前向保密且可被重放**。**本报告判断**（推测，非事实）：车云的写操作（车控指令、OTA 触发、授权变更）**不应**使用 0-RTT 承载，因为重放一个车控指令的后果与重放一个读请求完全不同。0-RTT 只应用于幂等的读请求，且服务于非安全关键的延迟优化。

## 11.7 防重放与时间基准

### 11.7.1 为什么时间本身是一个安全组件

所有「短期令牌」「nonce 有效期」「防重放窗口」都依赖一个隐含前提：**各方对「现在」有大致一致的认知**。如果车端的时钟可以被任意设置，攻击者就可以把时钟拨到某个已签发令牌的有效期内，使「已过期」的令牌重新可用；反之，时钟大幅前移会让正常令牌立即失效，形成拒绝服务。

### 11.7.2 RFC 3161 可信时间戳

信源档案 §3 记录：**RFC 3161（2001）Time-Stamp Protocol（可信时间戳，防重放的时间基准）**，`[A]`。

RFC 3161 提供的是：**由一个受信时间戳机构（TSA）对一个数据摘要出具「该摘要在某时刻已存在」的签名证明**。它不告诉客户端「现在几点」，而是告诉验证方「这个数据在某时刻之前不存在」。

| 用途 | 机理 | 车云意义 |
|---|---|---|
| 证明「某事件发生在某时刻之前」 | TSA 对摘要签名，含时间 | 审计日志、OTA 包发布顺序、授权变更时间线 |
| 提供不可否认的时间基准 | TSA 的签名使时间不可被事后篡改 | 争议场景下的取证（如「授权是在事故前撤销的吗」） |
| 对抗时钟回拨 | 以 TSA 签名时间为准而非本地时钟 | 车端时钟不可信时的补救 |

**边界**：RFC 3161 需要**在线访问 TSA**，因此对离线车端并不总可用。**本报告判断**（推测，非事实）：车端离线场景下，时间戳更适合「事后补证」（如回传审计日志时批量取时间戳），而非「实时校验」。

### 11.7.3 nonce 生命周期与多源 nonce 的管理

车云场景中，nonce 会同时出现在多个机制里，管理上极易混乱。下表梳理本章涉及的全部 nonce 来源：

| nonce 来源 | 载体 | 防护目标 | 生命周期约束 |
|---|---|---|---|
| OAuth 授权请求 `nonce` | 授权请求 + `id_token` | `id_token` 重放 | 与本次认证会话同寿命，用后即弃 |
| OAuth `state` | 授权请求 + 回调 | 回调 CSRF / 错绑 | 与本次授权请求同寿命 |
| PKCE `code_verifier` / `code_challenge` | 授权请求 + `/token` | 授权码拦截换码 | 与授权请求会话同寿命 |
| DPoP 证明 `jti` | `DPoP` 头 | 证明重放 | 服务器需在证明有效期 + 时钟偏移窗口内去重 |
| DPoP 服务器 nonce | 挑战响应 + 后续证明 | 强制证明新鲜度 | 服务器控制，可短周期轮换 |
| 客户端断言 `jti`（RFC 7523） | `client_assertion` | 断言重放 | 服务器去重时长 ≥ 断言有效期 |
| 设备授权 `device_code` | 轮询请求 | 设备轮询会话标识 | 由 `expires_in` 界定 |

**本报告判断**（推测，非事实）：**这七类 nonce/jti 必须在工程上被明确区分，不能混用同一个存储或同一个「已见集合」**——因为它们的作用域（全局 / 单会话 / 单客户端）与生命周期完全不同。一个常见错误是「用一个全局去重表缓存所有 jti」，导致内存膨胀且无法按客户端隔离，攻击者可借其他客户端的 jti 耗尽去重表（拒绝服务）。

### 11.7.4 时钟偏移容忍

**本报告判断**（推测，非事实）——以下为工程建议，非规范条款：

- 令牌/证明校验必须允许一个**时钟偏移窗口**（客户端与服务器时间差），否则弱网、休眠唤醒、时区误配会导致大量「本应有效却报过期」的失败。
- 偏移窗口的大小是一个**权衡**：窗口越大，重放窗口越大；窗口越小，误拒越多。
- 关键控制是「**窗口内的同一 nonce/jti 只能被接受一次**」——即偏移容忍与去重必须同时存在，单独放宽偏移而不去重会显著扩大重放面。
- 车端时钟的同步（NTP/SNTP）本身不可完全信任，因为攻击者可劫持 NTP 或伪造响应。**本报告判断**（推测，非事实）：更稳健的方式是「以服务器下发的时间为权威 + 记录本地时钟与服务器时钟的漂移量 + 对超过漂移阈值的时钟跳变告警」。

### 11.7.5 车端离线/弱网场景的影响分析

车端与手机/服务器的最大差异是**网络不可靠**。这对授权协议的冲击集中在三处：

| 场景 | 冲击 | 本报告判断的应对方向（推测，非事实） |
|---|---|---|
| 长时间离线（地库、隧道、无信号区） | 无法刷新令牌、无法内省、无法查 OCSP | 使用较长寿命的本地可用凭证（如数字钥匙），但**离线可用性与吊销及时性天然冲突**；应把「离线可用的能力」限制在低风险动作 |
| 弱网（高丢包、高延迟） | TLS 握手反复失败、按 `interval` 轮询超时 | 避免每请求重握手；对轮询类流程放宽 `interval` 但服务端仍限流；避免 0-RTT 承载写操作 |
| 时钟漂移（车辆长期休眠） | 令牌「已过期」、时间戳校验失败 | 用较大偏移窗口 + 服务器权威时间 + 漂移告警 |
| 断连期间的事件 | 状态变更（如授权被撤销）在离线期间无法生效 | 恢复连接后必须做「状态对账」，且**以服务器状态为准**（信源档案 §7.1 记录 Tesla 的遥测配置在被撤销所需 scope 后会被**从车辆移除** `[A]`，这是「服务器状态权威」的已公开实现实例） |

**核心张力（本报告判断，推测，非事实）**：车云授权存在一个无法回避的张力——**「车必须在断网时仍能用钥匙」**与**「授权撤销必须立即生效」**在物理上不能同时满足。任何车云授权架构都必须显式地做出这个取舍，并把这个取舍写进威胁模型（交由 `14-authz-40-threat-model.md` 展开）。务实的方向是**按风险分级**：低风险动作允许离线凭证长期有效，高风险动作要求在线校验或近场强认证。

## 11.8 协议组合参考架构

本章前七节分离地讨论了各协议。工程上真正需要的是**可落地的组合**。本节给出三个组合：**A 最小可用**、**B 高保障**、**C 车端强绑定**。三者的关系是递进的：A 是任何车云集成的基线；B 在 A 之上叠加发送方约束与资源级授权；C 解决「不经过云的车端本地授权」。

> **重要声明**：本节三套组合是**本报告判断**（推测，非事实）——它们由信源档案中 `[A]` 级规范条目组合推导而来，**不是任何车企的文档明载架构**。信源档案 §7 中 Tesla 与 Mercedes 的实现细节仅作为「该能力在车云中已被公开实现过」的佐证，不代表其架构等同本节组合。

### 11.8.1 组合 A：最小可用

**定位**：面向「车主手机 App 授权第三方读取车辆数据」这一最基础场景，在不引入客户端证书与硬件依赖的前提下，达到可接受的安全基线。

**协议组成**：

| 层 | 协议/机制 | 规范依据 | 职责 |
|---|---|---|---|
| 授权流 | OAuth 2.1 授权码 + 强制 PKCE | RFC 6749、RFC 7636、`draft-ietf-oauth-v2-1-16` | 车主授权第三方代表其行事 |
| 无浏览器场景 | 设备授权流 | RFC 8628 | 车机等受限 UI |
| 令牌格式 | JWT 访问令牌 profile | RFC 9068 | 资源服务器本地可校验，减少回调 |
| 令牌寿命 | 短 TTL + 刷新令牌轮换 | RFC 6749 §6 | 限制泄露后的可用窗口 |
| 身份层 | OIDC | OIDC Core 1.0、OIDC Discovery 1.0 | 车主身份确认 |
| 发现 | 元数据 | RFC 8414 | 客户端不硬编码端点 |

**分层图**：

```
 ┌──────────────────────────────────────────────────────────────┐
 │ 车主手机 App（公共客户端）                                     │
 │  · 生成 code_verifier / state / nonce                          │
 │  · 用系统浏览器（RFC 8252），禁止内嵌 WebView                  │
 └───────────────┬──────────────────────────────────────────────┘
                 │ 授权码 + PKCE(S256)
 ┌───────────────▼──────────────────────────────────────────────┐
 │ 车企授权服务器（SSO）                                          │
 │  · 同意界面（展示 scope / purpose）                            │
 │  · 签发 access_token(typ=at+jwt) + refresh_token(一次性轮换)   │
 │  · 发布 /.well-known/openid-configuration                      │
 └───────────────┬──────────────────────────────────────────────┘
                 │ Bearer（Authorization 头）
 ┌───────────────▼──────────────────────────────────────────────┐
 │ 车企资源服务器（业务 API）                                     │
 │  · 本地校验 JWT（iss/aud/exp/typ）                             │
 │  · 短 TTL，撤销依赖刷新令牌与 scope 收窄                        │
 └───────────────┬──────────────────────────────────────────────┘
                 │
 ┌───────────────▼──────────────────────────────────────────────┐
 │ 车辆（经车企云代理；本组合不含车端本地验签）                    │
 └──────────────────────────────────────────────────────────────┘
```

**报文序列**（简化，细节见 11.2.2）：

```
App → 浏览器 → /authorize (response_type=code, client_id, redirect_uri, scope, state, nonce, code_challenge, code_challenge_method=S256)
授权服务器 → 同意界面 → 车主同意
浏览器 → App: redirect_uri?code=..&state=..
App → /token (grant_type=authorization_code, code, redirect_uri, client_id, code_verifier)
授权服务器 → App: access_token(JWT) + refresh_token
App → /api (Authorization: Bearer <JWT>)
资源服务器: 校验 iss/aud/exp/typ → 返回数据
```

**适用场景**：第三方数据应用、车主自用 App、低风险读操作、MVP 阶段。

**不适用**：车控写操作（缺发送方约束）、高价值数据（缺资源级授权）、服务间调用（缺客户端强认证）。

### 11.8.2 组合 B：高保障

**定位**：面向「车控写操作 + 高价值数据 + 服务间调用」，以发送方约束令牌、结构化授权与步进认证为核心。

**协议组成**：

| 层 | 协议/机制 | 规范依据 | 职责 |
|---|---|---|---|
| 客户端认证 | mTLS 客户端认证 | RFC 8705、RFC 8446、RFC 5280 | 以证书取代/加强 secret |
| 令牌绑定 | 证书绑定令牌（`cnf`/`x5t#S256`）+ DPoP | RFC 8705、RFC 9449 | 令牌不可被复制盗用 |
| 服务间身份 | 客户端断言 | RFC 7523 | 服务账号私钥签名而非共享密钥 |
| 资源级授权 | 富授权请求 | RFC 9396 | 结构化描述「哪辆车/哪些字段/多久」 |
| 步进认证 | 认证强度挑战 | RFC 9470、WebAuthn L2 | 高风险动作前提升 `acr` |
| 实时校验 | 令牌内省 | RFC 7662 | 需要实时确认未吊销时使用 |
| 代理链 | 令牌交换 | RFC 8693 | `sub`/`act` 分离，审计可归属 |

**分层图**：

```
 ┌──────────────────────────────────────────────────────────────┐
 │ 第三方服务（机密客户端，持客户端证书 + DPoP 密钥对）            │
 └───────────────┬──────────────────────────────────────────────┘
                 │ mTLS 握手（RFC 8446 / RFC 5280）
                 │ 令牌请求带客户端断言（RFC 7523）
 ┌───────────────▼──────────────────────────────────────────────┐
 │ 车企授权服务器                                                 │
 │  · 校验客户端证书 + 断言（jti 去重）                            │
 │  · authorization_details（RFC 9396）→ 结构化授权对象            │
 │  · 签发绑定令牌：cnf.x5t#S256 = 客户端证书指纹 / DPoP jkt       │
 │  · 支持 acr 提升（RFC 9470）+ WebAuthn 强认证                  │
 └───────────────┬──────────────────────────────────────────────┘
                 │ 令牌交换（RFC 8693：sub=车主, act=第三方）
 ┌───────────────▼──────────────────────────────────────────────┐
 │ 车企云网关 / 资源服务器                                        │
 │  · 校验令牌绑定（证书指纹 / jkt）与请求方法、URL                │
 │  · 需要时内省（RFC 7662）确认未吊销                            │
 │  · 记录 sub + act + 授权决策依据                               │
 └───────────────┬──────────────────────────────────────────────┘
                 │ 车控指令（经云代理）
 ┌───────────────▼──────────────────────────────────────────────┐
 │ 车辆                                                          │
 └──────────────────────────────────────────────────────────────┘
```

**报文序列**（车控写操作，含步进认证）：

```
第三方服务 → 授权服务器: mTLS + client_assertion + authorization_details(资源=车辆X, 动作=unlock, 期限=10min)
授权服务器 → 第三方服务: 401 (需要更高 acr)
第三方服务 → 车主: 触发 WebAuthn 强认证
车主完成 WebAuthn → 授权服务器: 新令牌 (acr 已提升, cnf.x5t#S256=证书指纹)
第三方服务 → 车企云: POST /vehicle/X/unlock
  Authorization: DPoP <token>
  DPoP: <证明: htm=POST, htu=/vehicle/X/unlock, jti, iat>
车企云: 1) mTLS 证书指纹 == cnf ? 2) DPoP 验签 + jkt 匹配 ? 3) htm/htu 匹配 ? 4) jti 未重放 ? 5) 令牌交换链 sub/act 合法 ?
车企云 → 车辆: 下发已签名的车控指令
车辆 → 车企云 → 第三方服务: 执行结果
```

**适用场景**：车控写操作、高价值/敏感数据、企业车队、跨主体代理、需要审计归属的场景。

**代价**：客户端证书与 DPoP 密钥的运维复杂度、每请求签名开销、mTLS 在弱网下的握手失败率、`jti` 去重与时钟偏移窗口的工程成本。

### 11.8.3 组合 C：车端强绑定

**定位**：面向「数字钥匙与车端本地授权」——即**不经过云**的解锁/启动路径，以「车端验签」替代「云端令牌校验」。

**协议组成**：

| 层 | 机制 | 规范/证据依据 | 职责 |
|---|---|---|---|
| 近场信道 | BLE + UWB（NFC 强制备用） | CCC Digital Key Release 3.0 公告 `[A]`、FiRa `[B]` | 建立近场连接与物理在场证明 |
| 密钥载体 | 安全元件存储 | CCC 公告明载密钥存于 Secure Element `[A]` | 防密钥提取 |
| 车端授权校验 | 车端验签 | Tesla 虚拟密钥指引 `[A]`（车辆在执行命令前验证载荷签名） | 车端本地授权决策 |
| 密钥登记 | 可信用户添加公钥 | Tesla 指引 `[A]`（公钥须由可信用户添加到车辆） | 授权来源可追溯 |
| 吊销 | 用户在车辆侧删除密钥 | Tesla 指引 `[A]`（吊销由用户在车辆 Locks 界面删除密钥完成） | 本地吊销 |
| 参考架构 | GB/T 44402.1-2024 | 信源档案 §1.2 `[A]` | 国内架构定位 |
| 证书轮换 | ACME（RFC 8555）+ OCSP（RFC 6960） | 信源档案 §3 | 在线侧证书生命周期 |

**分层图**：

```
 ┌──────────────────────────────────────────────────────────────┐
 │ 手机/卡 内的安全元件（SE）                                     │
 │  · 数字钥匙私钥（不可导出）                                     │
 │  · 来源：CCC Digital Key Release 3.0 明载密钥存储于 SE  [A]     │
 └───────────────┬──────────────────────────────────────────────┘
                 │ 近场信道：BLE（连接与唤醒）/ UWB（测距，抗 relay）/ NFC（备用）
 ┌───────────────▼──────────────────────────────────────────────┐
 │ 车辆（车端网关 / 钥匙模块）                                    │
 │  · 保存已登记的可信公钥（来源：可信用户添加） [A]               │
 │  · 车辆在执行命令前验证载荷签名 [A]                             │
 │  · 本地吊销：用户在车辆 Locks 界面删除密钥 [A]                   │
 └───────────────┬──────────────────────────────────────────────┘
                 │ PEPS：被动无钥匙进入与启动（CCC 3.0 明载）  [A]
 ┌───────────────▼──────────────────────────────────────────────┐
 │ 车辆执行（解锁 / 上电 / 启动）                                 │
 └───────────────┬──────────────────────────────────────────────┘
                 │ 在线侧（钥匙下发 / 证书轮换 / 审计回传）
 ┌───────────────▼──────────────────────────────────────────────┐
 │ 车企云：钥匙签发、证书轮换（RFC 8555）、状态查询（RFC 6960）    │
 └──────────────────────────────────────────────────────────────┘
```

**报文序列**（配对 + 使用）：

```
[配对阶段]
用户(已认证) → 车企云: 请求为车辆 X 添加钥匙
车企云 → 手机 SE: 下发钥匙材料（SE 内生成/保存密钥）
车企云/车企App → 车辆: 登记可信公钥（Tesla 指引明载公钥须由可信用户添加 [A]）
车辆: 保存公钥（Tesla 指引明载车辆仅支持 prime256v1 密钥 [A]）

[使用阶段]
手机 SE → 车辆: 近场信道握手（BLE 唤醒 → UWB 测距 / NFC 备用）
车辆: 验证「设备在场且距离有效」
手机 SE → 车辆: 车控载荷 + 私钥签名
车辆: 用已登记公钥验证签名 → 通过则执行
```

**适用场景**：无网环境解锁/启动、钥匙分享、车端本地授权、对云可用性不敏感的高频近场操作。

**关键约束（`[A]` 级实例）**：信源档案 §7.1 记录 Tesla 虚拟密钥指引的若干关键点，可作为「车端强绑定」的已公开实现标尺——公钥须由可信用户添加到车辆、私钥留在应用服务器、**车辆在执行命令前或接受 Fleet Telemetry 配置前验证载荷签名**、文档称虚拟密钥「甚至能阻止 Tesla 自己的后端访问这些能力」、吊销由用户在车辆 Locks 界面删除密钥完成、车辆仅支持 prime256v1 密钥、公钥必须托管于 `/.well-known/appspecific/com.tesla.3p.public-key.pem` 且必须长期可用、私钥绝不可托管于域名 `[A]`；此外 B2B 项目车辆的自动添加密钥有**已配对密钥少于 20 把**这一前置条件 `[A]`——这是「用密钥数量上限限制影响范围」的工程手段。

### 11.8.4 三套组合的对照与选择

| 判据 | 组合 A 最小可用 | 组合 B 高保障 | 组合 C 车端强绑定 |
|---|---|---|---|
| 主要信任基 | 浏览器 + TLS + PKCE | 客户端证书/密钥 + 结构化授权 | 安全元件 + 车端验签 |
| 是否依赖云端在线 | 是 | 是（车控为核心时） | **否**（近场路径） |
| 令牌可复制性 | 可复制（Bearer） | **不可复制**（绑定） | 不适用（本地签名） |
| 授权粒度 | scope 字符串 | `authorization_details` 结构化 | 车端公钥 + 资源级策略 |
| 高风险动作保护 | 无 | 步进认证 + 强认证 | 物理在场 + 测距 |
| 离线可用性 | 差 | 中 | **好** |
| 吊销及时性 | 中（刷新令牌/scope） | 中-高（内省 + 绑定） | **差**（需车辆侧删除，且车辆需在线才能收到远程吊销） |
| 部署成本 | 低 | 高 | 中-高（SE 与近场器件） |
| 典型场景 | 第三方数据读取 | 车控写 / 企业车队 | 数字钥匙 |

**本报告判断**（推测，非事实）：三套组合不是互斥的，而是**共存**——成熟的车云授权架构会同时拥有 A（面向长尾第三方）、B（面向车控与企业）、C（面向近场钥匙）。选择的关键不是「哪个更安全」，而是**「该动作的失败后果是什么」**：读数据失败是可用性问题，车控被越权是安全问题，钥匙被复制是物理安全问题——三者应对应不同的组合与控制强度。

## 11.9 协议落地的 12 个常见错误清单

本节列出车云授权协议落地中最常见的 12 个配置错误，逐条给出「错误配置 → 后果 → 修正」。**每条修正均指向本章前文的规范依据**。

**错误 1：把访问令牌放在 URI 查询参数中传递。**
后果：令牌进入浏览器历史、Referer、代理与 CDN 日志，泄露点不受授权体系监控，等价于凭证泄露。
修正：一律使用 `Authorization` 请求头（RFC 6750 §2.1，见 11.3.1）。

**错误 2：公共客户端不使用 PKCE。**
后果：授权码被拦截即可换码，攻击者获得车主权限（Critical 级授权绕过）。
修正：强制 `code_challenge_method=S256`（RFC 7636；OAuth 2.1 列为强制，见 11.2.3 / 11.2.4）。

**错误 3：`redirect_uri` 允许前缀或通配匹配。**
后果：攻击者可用 `client.example.evil.com` 或开放重定向端点接收授权码。
修正：精确匹配 + 服务器侧白名单，且换码时再次校验（见 11.2.2.3）。

**错误 4：实现 `state` 但不实现 `nonce`（在使用 `id_token` 时）。**
后果：`id_token` 可被重放，车主可能被登录到攻击者控制的身份。
修正：OIDC 场景同时实现 `state` 与 `nonce`（见 11.2.2.4）。

**错误 5：把 `id_token` 当访问令牌用于调 API。**
后果：任意 OIDC 客户端都能用「合法签发但受众错误」的 `id_token` 越权访问资源。
修正：严格区分两者，资源服务器只接受访问令牌并校验 `aud`/`iss`（见 11.4.3）。

**错误 6：刷新令牌长期有效且不轮换。**
后果：刷新令牌一旦泄露，攻击者可长期续命，影响范围随时间扩大。
修正：一次性使用 + 轮换；OAuth 2.1 要求发送方约束或轮换。Tesla（一次性 + 3 个月 + 24h 宽限）与 Mercedes（一次性）为 `[A]` 级公开实例（见 11.2.1）。

**错误 7：在原生 App 中使用内嵌 WebView 承载授权码流。**
后果：宿主 App 可读取授权码、可伪造登录界面钓鱼，违反 RFC 8252。
修正：使用系统浏览器（外部用户代理）；车机改用设备授权流（见 11.2.5）。

**错误 8：不校验令牌 `aud`/`iss`，或信任任意来源的 `.well-known` 元数据。**
后果：跨环境/跨服务的令牌混用，或客户端被伪造元数据引向攻击者的授权服务器。
修正：`iss`/`issuer` 严格校验 + 元数据经 TLS 获取 + 拒绝弱算法（见 11.4.4）。

**错误 9：发送方约束只做「证书可信」，不做「指纹一致」。**
后果：任何持有合法客户端证书者都能使用他人的绑定令牌，绑定形同虚设。
修正：校验令牌 `cnf`（`x5t#S256` 或 DPoP `jkt`）与当前连接/证明一致（见 11.3.2 / 11.3.3）。

**错误 10：用一个全局去重表缓存所有 `jti`/nonce。**
后果：内存膨胀、无法按客户端隔离，攻击者可跨客户端耗尽去重表造成拒绝服务。
修正：按作用域与生命周期分离去重存储（见 11.7.3）。

**错误 11：对车控写操作使用 0-RTT（TLS 恢复）承载。**
后果：0-RTT 数据可被重放，重放一条车控指令可能造成实际车辆动作。
修正：写操作禁用 0-RTT，仅对幂等读请求优化（见 11.6.4.3）。

**错误 12：协议落地缺少「授权决策依据」的日志。**
后果：事件发生后无法回答「谁在何时、基于什么授权决策、经由哪个代理方，操作了哪辆车」。
修正：记录 `sub` + `act` + 授权对象 + 决策结果 + 时间基准（RFC 8693 的 `act` 链、RFC 3161 时间戳，见 11.2.7 / 11.7.2）。

> 说明：上述 12 条的「错误配置」描述的是机制层面的常见失误，**不指向任何具体车企或产品**。信源档案 §7 记录的车企实现细节仅作为「该正确做法在车云中已被公开实现」的佐证。

## 11.11 本章小结

### 11.11.1 本章覆盖了什么

本章完成了以下工作：

1. **建立选型框架**（11.1）：给出 18 行「场景 → 适用协议 → 规范依据 → 为什么」的主选型表，并归纳出三个判据（是否存在人类资源所有者、令牌是否可能被复制、是否需要物理在场）。
2. **拆解 OAuth 2.x 核心与演进**（11.2）：从 RFC 6749 的四类授权映射出发，给出授权码流的报文级时序（含每步参数表与每步攻击面）、PKCE 的机理与 S256 强制要求、OAuth 2.1 草案六项强制性变更的迁移影响、RFC 8252 的原生 App 要求与车机推论、RFC 8628 设备授权流的报文与轮询穷举风险、RFC 8693/7523 的两层代理与审计归属、RFC 9396 RAR 与 RFC 9635 GNAP 的设计差异。
3. **拆解令牌传输与绑定**（11.3）：RFC 6750 三种传输位置的风险对照、RFC 8705 的 `cnf`/`x5t#S256` 绑定机理、RFC 9449 的 `jkt` 绑定与 `htm`/`htu` 方法级绑定、以及三者的 12 维对照矩阵。
4. **拆解身份层与强认证**（11.4、11.5）：OIDC 的认证/授权分离、`id_token` 误用反模式、Discovery 两种路径及其风险面；WebAuthn/FIDO2 与 RFC 9470 步进认证的组合设计。
5. **拆解车端特有协议面**（11.6）：数字钥匙三通道与安全元件、V2X 证书与车云业务证书的目标冲突、OCPP 与 ISO 15118 的处理边界、服务间 mTLS + OCSP + ACME 的闭环。
6. **拆解防重放与时间基准**（11.7）：RFC 3161 时间戳、七类 nonce/jti 的分离管理、时钟偏移容忍、离线/弱网场景的影响与「离线可用性 vs 吊销及时性」的核心张力。
7. **给出三套可落地组合**（11.8）：最小可用（A）、高保障（B）、车端强绑定（C），各含分层图、报文序列与适用场景。
8. **给出 12 条常见错误清单与待补证清单**（11.9、11.10）。

### 11.11.2 本章的三条核心结论

**结论一：授权模型的复杂度由「资源所有者形态」决定，而非由「协议新不新」决定。** 车云场景中并存三类资源所有者：人类（车主）、组织（车队/企业）、物理实体（车辆本身 + 近场设备）。三者对应的授权流、信任基与吊销机制完全不同（最小可用 vs 高保障 vs 车端强绑定）。把三者塞进同一套 OAuth 客户端凭证里，是车云授权架构最常见的结构性错误。

**结论二：规范族已足以覆盖车云授权的全部已知需求形态，瓶颈在工程落地而非协议缺失。** 从 RFC 6749 到 RFC 9635，从 RFC 8705 到 RFC 9449，从 RFC 9396 到 RFC 9470，本章涉及的每一条需求（第三方授权、无浏览器登录、发送方约束、结构化授权、步进认证、代理链审计、自动轮换、可信时间）都有对应的规范依据（均为信源档案 §2/§3 已取证 `[A]` 条目）。真正的风险集中在 11.9 列出的 12 类配置错误——它们都不是「协议不支持」，而是「协议被配错」。

**结论三：车云的授权存在一个不可消除的张力——离线可用性与吊销及时性。** 车辆必须在断网时仍能解锁，而授权撤销又必须尽快生效，二者在物理上无法同时满足（11.7.5）。任何车云授权架构都必须**显式地**做出这一取舍并把它写入威胁模型，而不是假装两者都能满足。务实的方向是按风险分级：低风险动作允许离线凭证长期有效，高风险动作要求在线校验或近场强认证。

### 11.11.4 一句话总结

**车云授权与访问控制不是「选一个 OAuth 流」的问题，而是「为三类不同的资源所有者、在三种不同的网络条件下、按三种不同的风险等级，组合出可被审计、可被吊销、不可被复制的授权链」的问题**；本章给出的 18 行选型表、三套组合与 12 条错误清单，是这一组合工作的分析工具，而非标准答案。
