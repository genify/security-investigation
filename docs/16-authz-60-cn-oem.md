## 16.0 本章方法与覆盖度声明

### 16.0.1 本章要回答的三个问题

国内新能源汽车企业在「授权与访问控制」这一层，公开可取证的材料远比国际同行稀薄。这不是本章的写作失误，而是**取证条件的客观约束**（见 16.0.2）。因此本章不追求「把九家车企的授权架构都写出来」——那做不到，任何写出来的版本都会是编造。本章追求的是把**三个层次的问题分开回答**：

1. **已确证的事实层**：这九家企业在公开渠道上，究竟留下了哪些关于授权与访问控制的**一手痕迹**？本章逐家列出，并逐条标注证据等级（[A]/[B]/[C]/未取证）。
2. **明确披露的缺口层**：哪些方向**本次未找到公开来源**？本章把每一家的缺口方向逐项写清，并给出可执行的**补证动作**（RFI、商务申请沙箱、专利检索、T-BOX 拆解、招标与备案检索）。**「未找到公开来源」绝不等于「该企业没有该能力」**——这是本报告的中立性红线（`00-engagement-plan.md` §3.2 第 4 条）。
3. **基于国家标准与技术路线的设计空间层**：在中国的强制性国标（GB 44495/44496）与推荐性国标族（GB/T 47324、GB/T 47467、GB/T 44402.1、GB/T 45112 等）已经给定的**合规约束**下，一家希望在国内合法合规运营车云开放接口的车企，其授权架构**可能**会长成什么样子？这一层全部标注为推测，并给出可检验的推断与检验方法。

把这三层物理分开写，是本报告「证据分层写作法」（`00-engagement-plan.md` §4 第 4 条）在本章的落实：读者可以一眼看清哪些是「文档明载」，哪些是「本报告判断」。

## 16.1 中国车企车云安全的合规底座：先讲「必须做什么」，再讲「怎么做」

分析国内车企的授权架构，必须先把**约束条件**摆清楚。与欧美「标准先行、市场跟随」不同，中国的车云安全首先是**合规驱动**的：强制性国标划出红线，推荐性国标提供实现路径，行政法规规定数据义务。**授权与访问控制在这个体系里不是可选的架构优化，而是合规义务的技术执行点。**

本节按「强制 → 推荐 → 数据合规 → 密码体系」四步展开。

### 16.1.1 强制性国标 GB 44495-2024 与 GB 44496-2024 的定位与适用时间

根据 `source-dossier.md` §1.1（[A]：国家标准全文公开系统一手）：

- **GB 44495-2024《汽车整车信息安全技术要求》**——发布 2024-08-23，**实施 2026-01-01**。
- **GB 44496-2024《汽车软件升级通用技术要求》**——发布 2024-08-23，**实施 2026-01-01**。
- 两者均属**强制性**国家标准（状态「现行」），是中国车云与 OTA 安全的**合规基线**，**2026-01-01 起对新车型强制适用**。

**这对授权与访问控制意味着什么？** 强制性国标的存在，改变了国内车企授权架构设计的经济学：**在 2026-01-01 之后上市的新车型，其车云接口的授权控制不再是「做了更好」，而是「不做即不合规」。** 相应地，本报告对国内车企的一条核心推断是：**即便中文本地文档没有公开，面向国内销售车型的车云链路在 2026 年之后也必然要满足 GB 44495 的信息安全要求（本报告判断，推测，非事实）**。理由是强制适用本身构成法律义务，与文档是否公开无关。

**证据强度提示**：`source-dossier.md` §1.1 确认了这两项标准的**编号、名称、发布/实施日期与强制性状态**，但本次**未逐条解析标准正文的条款级要求**。因此本节只做「强制性与适用时间」层面的定位陈述，**不给出任何条款编号或款级要求**（`00-engagement-plan.md` §3.2 第 3 条红线）。

### 16.1.3 数据合规：GB/T 41871-2022、GB/T 44464-2024 与《汽车数据安全管理若干规定（试行）》

对国内车企而言，「授权」与「数据合规」在技术上是同一个执行点的两面：**授权是数据合规的技术执行层**。原因很直接——数据合规要求「谁在什么条件下可以处理哪些数据」，而「谁在什么条件下可以访问哪个资源」，正是授权系统在回答的问题。

`source-dossier.md` §1.2 / §1.3 给出的一手条目（全部 [A]）：

| 依据 | 名称 | 发布/成文 | 实施/施行 |
|---|---|---|---|
| GB/T 41871-2022 | 信息安全技术 汽车数据处理安全要求 | 2022-10-14 | 2023-05-01 |
| GB/T 44464-2024 | 汽车数据通用要求 | 2024-08-23 | 2024-08-23 |
| 《汽车数据安全管理若干规定（试行）》 | 网信办等五部门令第 7 号 | 2021-08-16 成文 | 2021-10-01 施行 |

`source-dossier.md` §1.3 明载该行政法规规定**重要数据目录、境内存储、年度报送、出境评估等义务**。据此可整理出义务清单（**以下四条义务的名称来自 dossier 原文，具体审批阈值/流程细节本次未取证，标注为待补证**）：

| 义务 | 内容（dossier 明载的**方向**） | 与授权设计的耦合点 |
|---|---|---|
| **重要数据目录** | 企业须识别并编制重要数据目录 | 授权系统须能**按数据分类分级**打标资源；分类分级是授权策略的输入 |
| **境内存储** | 重要数据原则上境内存储 | 授权与身份服务（IdP）的**部署位置**受约束；跨境令牌交换需评估 |
| **年度报送** | 须按年度报送相关情况 | 授权与访问**审计日志**成为报送材料的一部分 |
| **出境评估** | 数据出境须经安全评估 | 跨境 API 的**授权决策点**须能识别数据流向 |

**为什么说「授权是数据合规的技术执行点」？** 因为上述四条义务如果只写在制度文件里、没有落到代码里，就无法通过审计。而落地的技术抓手恰好就是授权层：

1. **分类分级 → scope / 属性**：数据要分「重要数据 / 个人信息 / 一般数据」，授权系统就必须能把这一分级编码进令牌或策略（例如把 RFC 9396 的 `authorization_details` 结构化权限对象带上 `data_classification` 属性）。**本报告判断（推测，非事实）**：国内车企若做数据分类分级的系统化落地，其授权令牌或资源服务器策略大概率会包含类似的数据分级字段。
2. **境内存储 → 身份服务本地化**：若 IdP 在境外，则「境内存储」义务难以满足。**本报告判断（推测，非事实）**：面向国内销售的车型，其车主身份与授权服务应在国内区域部署。
3. **年度报送 / 出境评估 → 授权审计**：报送需要「谁访问了什么」，这正是授权决策日志。**GB/T 45181-2024（异常行为检测）** 与 **GB/T 47324-2026（平台防护）** 在此处与数据合规交汇。

**证据强度提示**：`source-dossier.md` §1.3 引用的是《汽车数据安全管理若干规定（试行）》的**法规页与答记者问页**（[A]），确认了「重要数据目录 / 境内存储 / 年度报送 / 出境评估」这四项义务的**存在与方向**。但本次**未逐条解析法规文本**，因此本节**不给出任何条款编号、审批时限、阈值数字**。上述「与授权设计的耦合点」一栏，凡属技术推导者，均为 **本报告判断（推测，非事实）**。

### 16.1.4 国密算法体系对车云链路的技术含义

国内合规路径与国际路径在密码学栈上的差异，是理解「为什么国内车企的授权架构不能简单复制国际方案」的关键。`source-dossier.md` §1.2 / §3 给出的国密相关一手条目（全部 [A]，国家标准全文公开系统 / RFC Editor）：

| 标准号 | 名称 |
|---|---|
| GB/T 32918.1~.5-2016/2017 | SM2 椭圆曲线公钥密码算法（总则 / 数字签名 / 密钥交换 / 公钥加密 / 参数定义） |
| GB/T 32905-2016 | SM3 密码杂凑算法 |
| GB/T 32907-2016 | SM4 分组密码算法 |
| GB/T 35275-2017 | SM2 密码算法加密签名消息语法规范 |
| GB/T 35276-2017 | SM2 密码算法使用规范 |
| RFC 8998 (2021) | ShangMi (SM) Cipher Suites for TLS 1.3（SM2 签名、AEAD_SM4_GCM / AEAD_SM4_CCM、SM3） |

`source-dossier.md` §3 对 RFC 8998 的定位注释为：「**国密 TLS 在国际标准层面的唯一落点，国产车云链路合规的关键**」[A]。这是理解国密栈与车云链路关系的核心事实：**SM2/SM3/SM4 不是「中国自己的一套孤立密码」，而是已经通过 RFC 8998 进入 IETF 的 TLS 1.3 套件体系**——也就是说，国密 TLS 可以与标准 TLS 1.3 握手框架复用（`source-dossier.md` §3 同时列有 RFC 8446 TLS 1.3）。

#### 「国际栈 vs 国密栈」对照表

下表把两条技术路线逐层对照。**左列「国际栈」的规范引用来自 `source-dossier.md` §2/§3（RFC 一手）；右列「国密栈」的规范引用来自 §1.2/§3（国标一手 + RFC 8998）。「工程含义」一栏为**本报告判断（推测，非事实）**。**

| 层次 | 国际栈（规范来源 [A]） | 国密栈（规范来源 [A]） | 工程含义（本报告判断，推测） |
|---|---|---|---|
| 公钥算法 | ECDSA / ECDH（RFC 6090、RFC 5480） | SM2（GB/T 32918.1~.5） | 两者均为椭圆曲线体制；**密钥格式与证书扩展的编码差异**导致证书链工具链不通用 |
| 摘要算法 | SHA-256 等 | SM3（GB/T 32905-2016） | 签名/验签与证书指纹需按 SM3 计算 |
| 对称算法 | AES-GCM（NIST SP 800-38D、FIPS 197） | SM4（GB/T 32907-2016），AEAD_SM4_GCM / AEAD_SM4_CCM（RFC 8998） | 分组长度均为 128 位；**GCM/CCM 模式在 RFC 8998 中已定义**，可复用 AEAD 框架 |
| TLS 套件 | RFC 8446 TLS 1.3 标准套件 | RFC 8998 SM 套件（TLS 1.3） | **可共用 TLS 1.3 握手骨架**；套件协商与证书链是差异点 |
| 证书/消息语法 | RFC 5280 X.509、PKCS#1（RFC 8017） | GB/T 35275-2017 SM2 加密签名消息语法、GB/T 35276-2017 SM2 使用规范 | **消息语法层**的差异会传导到签名验签与封装格式 |
| PKI 吊销 | RFC 5280 CRL、RFC 6960 OCSP | 未见对应国密专有公开一手条目（本次未取到） | 国密 PKI 的吊销机制本次未取证，列入 16.6 |

**「为什么国内合规路径与国际 PKI 栈不同」——三个层面的原因**（本报告判断，推测，非事实）：

1. **密码算法主权**：国内法规环境对关键信息基础设施与汽车数据处理的密码使用有国产化要求，SM 系列是法定可用的国产算法族。**这与「市场自发选择」不同，是合规驱动。**
2. **证书体系主权**：`GB/T 45112-2024` 明确定义了 C-V2X 的**安全证书管理系统技术要求**，这是「车-云-车」通信证书的国家级规范。**如果车云链路要接入 V2X 证书体系，其证书管理不能完全依赖国际 CA 体系。**
3. **消息语法差异**：GB/T 35275 定义了 SM2 的加密签名消息语法，与国际 PKCS / CMS 体系在编码细节上不同，**这会在证书与签名互操作层面形成「栈内闭环」**。

**换言之**：一家国内车企的车云链路若走国密路径，其 PKI 栈（CA、RA、证书格式、吊销、TLS 套件）会与国际栈形成**两套并行但语义等价的体系**。这是「双栈」工程成本的来源，也是国内车云安全与国际车云安全出现结构性差异的密码学根因。

**证据强度提示**：本节所有**标准号、名称、日期**均来自 `source-dossier.md` 一手条目（[A]）。「工程含义」「为什么不同」两栏均为**本报告判断（推测，非事实）**。本次**未取得任何国内车企实际使用国密栈的一手证据**（`source-dossier.md` §7.10 第 5 条），因此**不得**把「国密栈」写回国别内任何一家车企的已取证事实中——它只出现在设计空间分析（16.2 各家第(4)小节）中，且逐条标注推测。

**关键观察一：蔚来把「文档访问」纳入授权控制。** `interface.html` 页面明载「请联系文档提供人获取文档访问 token」[A]。这在工程上是一种**信息层面的访问控制**：不是所有拿到 Open NSC 入口的人都能读到接口规范，须持有文档 token。**本报告判断（推测，非事实）**：这种设计通常出现在「接口尚在商务定制阶段、需要按合作方逐份签署协议」的场景中，与蔚来 app-id/secret「通过商务渠道获取」的表述在逻辑上一致。

**关键观察二：蔚来走的是 app-id + secret 而非 OAuth。** 与 `source-dossier.md` §7.1 Tesla（OAuth authorization_code + scope 全清单）与 §7.2 Mercedes-Benz（OAuth Authorization Code Flow + `mb:` 命名空间 scope + `openid`/`offline_access`）相比，蔚来 Open NSC 采用的是**服务端到服务端的双凭证模型**（app-id + secret）。**这是「服务集成型」授权，而非「代表车主行事型」授权**——它解决的是「哪个合作方在调用接口」，而不是「车主是否同意该合作方访问其车辆」。**本报告判断（推测，非事实）**：app-id+secret 模型之所以在服务云场景够用，是因为服务云业务（加电、维保）的处理对象通常是「订单与服务履约」，不是「逐车主的敏感车辆控制」，对逐车主同意的合规压力较小。

**关键观察三：时效性护栏。** 任何人引用蔚来 Open NSC 的证据时，必须同时引用「2019-08-13」这个时间戳。**蔚来在 2019 年之后的数字钥匙、车控授权、UWB 等能力，本次没有任何一手来源。** 蔚来官方对「UWB+蓝牙+NFC 三合一数字钥匙」的技术说明本次未取得（§7.10 第 1 条，仅二手报道 [C]）。

| 要素 | 文档明载（[A]） |
|---|---|

**工程解读（本报告判断，推测，非事实）**：`x-Gateway-APIKey` 这种「自定义 `x-` 前缀 + 网关（Gateway）语义」的鉴权头，是**API 网关产品的常见模式**：网关在入口校验 `x-Gateway-APIKey`，把 appKey 映射到某个已订阅的应用/租户，再决定放行哪些服务。**它的授权粒度是「应用—服务订阅」级，而非「资源实例」级**——也就是说，识别的是「哪个应用在调用哪个服务」，而不是「该应用是否有权访问某一辆具体车辆」。**这是 ESB 场景的特征，也是与 OAuth + 资源级策略（RFC 9396 / RFC 8705，`source-dossier.md` §2.1）在模型上的根本差异。**

**与 OAuth 的对照（本报告判断，推测，非事实）**：

| 维度 | i迪桥 APIKey（[A] 事实） | OAuth 授权码（[A] 规范，Tesla/Mercedes 为公开实例） |
|---|---|---|
| 身份对象 | **应用（调用者）** | 可达「用户 + 应用」双身份 |
| 凭证形态 | 静态 APIKey（可长期不变） | 短期 access_token + 一次性 refresh_token |
| 授权粒度 | 应用—服务订阅 | scope + 资源级策略 |
| 逐车主同意 | 不涉及（B 端场景） | 有（`code` 换 token 前的同意界面） |
| 吊销/轮换 | 未见文档（**未取证**） | 规范定义（RFC 7009 吊销，`source-dossier.md` §2.1） |

##### 2.4 接入五步流程（一手拆解）

### 16.3.2 从「服务云开放」到「车控开放」的演进阶段判断

**方法论前置声明（极重要）**：本小节把车企放入 4 个阶段，**目的是给「取证横截面」一个结构化坐标，不是给车企排技术能力。** 阶段归属**只依据已取证事实**；无证据者一律归入「未取证」而非「落后」。

**四阶段模型（本报告提出的分析框架，属 [合理推测] 框架）**：

```
阶段 0  无开放平台
        —— 无对外接口；仅自营 App ↔ 车云 ↔ 车端

阶段 1  服务云开放（app-id + secret / APIKey）
        —— 开放「服务履约类」接口（加电、维保、物流…）
        —— 身份对象 = 合作方应用；无车主同意语义

阶段 2  数据开放（OAuth 授权码）
        —— 开放「车主数据」接口，以 OAuth 代表车主行事
        —— 身份对象 = 车主 + 应用；有同意界面与 scope

阶段 3  车控开放（OAuth + 资源级 + 虚拟密钥）
        —— 开放「车辆控制」接口，需资源级策略 + 密钥绑定
        —— 对应 RFC 9396（结构化权限）+ RFC 8705（证书绑定令牌）
          + Tesla 虚拟密钥模型（source-dossier.md §7.1 实例）
```

**九家车企的阶段归属（仅依据已取证事实）**：

| 车企 | 阶段归属（依据取证） | 依据 | 说明 |
|---|---|---|---|
| 比亚迪 | **阶段 1（服务层 ESB）** | [A] i迪桥 APIKey，七大企业领域 | **企业级 ESB 是「服务云开放」的一种形态**（B 端） |
| 蔚来 | **阶段 1（服务云）** | [A] app-id+secret，服务云业务 | 文档 2019 时效，不代表当前 |
| 小米 | **无法归属**（IoT 平台是产品级，非车云） | [A] IoT 平台面向模组厂商 | 车云阶段未取证 |
| 小鹏 | **未取证** | 403 | 不归入任何阶段 |
| 理想 | **未取证** | 域名无 DNS | 不归入任何阶段 |
| 零跑 | **未取证** | 域名无 DNS | 不归入任何阶段 |
| 华为鸿蒙智行 | **未取证** | 文档 JS 空壳 | 不归入任何阶段 |
| 极氪 | **未取证** | HTTP 500 | 不归入任何阶段 |
| 奇瑞 | **未取证** | 无开放平台入口 | 不归入任何阶段 |

**本报告判断（推测，非事实）**：**从本报告掌握的国际一线样本（Tesla 阶段 3、Mercedes-Benz 阶段 2，均为 [A]）与传统车企的公开表现看，中国市场大概率也存在阶段 2/3 的实践**——理由是 GB 44495/44496 于 2026-01-01 强制适用（§16.1.1），而车控开放若存在，其授权必然要满足该强制性要求。**但本次取证完全没有触达这一层，因此结论只能是「未取证」。** 这是本章贯穿始终的「取证边界」纪律。

**阶段演进的三条可检验推断（均标推测）**：

- **推断 S-1（本报告判断，推测，非事实）**：中国车企若从阶段 1 走向阶段 2/3，**最可能的路径是「先服务云（B 端）→ 后车主数据（C 端）」**，因为 B 端服务云的合规压力（无个人数据）小于 C 端车主数据（涉及个人信息与重要数据）。**检验方法**：跟踪各车企开放平台的服务目录是否从「履约类」扩展到「数据/车控类」。
- **推断 S-2（本报告判断，推测，非事实）**：阶段 2/3 的实现**大概率会引入 OAuth 授权码流**（因需要「代表车主行事」语义），这与阶段 1 的 app-key 模型有本质区别。**检验方法**：探测车企域名下的 `.well-known/oauth-authorization-server`（RFC 8414）。
- **推断 S-3（本报告判断，推测，非事实）**：阶段 3（车控开放）**大概率会引入「密钥绑定令牌」或「虚拟密钥」类机制**（RFC 8705 / DPoP RFC 9449，或 Tesla 式虚拟密钥），因为纯 Bearer 令牌无法满足车控的持有者约束需求。**检验方法**：检索车企是否有 `.well-known/appspecific/*.pem` 类的公钥托管路径（Tesla 用此模式，`source-dossier.md` §7.1）。

### 16.3.3 中国企业常见的三类授权治理结构（推演）

> **本节全部为推演（[合理推测]）**，目的是为后续 RFI 提供「组织假设」。**本节不对应任何单一车企的已取证事实**，不得用于描述任何具体企业的实际组织结构。

**结构 A：集团统一开放平台**

- **形态**：由集团层面建设统一身份与开放平台，各品牌/子品牌接入。
- **信任边界**：单一身份源（IdP）服务多品牌 → **边界在「集团边界」**；一个品牌委派的合作方凭证若管理不当，理论上可影响同集团其他租户。
- **授权后果（推测）**：适合统一 scope 命名空间（如 Mercedes 的 `mb:` 命名空间式约定，`source-dossier.md` §7.2）；但跨品牌的资源隔离需在平台层显式实现。
- **对本次取证的启示**：若某车企属此类，其开放平台域名可能**不带品牌名**（如集团域名），这会解释「品牌子域无 DNS」的现象。

**结构 B：事业群各自平台**

- **形态**：各事业群（如服务、智造、营销）各自建设开放接口。
- **信任边界**：**边界在「事业群边界」**；跨事业群的数据流动需额外协调。
- **授权后果（推测）**：容易出现「多个网关、多套鉴权」。**本报告判断（推测，非事实）**：比亚迪 i迪桥（企业级 ESB，覆盖七大企业领域 [A]）的形态**更接近结构 B 的「集团内多系统 API 化」**，即以一个 ESB 汇聚多个事业域。
- **对本次取证的启示**：若属此类，**「开放平台」可能不止一个**，单一域名的检索会漏掉其他平台的入口。

**结构 C：供应商代运营**

- **形态**：开放平台/云底座由第三方云或系统集成商代建代营。
- **信任边界**：**边界延伸到「供应商边界」**；供应商的运维权限成为信任链的一部分。
- **授权后果（推测）**：授权策略的最终控制权与实现细节分属两家，**审计需覆盖供应商侧**。
- **对本次取证的启示**：若属此类，其开放平台文档可能由供应商模板生成，**命名与风格可能趋同**（这解释了为何多家车企的开放平台形态相似）。

**三类结构的信任边界对照（推演）**：

| 结构 | 信任边界止于 | 主要信任风险（推测） | 授权治理重点（推测） |
|---|---|---|---|
| A 集团统一 | 集团 | 跨品牌横向影响 | 统一 IdP + 资源级隔离 |
| B 事业群各自 | 事业群 | 多套鉴权、策略不一致 | 统一网关 + 策略编排 |
| C 供应商代运营 | 供应商 | 运维权限过大、审计盲区 | 供应商访问审计 + 权限最小化 |

> **再次强调**：以上三类结构是**组织假设**，用于指导 16.6 的补证动作（例如：结构 B 假设下应检索「多个开放平台域名」），**不构成对任何车企组织形态的事实断言**。

### 16.3.4 按切面的缺口聚类分析

把 §16.0.4 的 45 格矩阵按**切面**（列）而非车企（行）重新聚类，可以看出一组更有解释力的结构。**下表统计的是「本次取证的缺口分布」，不是「车企的能力分布」。**

| 切面 | 取到 [A] 的车企数 | 未取证车企数 | 缺口性质（本报告判断，推测，非事实） |
|---|---|---|---|
| **C1 硬件根信任** | **0** | 9 | 硬件实现细节天然不公开；须靠拆解/专利补证 |
| **C2 通信安全** | **0** | 9 | 密码栈选择属敏感配置；须靠 RFI/白皮书补证 |
| **C3 授权与访问控制** | **2**（比亚迪 ESB、蔚来服务云） | 7 | **服务层可公开、车控层不公开**；两格均为非 OAuth |
| **C4 应用与平台** | **4**（蔚来、小米、比亚迪、奇瑞） | 5 | 平台/治理层最易公开（文档站、认证、漏洞专栏） |
| **C5 OTA 与数据合规** | **2**（理想、小米） | 7 | 合规承诺载体（隐私政策/信任中心）可公开；OTA 技术细节不公开 |

**从这张聚类表可以读出三条结构性结论**：

1. **「越靠近车辆物理安全，越不公开」**（本报告判断，推测，非事实）：C1/C2（硬件与通信）取证率为 0，C3 仅服务层取证，C4/C5 的合规与文档层取证率最高。**这符合敏感信息披露的一般规律**——车企倾向公开「合规承诺」与「平台能力」，回避「密钥/算法/车控接口」细节。
2. **授权切面（C3）的取证集中度最高但层级最低**：9 家中 7 家完全未取证，2 家取证的均是**服务层**（企业 ESB / 服务云），**没有一家车控层**。这一「服务层可公开 / 车控层不公开」的分野，是本章最重要的取证观察之一。
3. **合规层（C5）的公开度提示了补证路径**：理想隐私政策（生效 2026-01-22）与小米信任中心（ISO 27001 编号 IS 831552）说明——**合规承诺文件是公开信息「最容易触达」的一层**。因此**补证的优先级应为：先从合规文件切入（易得），再向授权技术文档推进（难得）**。这正是 16.6 清单按「合规文件 → 商务沙箱 → 拆解」递进排列的依据。

**与 `source-dossier.md` §8 的呼应**：§8 列出的「国内 9 家车企的车云通信安全（mTLS/国密）——未找到公开一手来源」与「TEE/SE/HSM 实现——未找到公开一手来源」，正是本聚类表中 C2/C1 两列为 0 的直接体现。**本章的 45 格矩阵与 §8 的缺口表在结构上完全一致，互为交叉验证。**

## 16.4 国内路线与国际路线的结构性差异（国内视角）

> **本节定位**：作为 `30-comparison.md` 对比章的输入，本节**只给国内视角**——即从本章已确证的国内取证事实出发，对照国际公开样本（主要来自 `source-dossier.md` §7.1 Tesla、§7.2 Mercedes-Benz、§7.3 VW/CARIAD），指出**结构性差异**。**差异描述不等于优劣判断**；每一条差异都同时给出「已取证锚点」与「推测成分」的标注。

**对照物说明**：国际侧的可引用事实来自 `source-dossier.md` §7.1（Tesla Fleet API，证据最厚）、§7.2（Mercedes-Benz，`mb:` 命名空间 + Authorization Code Flow）。国内侧来自本章 16.2 的取证。**注意**：国际样本本身也是「公开文档可达的企业」，同样存在覆盖度偏置（§0）——因此本节是「两条被取证路径的差异」，不是「两个市场的全量差异」。

### 16.4.1 差异维度一：合规驱动 vs 市场驱动

| 观察 | 国内（已取证锚点 / 推测） | 国际（已取证锚点） |
|---|---|---|
| 强制基线 | **GB 44495-2024 / GB 44496-2024，2026-01-01 强制适用** [A] | UN R155/R156 等（`source-dossier.md` §1.4 标 [未验证]） |
| 数据法规 | 《汽车数据安全管理若干规定（试行）》，重要数据目录/境内存储/年度报送/出境评估 [A] | 欧盟 GDPR（§1.4 标 [C]）、Data Act 数据可携权（§1.4 标 [C]） |
| 驱动逻辑 | **本报告判断（推测，非事实）**：国内车企的授权架构**首先由合规定义下限**，再由商务需求定义上限 | **据 `source-dossier.md` §7.2**：Mercedes 明确以「GDPR 合规 + 用户信任」为授权码流的理由 [A] |

**结构性差异（本报告判断，推测，非事实）**：国内路线的**合规驱动力度更强、时间点更集中**（2026-01-01 是一个硬节点），这会推动国内车企在**短期**内补齐授权与访问控制基线；但合规驱动也可能导致「**满足最低要求即止**」的倾向，而非国际样本中「以公开文档建立开发者生态」的**主动披露动机**。**这一推测可直接检验**：观察 2026 年后国内车企是否出现类似 Tesla `developer.tesla.com` 的完整公开授权文档。

### 16.4.2 差异维度二：APIKey/ESB 体系 vs OAuth 授权码体系

| 观察 | 国内 | 国际 |
|---|---|---|
| 有取证的两家鉴权形态 | **蔚来 app-id+secret [A]；比亚迪 APIKey `x-Gateway-APIKey` [A]** | **Tesla OAuth authorization_code + scope 全清单 [A]；Mercedes Authorization Code Flow [A]** |
| 身份对象 | 应用（合作方） | 车主 + 应用 |
| 授权语义 | 订阅/审核 | 同意 + scope |
| 令牌生命周期 | **未取证** | 规范定义（刷新令牌一次性、TTL 等，§7.1/§7.2 [A]） |

**结构性差异（本报告判断，推测，非事实）**：国内有取证的两家均落在「**应用身份型**」授权（APIKey/双凭证），而国际两家落在「**用户代理型**」授权（OAuth）。**这一差异与 16.4.1 的「服务云开放」定位一致**：应用身份型授权服务于 B 端集成，用户代理型授权服务于 C 端数据/车控。

**但必须克制归纳**：这**只是两家**的取证结果，且都是**服务级**平台。**不得**据此得出「中国车企不做 OAuth」的结论。**检验方法**：探测国内车企域名是否发布 OAuth 授权服务器元数据（RFC 8414）。

### 16.4.3 差异维度三：服务云开放 vs 车控开放

| 观察 | 国内 | 国际 |
|---|---|---|
| 有取证平台的业务域 | 蔚来 = 服务云（加电/维保）[A]；比亚迪 = 企业 ESB（七大领域）[A]；小米 = IoT 模组 [A] | Tesla = 车控 + 遥测 + 虚拟密钥 [A] |
| 是否含车控 | **三家均不含**（均非车控开放） | **Tesla 明确含车控**（`vehicle_cmds`、虚拟密钥）[A] |
| 授权与车控的耦合 | **未取证** | 虚拟密钥 + 资源级（`hide_private`）[A] |

**结构性差异（本报告判断，推测，非事实）**：国际样本（Tesla）展示的是**「车控开放」这一更激进的产品形态**——把车控能力开放给第三方，并以「虚拟密钥 + 资源级策略」控制风险。国内有取证的平台**均停留在服务云/企业集成层**。**这可能是「阶段差」，也可能是「披露差」**——本报告无法区分（§16.3.2）。

### 16.4.4 差异维度四：国密栈 vs 国际 PKI 栈

| 观察 | 国内 | 国际 |
|---|---|---|
| 密码算法族 | SM2/SM3/SM4（GB/T 32918/32905/32907）[A] | ECDSA/ECDH、AES（RFC 6090/5480、FIPS 197）[A] |
| 消息语法 | GB/T 35275-2017 / GB/T 35276-2017 [A] | RFC 5280 X.509 / CMS [A] |
| TLS 套件 | RFC 8998（SM 套件，TLS 1.3）[A] | RFC 8446（标准套件）[A] |
| 车企实际使用 | **九家全部未取证**（§7.10 第 5 条） | **未取证**（本报告亦未取得 Tesla/Mercedes 明文使用国密/国际栈的密码套件清单） |

**结构性差异（本报告判断，推测，非事实）**：国内合规路径**可能**推动「国密栈」与「国际 PKI 栈」并存（双栈），带来证书链、消息语法、套件协商上的工程差异（详见 §16.1.4 的对照表）。**但必须明确**：`source-dossier.md` §7.10 第 5 条记载，**九家国内车企本次全部未取得关于国密、mTLS、证书轮换的任何官方一手来源**——**因此「国内车企实际使用国密栈」是一个未取证命题，本章严禁将其写成事实。** 同样，国际样本的密码套件细节本次也未取得明文。**这是一条「理论差异明确、实证缺口巨大」的维度**，须在 16.6 重点补证。

### 16.4.5 差异维度五：数据本地化 vs 数据可携权

| 观察 | 国内 | 国际 |
|---|---|---|
| 数据义务 | 境内存储 + 出境评估（§1.3 [A]） | 数据可携权/互联产品数据访问权（欧盟 Data Act，§1.4 标 [C]） |
| 对授权的影响 | **本报告判断（推测，非事实）**：授权决策点须识别数据流向，跨境令牌交换需评估 | **据 §7.1**：Tesla 车主可撤销授权（`revoke/consent` 端点 [A]），体现用户对授权的控制 |

**结构性差异（本报告判断，推测，非事实）**：国内路线的重心是「**数据不出境**」，国际路线（尤其欧盟）的重心是「**用户可携/可访问**」。落在授权层：国内更强调**地域与流向控制**，国际更强调**用户授权可视化与撤销**（Tesla 的撤销入口是公开实例 [A]，Mercedes 的同意界面展示 scope 与 purpose URL [A]）。**两条路线并不互斥**，但它们塑造了不同的授权 UI/审计优先级。

### 16.4.6 差异维度六：企业级开放 vs 消费者级开放

| 观察 | 国内 | 国际 |
|---|---|---|
| 有取证平台的消费者 | 蔚来 = 商务渠道合作方 [A]；比亚迪 = 公司/组织 [A]；小米 = 硬件模组厂商 [A] | Tesla = 第三方应用开发者（代表车主）[A]；Mercedes = 开发者（代表终端用户）[A] |
| 接入方式 | 商务渠道 / 组织认证 / 模组认证 | 自助注册 + OAuth 授权码 |
| 文档可达性 | 定向提供（蔚来文档需 token）[A] | 公开文档（`developer.tesla.com`）[A] |

**结构性差异（本报告判断，推测，非事实）**：国内有取证的开放平台以「**企业级/B 端**」为主，接入靠商务渠道；国际样本以「**消费者级/C 端**」为主，接入靠自助 + OAuth。**这直接导致取证难度差异**：B 端定向开放的文档**天然不可公开检索**，这正是本章 45 格矩阵大面积「未取证」的结构性原因（§16.0.4）。

## 16.5 关于数字钥匙的中国市场特殊面

> **本节立场**：数字钥匙是「授权与访问控制」在物理世界的延伸——**一把数字钥匙就是一组被授权的密钥**。但本章对数字钥匙的取证**极为有限**：`source-dossier.md` §5 提供的是**国际规范侧**的一手证据（CCC、FiRa），国内车企侧仅有二手材料（§7.10 第 1、2 条）。本节据此**只讲「中国市场的结构性特殊面」与「规范层的意义」，可推测处一律标注**。

### 16.5.1 CCC 3.0 的公开事实（国际规范侧，[A]/[B]）

`source-dossier.md` §5 一手条目：

- **CCC Digital Key Release 3.0 发布公告（2021-04-21）**：新增 **BLE + UWB** 实现被动无钥匙进入与启动，**NFC 保留为强制备用方案**，**密钥存储于 Secure Element** —— Car Connectivity Consortium —— [A]
- CCC Digital Key 主页面（跨 OS 生态、认证计划）—— `https://carconnectivity.org/digital-key/` —— [A]
- CCC Digital Key Release 3 v1.1 规范向公众开放 —— [B]
- CCC 与 FiRa Consortium 就 UWB 技术合作 —— [B]
- FiRa 2.0（2023-11）/ Core 3.0（2025-01）/ Core 4.0（2025-12）—— [B]

**要点**：CCC 3.0 的三项技术基元是 **BLE（发现/唤醒）+ UWB（安全测距/抗中继）+ NFC（强制备用）**，密钥存于 **SE（Secure Element）**[A]。这三者在国内市场的适配，是本小节的主题。

### 16.5.2 GB/T 44402.1-2024 参考架构的意义（含推测标注）

`source-dossier.md` §1.2 一手条目：**GB/T 44402.1-2024《卡及身份识别安全设备 数字钥匙系统 第 1 部分：参考架构》**，发布 2024-08-23，实施 2025-03-01 [A]，被 dossier 注释为「**中国数字钥匙授权模型的国标参考架构**」。

**意义分析（区分事实与推测）**：

- **已确证事实 [A]**：该标准存在，是「数字钥匙系统」系列标准的**第 1 部分：参考架构**，2025-03-01 实施。**「第 1 部分：参考架构」的编号方式（`.1`）说明这是一个多部分标准（multi-part standard）**，后续部分（`.2`、`.3`…）**本次未取证**，因此**本报告不推测其后续部分的内容**。
- **本报告判断（推测，非事实）**：该参考架构标准的实施（2025-03-01）为国内市场提供了**与国际 CCC 体系并行的一套「国标参考架构」**。这意味着国内车企的数字钥匙实现**可能面临「CCC 兼容」与「国标符合」两条路线的取舍或并行**。
- **本报告判断（推测，非事实）**：GB/T 44402.1 落在「卡及身份识别安全设备」标准体系下（标题前缀），**这提示其安全模型可能与「安全元件/智能卡」体系更接近**（即把数字钥匙视为一种安全设备凭证），而 CCC 体系则不限定具体安全元件实现。**但本次未取得标准正文，该推断仅为方向性提示。**

### 16.5.3 国内适配的三个结构性问题

**问题一：UWB 的频谱与合规。**

- **已确证 [A]**：CCC 3.0 使用 UWB；FiRa 负责 UWB 技术规范（`source-dossier.md` §5）。
- **本次未取证**：IEEE 802.15.4z（UWB 物理层增强）在 dossier §5 中**标为「未验证：未取得可核验官方 URL」**。因此**本章不给出 UWB 在国内的频谱/合规细节**。
- **本报告判断（推测，非事实）**：UWB 的车载部署涉及频率与功率的监管，其国内适配**可能需要额外的合规确认**——但**具体法规本次未取证，不作断言。**

**问题二：手机厂商钱包生态的中立性。**

- **已确证 [A]**：CCC 强调「跨 OS 生态」（`carconnectivity.org/digital-key/` [A]）；CC Digital Key 有认证计划 [A]。
- **本次未取证**：国内手机厂商钱包（如小米钱包、华为钱包）对数字车钥匙的具体支持**本次未取得一手文档**（§7.8 / §7.9 均记为未取到）。
- **本报告判断（推测，非事实）**：国内数字钥匙落地的关键环节之一是**手机厂商钱包作为钥匙凭证的托管方**；因此**授权链中出现了「车企—手机厂商—车主」三方结构**。这会引入新的信任边界：**手机厂商钱包成为密钥托管方，其安全能力直接影响数字钥匙的整体安全性**（§16.3.3 结构 C「供应商代运营」的变体）。
- **检验方法**：检索各手机厂商钱包对数字车钥匙的支持说明；检索 CCC/FiRa 认证清单是否含国内手机型号。

**问题三：二手报道与一手事实的鸿沟（§7.10 第 1、2 条）。**

- **已确证 [C]**：「蔚来 UWB+蓝牙+NFC 三合一数字钥匙」**仅有二手报道**（新浪汽车等）[C]，**蔚来官方未取得技术说明**；无法确认是否 CCC 3.0、是否有 SE 保护（§7.10 第 1 条）。
- **已确证 [C]**：小鹏 UWB 钥匙为**论坛/短视频内容**，官方未证实（§7.10 第 2 条）。
- **本章纪律**：**这两条均不得作为技术事实写入。** 它们只说明「中国市场存在 UWB 数字钥匙的市场传闻」，**不说明任何车企的 CCC 符合性或 SE 使用情况**。**这正是本章反复强调的「未取证 ≠ 无能力，传闻 ≠ 事实」的双向纪律。**

### 16.5.4 数字钥匙的授权链结构（通用推演）

**本报告判断（推测，非事实）**：把数字钥匙看作授权系统，其链路可抽象为：

```
车主身份（厂商 IdP）
   │  ①授权（同意把钥匙发给谁）
   ▼
密钥签发（车企 KMS / 密钥服务器）
   │  ②密钥分发（公钥/私钥或对称密钥）
   ▼
承运载体（手机 SE / 卡片 / 车端 SE）
   │  ③本地持有（硬件保护）
   ▼
车端验证（车辆侧安全模块校验挑战-响应）
   │  ④本地授权（是否放行解锁/启动）
   ▼
物理动作（车门/启动）
```

**这条链上「国标 vs CCC」的落点（本报告判断，推测，非事实）**：CCC 3.0 明确把密钥存于 SE [A]，因此**落点在「承运载体」与「车端验证」两环**；GB/T 44402.1 作为参考架构 [A]，**可能**规定各环的接口与安全要求，但**本次未取得正文，不展开**。**国内车企的实际落点（是否用 SE、用何算法、是否 UWB）本次九家全部未取证**（§7.10 第 5 条）。

### 16.5.5 本节小结（事实 vs 推测对照）

| 命题 | 状态 |
|---|---|
| CCC 3.0 = BLE + UWB + NFC，密钥存 SE | **[A] 事实**（§5） |
| GB/T 44402.1-2024 是数字钥匙参考架构第 1 部分，2025-03-01 实施 | **[A] 事实**（§1.2） |
| 国内车企是否采用 CCC 3.0 / UWB / SE | **未取证**（§7.10 第 1、2、5 条；仅二手 [C]） |
| 国内市场存在「CCC 与国标并行」的路线取舍 | **推测**（本报告判断） |
| 手机厂商钱包成为密钥托管方引入三方信任边界 | **推测**（本报告判断） |
| 数字钥匙授权链的环节划分 | **推测**（本报告判断） |

## 16.7 本章小结

本章用「已取证事实 + 明确披露缺口 + 基于国标的设计空间分析」三层结构，对国内九家新能源车企的授权与访问控制实践做了尽可能诚实的记录。小结分四部分：**已确证的三条事实 / 未确证的四个方向 / 对企业选型的启示 / 本章的自我限制**。全部区分事实与推测。

### 16.7.1 已确证的三条事实

**事实一：国内车企在「授权与访问控制」切面上的公开一手证据极为稀薄，45 格中仅 9 格取到 [A]，核心授权切面仅 2 格。**

依据：§16.0.4 的 45 格矩阵。九家中只有比亚迪（i迪桥）、蔚来（Open NSC）、小米（IoT 平台/信任中心）、理想（隐私政策）、奇瑞（漏洞专栏）取到了 [A] 级的公开页面；而落在**授权与访问控制（C3）**切面核心的，只有**比亚迪的 APIKey** 与**蔚来的 app-id+secret** 两格 [A]。**这是本次取证横截面的最硬结论，也是本章全部后续分析的事实起点。**

**事实二：有取证的两家国内开放平台，其鉴权形态均为「非 OAuth」的应用身份型（APIKey / app-id+secret），且均非车控开放。**

依据：`source-dossier.md` §7.6（比亚迪：appKey + `x-Gateway-APIKey` Header，企业级 ESB，覆盖供应链/研发/智造/营销/物流/品质/财务七大领域 [A]）；§7.7（蔚来：app-id+secret 双凭证，服务云业务，不含车控/数字钥匙 API [A]）。**对照国际样本**（§7.1 Tesla、§7.2 Mercedes-Benz 均为 OAuth 授权码流 [A]），国内有取证路径呈现「应用身份型 / 服务层」的结构特征。**此结论仅覆盖被取证的两家，不得外推为行业事实。**

**事实三：中国已建立覆盖「车云授权与接口」的国标与法规底座，且强制性国标于 2026-01-01 强制适用。**

依据：§16.1。强制性国标 GB 44495-2024 / GB 44496-2024（2026-01-01 实施）[A]；与授权/接口直接相关的推荐性国标 GB/T 47324-2026（车联网平台网络安全防护要求）、GB/T 47467-2026（车联网安全管理接口规范）、GB/T 45112-2024（C-V2X 证书管理体系）、GB/T 44402.1-2024（数字钥匙参考架构）[A]；行政法规《汽车数据安全管理若干规定（试行）》（重要数据目录/境内存储/年度报送/出境评估）[A]；国密算法族 GB/T 32918/32905/32907/35275/35276 与 RFC 8998（SM 套件 TLS 1.3）[A]。**这构成了国内车企授权架构的「必须做什么」的约束集。**

### 16.7.2 未确证的四个方向

**方向一：国内车企的车云授权协议细节（是否 OAuth、scope 粒度、令牌生命周期、逐车主同意）。**

状态：**未取证**。九家中两家（蔚来、比亚迪）的取证均落在**非 OAuth 的服务层**；**其余七家全部未取得任何鉴权机制文档**。**因此「国内车企是否采用 OAuth 授权码流」是一个未确证命题。** 补证：16.6 序号 1、4、5、8、11、21。

**方向二：国内车企的密码学与硬件根实现（国密 / mTLS / HSM / SE / TEE）。**

状态：**全部未取证**。`source-dossier.md` §7.10 第 5 条明确：**九家国内车企本次全部未取得关于国密 SM2/SM3/SM4、mTLS 双向证书、证书轮换、HSM/SE/TEE 的任何官方一手来源**。**本章据此把「国内车企使用国密/专用安全硬件」严格标注为未取证，绝不写成事实。** 补证：16.6 序号 27、28、29。

**方向三：国内车企的数字钥匙实现（是否 CCC 3.0、是否 UWB、是否 SE）。**

状态：**未取证**。仅存在二手材料（蔚来 [C]、小鹏 [C]，§7.10 第 1、2 条），**不得作为事实**。国际规范侧（CCC 3.0 = BLE+UWB+NFC、密钥存 SE）[A] 与国标侧（GB/T 44402.1-2024 参考架构）[A] 均已确证，但**车企侧落点未取证**。补证：16.6 序号 2、7、13、17、24。

**方向四：国内车企的授权治理组织结构（集团统一 / 事业群各自 / 供应商代运营）。**

状态：**未取证（本节为推演）**。§16.3.3 的三类结构是**组织假设**，用于指导补证，**不构成对任何车企的事实断言**。补证：16.6 各家的 ICP 备案与 RFI 条目。

### 16.7.3 对企业选型的启示

> **本节是面向读者的中性建议**，不构成对任何车企的评价。**每条建议均建立在「本章已确证事实」或「显式标注的推测」之上。** 凡涉及具体车企的能力判断，一律提示「须先完成 16.6 的补证」。

**启示一：评估任何车企的车云授权能力，必须先索取「授权三件套」。** 依据本章的取证实践，判断一个车云开放平台的授权成熟度，最有效的三个索取对象是：

1. **鉴权与令牌文档**（凭证类型、令牌模型、TTL、轮换、吊销）；
2. **scope / 授权粒度清单**（是否有资源级策略，对应 RFC 9396 / RFC 8705 思路）；
3. **逐车主同意与撤销流程**（对应 §16.1.3 数据合规的可追溯要求）。

**本章的 45 格矩阵说明：这三个对象在国内车企的公开渠道上几乎全军覆没（§16.0.4），因此必须通过 RFI/商务渠道主动索取，而非依赖公开检索。**

**启示二：合规时间点是 2026-01-01，评估窗口应以该节点为界。** GB 44495-2024 / GB 44496-2024 于 **2026-01-01 强制适用** [A]。**本报告判断（推测，非事实）**：2026-01-01 之后上市的新车型，其车云授权控制将成为**合规要求**而非可选优化。采购或合作评估时，可将「是否提供符合 GB 44495/44496 的授权控制说明」作为一项明确的准入问题。

**启示三：区分「服务云开放」与「车控开放」，不要把前者当作后者的能力证明。** 本章 16.2.8 用整整一节说明了这个陷阱：**比亚迪 i迪桥是服务层 ESB [A]，不能用来证明其车控授权能力**（§7.10 第 3 条）。同理，**小米 IoT 平台面向模组厂商 [A]，不能用来证明其车云授权能力**（§7.10 第 6 条）。**评估时应明确询问「该平台是否包含车辆控制类接口、其授权是否代表车主」。**

**启示四：为「国密栈 vs 国际 PKI 栈」的双栈现实预留工程与合规预算。** 依据 §16.1.4，国内合规路径使国密栈（SM2/SM3/SM4 + RFC 8998）可能与国际 PKI 栈并行。**本报告判断（推测，非事实）**：涉及国内销售车型的车云链路，其证书体系、消息语法、TLS 套件可能需要在两套栈之间做适配（无论最终选择哪一套）。**但需强调：本次未取得任何国内车企实际使用国密栈的一手证据**（§7.10 第 5 条），因此这是「预算预留」建议，不是「现状断言」。

**启示五：把「取证缺口」当作评估的一等对象。** 本章的写作实践本身说明：**在授权安全评估中，「拿不到证据」与「证据显示不安全」是两种不同的风险**。前者需要补证动作（16.6 的 30 条），后者需要控制建议。**混淆二者——把「未取到」读成「没有」或「不安全」——是评估中最常见的系统性错误。** 本报告的中立性红线（§3.2 第 4 条）正是为此设立。
